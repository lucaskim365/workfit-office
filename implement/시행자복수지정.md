# 복수 시행자 지정 및 담당자(집행자) 처리 아키텍처 명세서 (상용화 레벨 고도화)

본 문서는 **WorkFit 그룹웨어 프로젝트**에서 결재 승인 완료 후 여러 **시행부서**로 문서가 이관되고, 각 부서별 담당자가 독립적으로 업무를 집행하여 완결 짓는 **"복수 시행처 업무 이관 및 추적 시스템"**의 상용 그룹웨어급 아키텍처 및 데이터베이스 설계 명세서입니다.

---

## 1. 용어 정의 (Terminology)

상용화 단계에서 개발자 및 사용자의 혼선을 방지하기 위해 용어의 정의를 한 단계 구체화합니다.

* **기안서 (Approval Document)**: 기안자가 작성하여 내부 결재선을 거쳐 최종 승인되는 원본 결재 문서.
* **시행처 / 시행부서 (Target Department)**: 최종 결재 승인 후 업무 수행 의무를 이관받는 부서(들) 또는 외부 기관.
* **담당 집행자 (Assignee)**: 시행부서 소속 팀원 중, 해당 업무를 전담하여 접수하고 실무를 처리하는 담당 실무자.
* **시행 임무 (Document Execution)**: 각 부서별로 할당된 독립적인 업무 수행 단위(인스턴스).

---

## 2. 데이터베이스 아키텍처 (Hybrid NoSQL Design)

Firestore NoSQL 환경에서 대규모 조회(내 시행 문서함, 부서별 미접수 배지 등) 및 동시성 문제를 해결하기 위해 **"원본 문서 Snapshot 백업"**과 **"독립 조회용 Task 인덱스 컬렉션"**을 분리하는 하이브리드 모델을 채택합니다.

### 2.1. 원본 결재 문서 컬렉션 (`approvalDocs`)
결재 이력 및 당시 지정된 시행처 목록을 Snapshot 형태로 직접 소유하여 단일 문서 조회 속도를 보장합니다.

```typescript
export interface ApprovalDoc {
  id: string;
  title: string;
  drafterId: string;
  drafterDept: string;
  status: '임시저장' | '진행중' | '완료' | '반려' | '회수';
  
  /** 
   * 기안 당시에 지정된 시행처 목록 Snapshot 
   * (인사이동, 조직개편 시점에도 과거 문서의 무결성 보존 목적)
   */
  executionsSnapshot?: DocumentExecutionSnapshot[];
}

export interface DocumentExecutionSnapshot {
  deptId: string;
  deptName: string;
  status: ExecutionStatus;
  assigneeId: string | null;
  assigneeName: string | null;
}
```

### 2.2. 독립 시행 임무 컬렉션 (`documentExecutions`)
각 부서의 실무자가 자신의 시행함이나 부서 미접수 함을 효율적으로 인덱싱 조회할 수 있도록 독립 컬렉션으로 분리합니다.

```typescript
export type ExecutionStatus =
  | 'WAITING'       // 원본 결재 대기 중 (아직 시행 발송 전)
  | 'UNASSIGNED'    // 부서 이관 완료, 담당자 미지정 (부서 전체 대기)
  | 'IN_PROGRESS'   // 담당자 지정 및 처리 중
  | 'COMPLETED'     // 실무 처리 완료
  | 'RETURNED'      // 시행 불가 및 반송 (일반 결재 반려와 구분)
  | 'CANCELLED';    // 기안자/관리자에 의한 시행 취소

export interface DocumentExecution {
  id: string;          // {documentId}_{deptId} 조합의 고유 식별자
  documentId: string;  // 원본 결재문서 ID (Foreign Key 역할)
  
  // 시행 대상 부서
  targetDeptId: string;
  targetDeptNameSnapshot: string;

  // 담당 집행자 (Claim 방식 지정)
  assigneeId: string | null;
  assigneeNameSnapshot: string | null;

  // 상태 관리
  status: ExecutionStatus;

  // 타임라인 이력
  receivedAt: string | null;   // 부서 이관 완료 일시 (결재 완료 시점)
  assignedAt: string | null;   // 담당자 배정 일시
  completedAt: string | null;  // 집행 완료/반송 일시
  updatedAt: string;

  // 피드백 및 처리 기록
  comment: string | null;
  
  // 이력 타임라인 추적 (감사용 로그)
  history: ExecutionHistoryEvent[];
}

export interface ExecutionHistoryEvent {
  eventId: string;
  type: 'DISPATCHED' | 'ASSIGNED' | 'RELEASED' | 'COMPLETED' | 'RETURNED' | 'CANCELLED';
  actorId: string;      // 작업을 수행한 사용자 ID
  actorName: string;    // 작업을 수행한 사용자 이름
  comment?: string;     // 처리 의견 / 반려(반송) 사유
  createdAt: string;
}
```

## 3. 핵심 비즈니스 로직 및 동시성 제어

### 3.1. 원자적 담당자 배정 (Atomic Claim Transaction)
한 부서에 여러 명의 실무자가 동시에 `[내가 담당하기]`를 클릭했을 때 발생할 수 있는 Race Condition(동시성 경쟁)을 방지하기 위해, Firestore의 **Transaction(트랜잭션)** 또는 낙관적 락을 이용하여 원자적 배정을 보장합니다.

```typescript
// 원자적 담당 배정 가상 트랜잭션 의사 코드
async function claimExecution(executionId: string, userId: string, userName: string) {
  const execRef = doc(db, 'documentExecutions', executionId);
  
  await runTransaction(db, async (transaction) => {
    const execDoc = await transaction.get(execRef);
    if (!execDoc.exists()) throw new Error('존재하지 않는 시행 임무입니다.');
    
    const data = execDoc.data() as DocumentExecution;
    
    // 이미 담당자가 지정되었는지 사전 검증 (방어선)
    if (data.assigneeId !== null) {
      throw new Error(`이미 담당자(${data.assigneeNameSnapshot})가 배정되었습니다.`);
    }
    
    // 상태 및 담당자 업데이트
    transaction.update(execRef, {
      assigneeId: userId,
      assigneeNameSnapshot: userName,
      status: 'IN_PROGRESS',
      assignedAt: new Date().toISOString(),
      history: [
        ...data.history,
        {
          eventId: generateUUID(),
          type: 'ASSIGNED',
          actorId: userId,
          actorName: userName,
          createdAt: new Date().toISOString()
        }
      ]
    });
  });
}
```

### 3.2. 보안 및 부서 열람 권한의 차별화 (Security Rules)
부서에 배포되는 시행 문서 중 **인사/연봉 등 비공개 지정 문서**에 대하여 무차별 열람을 차단하기 위한 3단계 보안 정책을 수립합니다.

1. **전체 공개형 시행문서**: 해당 부서 소속 임직원 전체 열람 허용.
2. **부서 보안 문서**: 해당 부서의 **부서장(Manager)** 및 **지정된 담당자(assignee)**만 열람 허용. 일반 부서원의 접근 시 차단.
3. **Firestore Security Rules 정의**:
   ```javascript
   match /documentExecutions/{execId} {
     allow read: if request.auth != null && (
       resource.data.assigneeId == request.auth.uid ||
       getUserDept(request.auth.uid) == resource.data.targetDeptId && isDeptManager(request.auth.uid)
     );
   }
   ```

## 4. 사용자 관점의 UX/UI 개선 모델

일반 실무자 관점에서 "내가 해야 할 일"과 "부서의 대기 상태"를 명확하게 구분할 수 있도록 목록 및 상세 카드를 시각적으로 재정립합니다.

### 4.1. 시행 문서함 상태 탭 분류
* **부서 시행 미지정**: 우리 부서로 왔지만 아무도 담당자로 지정하지 않은 업무 (빨간색 경고 배지 유발).
* **내 진행 업무**: 내가 담당자로 Claim하여 처리 중인 업무.
* **부서 처리 완료**: 우리 부서에서 종결 지은 이력 보관함.

### 4.2. 상세 카드 내 처리 컴포넌트 시각화
```text
[ 시행 부서별 처리 현황 ]
──────────────────────────────────────
■ 인사팀  | 담당자: 홍길동(과장)  | 🟢 완료     (처리일: 08/07 14:00)
  └ "인사 시스템 동기화 및 부서배치 발령 완료했습니다."
  
■ 총무팀  | 담당자: 미지정        | 🟡 담당자 지정 필요 [ 내가 담당하기 ]
  
■ 개발팀  | 담당자: 김철수(대리)  | 🔵 처리중
```

## 5. 결재 완료(Approval)와 시행 종결(Execution Complete)의 상태 전이

1. 원본 기안서의 결재가 완료(`status: '완료'`)되는 것은 문서의 효력 발생을 뜻하며, 이때 원본 기안서의 상태 변경은 완료 처리되어 고정됩니다.
2. 각 부서별 `DocumentExecution`은 **결재 완료 이후에 활성화**되어 각자 다른 시행 주기(시행 완료, 반송)로 동작합니다.
3. 모든 지정 부서의 `DocumentExecution`이 `'COMPLETED'` 또는 `'RETURNED'` 상태가 되면, 전체 시행 업무 통계는 **"최종 시행 종결"**로 자동 합산 마감 처리됩니다.
