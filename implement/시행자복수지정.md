# 복수 시행자 지정 및 담당자(집행자) 처리 아키텍처 명세서 (상용화 레벨 고도화)

본 문서는 **WorkFit 그룹웨어 프로젝트**에서 결재 승인 완료 후 여러 **시행부서**로 문서가 이관되고, 각 부서별 담당자가 독립적으로 업무를 집행하여 완결 짓는 **"복수 시행처 업무 이관 및 추적 시스템"**의 상용 그룹웨어급 아키텍처 및 데이터베이스 설계 명세서입니다.

---

## 1. 용어 정의 (Terminology)

상용화 단계에서 개발자 및 사용자의 혼선을 방지하기 위해 용어의 정의를 한 단계 구체화합니다.

* **기안서 (Approval Document)**: 기안자가 작성하여 내부 결재선을 거쳐 최종 승인되는 원본 결재 문서.
* **시행처 / 시행부서 (Target Department)**: 최종 결재 승인 후 업무 수행 의무를 이관받는 사내 부서(들).
* **담당 집행자 (Assignee)**: 시행부서 소속 팀원 중, 해당 업무를 전담하여 접수하고 실무를 처리하는 담당 실무자.
* **시행 임무 (Document Execution)**: 각 부서별로 할당된 독립적인 업무 수행 단위(인스턴스).

---

## 2. 데이터베이스 아키텍처 (Hybrid NoSQL Design)

Firestore NoSQL 환경에서 대규모 조회(내 시행 문서함, 부서별 미접수 배지 등) 및 동시성 문제를 해결하기 위해 **"원본 문서 Snapshot 백업"**과 **"독립 조회용 Task 인덱스 컬렉션"**을 분리하는 하이브리드 모델을 채택합니다.

### 2.1. 원본 결재 문서 컬렉션 (`approvalDocs`)
결재 이력 및 당시 지정된 시행처 목록을 Snapshot 형태로 직접 소유하여 단일 문서 조회 속도를 보장합니다.

> [!IMPORTANT]
> **Source of Truth (참값의 원천)**
> 실시간 시행 상태와 집행자의 참값(Source of Truth)은 `documentExecutions` 컬렉션입니다.
> `ApprovalDoc.executionsSnapshot`은 **기안 당시 "어느 부서로 시행을 보냈는지"에 대한 기록 및 단순 조회용 Snapshot**이며, 실시간 상태값 검증에는 사용하지 않습니다.

```typescript
export interface ApprovalDoc {
  id: string;
  title: string;
  drafterId: string;
  drafterDept: string;
  status: '임시저장' | '진행중' | '완료' | '반려' | '회수';
  
  /** 
   * 기안 당시에 지정된 시행처 목록 Snapshot 
   * (인사이동, 조직개편 시점에도 과거 문서의 무결성 보존 목적)
   */
  executionsSnapshot?: DocumentExecutionSnapshot[];
}

export interface DocumentExecutionSnapshot {
  executionId: string; // 연결된 실제 DocumentExecution ID
  deptId: string;
  deptName: string;
}
```

### 2.2. 독립 시행 임무 컬렉션 (`documentExecutions`)
각 부서의 실무자가 자신의 시행함이나 부서 미접수 함을 효율적으로 인덱싱 조회할 수 있도록 독립 컬렉션으로 분리합니다.

```typescript
import { Timestamp } from 'firebase/firestore';

export type ExecutionStatus =
  | 'WAITING'       // 원본 결재 대기 중 (아직 시행 발송 전)
  | 'UNASSIGNED'    // 부서 이관 완료, 담당자 미지정 (부서 전체 대기 / 배정 대기)
  | 'IN_PROGRESS'   // 담당자 지정 및 처리 중
  | 'COMPLETED'     // 실무 처리 완료 (정상 종결)
  | 'RETURNED'      // 시행 불가 및 반송 (기안자 보완 후 재처리 대기)
  | 'CANCELLED';    // 기안자/관리자에 의한 시행 취소

export interface DocumentExecution {
  id: string;          // 고유 UUID (동일 부서 다중 시행 및 재시행 대비)
  documentId: string;  // 원본 결재문서 ID (Foreign Key 역할)
  
  // 시행 대상 부서
  targetDeptId: string;
  targetDeptNameSnapshot: string;

  // 담당 집행자 (Claim 방식 지정)
  assigneeId: string | null;
  assigneeNameSnapshot: string | null;

  // 상태 및 권한 정책
  status: ExecutionStatus;
  
  /** 
   * 시행 상세조회 공개 범위 (기존 프로젝트 visibility 규격 적용)
   * - '부서': 시행부서 소속 직원 전체 열람 허용 (일반 시행 공문용)
   * - '비공개': 배정된 담당자(assignee) 및 부서 관리자(직책이 팀장/부서장 등인 임직원)만 열람 허용 (민감 시행 공문용)
   * - '전사': 전사 공문 성격으로 전체 열람 가능
   */
  visibility: '부서' | '비공개' | '전사';

  // 타임라인 이력
  dispatchedAt: Timestamp | null; // 최종 승인되어 부서로 발송된 시점
  receivedAt: Timestamp | null;   // 부서 이관 접수 일시
  assignedAt: Timestamp | null;   // 담당자 배정 일시
  completedAt: Timestamp | null;  // 집행 완료/반송 일시
  updatedAt: Timestamp;

  // 피드백 및 처리 기록
  comment: string | null;

  /**
   * 시행부서의 반송 사유 성격 분류 (RETURNED 상태일 때 세부 분기용)
   * - 'SUPPLEMENT': 결재 변경이 필요 없는 단순 자료/정보/파일 보완 요구
   * - 'APPROVAL_CHANGE': 결재권자의 의사결정 범위(금액, 대상, 중요계약 조건) 변경이 필요하여 재결재를 요구하는 건
   */
  returnReasonType: 'SUPPLEMENT' | 'APPROVAL_CHANGE' | null;
}
```

### 2.3. 시행 이력 서브 컬렉션 (`documentExecutions/{executionId}/history`)
데이터 크기 무제한 증가 및 Firestore 문서 1MB 한계를 해결하기 위해, 이력 필드를 단일 문서 내 배열로 보관하지 않고 **서브 컬렉션으로 분리**하여 추가형(Append-Only) 구조로 설계합니다.

```typescript
import { Timestamp } from 'firebase/firestore';

export interface ExecutionHistoryEvent {
  eventId: string;
  type: 'DISPATCHED' | 'ASSIGNED' | 'RELEASED' | 'COMPLETED' | 'RETURNED' | 'CANCELLED' | 'REASSIGNED';
  actorId: string;      // 작업을 수행한 사용자 ID
  actorName: string;    // 작업을 수행한 사용자 이름
  comment?: string;     // 처리 의견 / 반려(반송) 사유
  createdAt: Timestamp;
}
```

## 3. 핵심 비즈니스 로직 및 동시성 제어

### 3.1. 원자적 담당자 배정 (Atomic Claim Transaction)
여러 실무자가 동시에 `[내가 담당하기]`를 클릭했을 때 발생할 수 있는 Race Condition(동시성 경쟁)을 방지하기 위해, Firestore의 **Transaction(트랜잭션)**을 이용하여 원자적 배정을 보장합니다.

```typescript
// 원자적 담당 배정 트랜잭션 의사 코드
async function claimExecution(executionId: string, userId: string, userName: string) {
  const execRef = doc(db, 'documentExecutions', executionId);
  const historyColRef = collection(db, 'documentExecutions', executionId, 'history');
  
  await runTransaction(db, async (transaction) => {
    const execDoc = await transaction.get(execRef);
    if (!execDoc.exists()) throw new Error('존재하지 않는 시행 임무입니다.');
    
    const data = execDoc.data() as DocumentExecution;
    
    // 이미 완료되었거나 취소된 임무 및 중복 지정 방지 검증
    if (data.status !== 'UNASSIGNED' || data.assigneeId !== null) {
      throw new Error(`이미 업무가 접수되었거나 담당자(${data.assigneeNameSnapshot})가 배정되어 처리 중입니다.`);
    }
    
    // 1. 상태 및 담당자 업데이트
    transaction.update(execRef, {
      assigneeId: userId,
      assigneeNameSnapshot: userName,
      status: 'IN_PROGRESS',
      assignedAt: serverTimestamp(),
      updatedAt: serverTimestamp()
    });

    // 2. 이력 서브 컬렉션 추가
    const newEventRef = doc(historyColRef);
    transaction.set(newEventRef, {
      eventId: newEventRef.id,
      type: 'ASSIGNED',
      actorId: userId,
      actorName: userName,
      createdAt: serverTimestamp()
    });
  });
}
```

### 3.2. 보안 및 부서 열람 권한의 차별화 (Security Rules)
부서에 배포되는 시행 문서 중 **인사/연봉 등 비공개 지정 문서**에 대하여 무차별 열람을 차단하기 위한 보안 정책을 규칙으로 명시합니다.

```javascript
service cloud.firestore {
  match /databases/{database}/documents {
    match /documentExecutions/{execId} {
      allow read: if request.auth != null && (
        // 1. 공개 범위가 전사인 경우 모든 임직원 열람 허용
        resource.data.visibility == '전사' ||
        // 2. 공개 범위가 부서 전체 공개인 경우 해당 부서 소속 팀원 열람 허용
        (resource.data.visibility == '부서' && getUserDept(request.auth.uid) == resource.data.targetDeptId) ||
        // 3. 비공개 문서인 경우: 지정 담당자이거나 부서의 관리 책임자(직책 검증)만 허용
        (resource.data.visibility == '비공개' && (
          resource.data.assigneeId == request.auth.uid ||
          (getUserDept(request.auth.uid) == resource.data.targetDeptId && isDeptManager(request.auth.uid))
        ))
      );
    }
  }
}
```

## 4. 상태 머신 (State Machine) 및 전이 규칙

실무의 모든 진행 루트와 취소/반송 라이프사이클을 매핑한 상태 전이 규칙입니다.

### 4.1. 상태 전이 다이어그램

```text
최종 승인 완료 (dispatchedAt)
   │
   ▼
[ UNASSIGNED (배정 대기) ] ─── (관리자 강제 취소) ───► [ CANCELLED (취소) ]
   │
   │ 1. 담당자 지정 (ASSIGNED)
   ▼
[ IN_PROGRESS (처리중) ] ──── 2. 담당 반납 (RELEASED) ────► [ UNASSIGNED ]
   │
   ├──── 3. 실무 처리 완료 (COMPLETED) ───────────────────► [ COMPLETED (종결) ]
   │
   └──── 4. 서류 보완 요청 (RETURNED) 
             │
             ├─ [SUPPLEMENT (단순 보완)] ───► 보완 후 재발송 ───► [ UNASSIGNED ]
             │
             └─ [APPROVAL_CHANGE (의사결정 변경)] 
                   │
                   ▼ (원본 보존 보장)
                재결재 필요
```

### 4.2. 주요 이벤트 및 비즈니스 규칙 정의

* **`RELEASED` (담당 반납)**: 배정된 담당자가 담당 업무를 반납하면 해당 시행 임무를 다시 `UNASSIGNED` 상태로 변경한다.

* **`RETURNED` (시행 반송)**: 시행부서에서 처리를 위해 추가 정보나 자료가 필요할 경우 기안자에게 보완을 요청하는 상태이다. 결재 반려와는 구분한다.

* **반송 후 보완 처리**

  * 기존 결재 내용에 변경이 없는 단순 보완(`SUPPLEMENT`)은 재결재 없이 보완 후 재시행한다.
  * 기안자는 시행 업무의 보완 내용을 입력하고 `[재시행 요청]`을 수행한다.
  * 해당 시행 임무만 다시 `UNASSIGNED` 상태로 변경한다.
  * 금액, 목적, 주요 조건 등 기존 결재 내용이 변경되는 경우(`APPROVAL_CHANGE`)에는 재결재가 필요하다.

* **원본 결재 문서 보호**

  * 최종 결재가 완료된 원본 결재 문서는 수정하지 않는다.
  * 시행 과정에서 발생한 보완 내용은 시행 업무에서 별도로 관리한다.

## 5. 결재 완료와 시행 종결의 분리 제어

1. **원본 결재 문서**

   * 최종 결재가 완료되면 `'완료'` 상태로 유지한다.
   * 완료된 원본 결재 문서는 수정하지 않는다.

2. **시행 업무**

   * 각 시행부서는 독립적인 `documentExecution`으로 처리 상태를 관리한다.
   * 특정 부서의 `RETURNED` 또는 처리 지연은 원본 결재 문서의 완료 상태에 영향을 주지 않는다.
   * `RETURNED` 상태는 보완 후 재시행할 수 있다.

3. **최종 시행 종결**

   * 모든 시행 임무가 `COMPLETED` 상태가 되면 최종 시행 완료로 처리한다.
