## 1. 공용 계정 다중 연동 + 발신자 이름 표시

### 요청
네이버 계정 A를 그룹웨어 사용자 B·C가 동시에 연동하고, 각자 발송했을 때
보낸메일함에 누가 보냈는지 이름이 보이게 한다.

### 현재 상태

**다중 연동은 된다.** 유일 인덱스가 `(workfitUserId, email)` 복합키다.

- `scripts/appwrite-schema.ts:862-866` — `UQ('mailAcctOwnerEmail', ['workfitUserId', 'email'])`
- `appwrite/functions/mail/src/accounts.js:99-104` — 중복 검사도 `workfitUserId` 범위로만 건다

다른 사용자가 같은 주소를 등록하는 것은 설계상 허용된다. 단 "계정 공유" 기능이 아니라
**B와 C가 각자 앱 비밀번호를 넣어 독립된 계정 문서를 만드는 것**이다.

**발신자 이름 표시는 안 됐다** (→ `dda55af`·`4e51ff0`로 **해결**). 막던 지점이 세 군데였다.

1. `appwrite/functions/mail/src/send.js:170` — `from: account.email`로 **주소만** 넣는다.
   `이름 <주소>` 포맷터가 같은 파일에 있는데도 받는사람에만 쓰고 있다.
2. `appwrite/functions/mail/src/imap.js:161-173` — 보낸메일함일 때 발신자 자리에
   **첫 번째 수신자를 넣어** 내려보낸다. 주석에 의도가 적혀 있다:
   "보낸메일함에서는 보낸 사람이 항상 나라서 받는 사람을 보여야 목록이 쓸모 있다."
   개인 메일함 기준으로는 맞는 설계이고, 공용 계정에서만 걸림돌이 된다.
   **실제 발신자 정보가 클라이언트까지 아예 전달되지 않는다.**
3. `src/modules/gw/mail/MailList.tsx` — `folder` prop이 없어서 보낸메일함일 때
   다르게 그릴 수 없다.

### 한 일 (완료)
- `send.js`의 `from`에 **그룹웨어 사용자 이름**을 붙인다. SMTP는 주소만 인증 계정과 맞으면
  표시 이름은 자유라 네이버에서도 그대로 나간다.
- 발송할 때 `mailSentBy`에 "누가 보냈나"를 확정 기록한다. From 표시 이름은 문자열이라
  동명이인이 겹치고 공급자가 고쳐 쓸 수도 있어서, `Message-ID`를 키로 우리 쪽에 남긴다.
- 보낸메일함 목록·상세가 `sentBy`를 배지로 보여주고, 기록이 없으면(앱 밖에서 보낸 메일)
  From 헤더 이름으로 물러선다. `imap.js`의 수신자 치환은 그대로 두되 실제 발신자를 함께 싣는다.

> 조인 키는 `Message-ID`가 아니라 **sha256 해시 64자**다(`sentBy.js`). Message-ID는 길이가
> 들쭉날쭉해 인덱스 키 상한에 걸리고, 짧게 자르면 다른 메일이 뭉친다. 쓰는 쪽·읽는 쪽이
> 같은 계산을 써야 해서 모듈 한 곳에 뒀다.

### 결정 — (a) 해결 / (b) 확인만 남음

**(a) `displayName`을 발신자 이름으로 쓸 것인가?** → **안 쓴다.**
`displayName`은 사람 이름이 아니라 **계정 별칭**으로 안내되고 있어
(`MailAccountDialog.tsx:217-218` placeholder가 "업무용 네이버") 전용하면 혼란이 생긴다.
대신 그룹웨어 사용자 이름을 쓰고, 보낸 시점 이름을 `mailSentBy.senderName`에 스냅샷으로 남긴다
— 사람이 나가거나 개명해도 그때 누가 보냈는지는 남는다.

**(b) 읽음·별표가 공유되는 것을 받아들일 것인가?**
읽음·별표는 IMAP **서버 플래그**라 B가 읽으면 C 화면에서도 읽음이 된다.
공용 메일함이면 자연스러울 수 있으나 의도한 동작인지 확인이 필요하다.
(임시보관은 브라우저 로컬 저장이라 반대로 공유되지 않는다.)

## 3. 제목·보낸사람·본문 검색이 잘 안 됨

### 현재 상태
**기능 자체는 구현돼 있다.** `imap.js:132`가 IMAP SEARCH를 이렇게 조립한다:

```js
criteria.or = [{ subject: text }, { from: text }, { body: text }];
```

한글 인코딩(`CHARSET UTF-8`)은 앱 코드에 없지만 **imapflow 라이브러리가 자동으로 붙인다**
(`search-compiler.js:505-508`). 즉 한글 검색이 근본적으로 막혀 있진 않다.

### 원인 후보 (재현 전이라 미확정)

1. **받는사람(TO/CC)을 검색하지 않는다.** ← 가장 유력
   검색 대상이 제목·발신자·본문 셋뿐이다. 그런데 **보낸메일함은 발신자 칸에
   받는사람을 보여준다**(1번 항목 참조). 즉 화면에 보이는 이름으로 검색하면
   보낸메일함에서는 아무것도 안 나온다. 사용자 입장에서 "검색이 안 된다"로 느껴진다.
2. **폴더를 바꾸면 검색어가 지워진다** (`MailScreen.tsx:306-312`).
   의도된 동작이지만 검색이 풀린 걸 모르면 "안 된다"로 보인다.
3. **IMAP 서버의 본문 검색 품질.** 네이버·다음이 BODY 검색을 어디까지 지원하는지는
   서버 구현에 달렸다. 한글 부분일치는 특히 서버마다 다르다.
4. 결과 상한 — `imap.js:147` `uids.slice(-limit)`로 계정당 최근 50건만 가져온다.
   오래된 메일은 검색에 걸려도 목록에 안 나온다.

### 해야 할 일
먼저 **어떤 검색어가 안 나왔는지 한 건만 알려주시면** 위 넷 중 무엇인지 바로 가려진다.
1번이면 `criteria.or`에 `{ to: text }`, `{ cc: text }`를 더하는 것으로 끝난다(소).

## 5. 임시보관 중인 메일 표시

### 현재 상태
임시보관이 **두 곳에 나뉘어 있고, 한쪽만 보인다.**

- **로컬 임시보관**: 브라우저 `localStorage`에 저장(`src/data/mail/draft.store.ts:13`).
  목록에 보이고 편집·삭제된다.
- **서버 임시보관**: IMAP DRAFTS 폴더. **목록에 안 나오고 건수만 알린다** —
  `MailDraftList.tsx:28-33`이 "메일 서버에 임시보관 N건이 더 있습니다" 배너만 띄운다.
- 원인: `MailScreen.tsx:575-582`가 DRAFTS 폴더일 때 `MailList` **대신**
  `MailDraftList`를 렌더한다. 서버 메일은 조회는 되는데 화면에 그려지지 않는다.

### 해야 할 일
DRAFTS 폴더에서 로컬과 서버 임시보관을 **함께** 보여준다.
서버 것은 현재 편집 경로가 없으므로, 열어서 내용을 보고 → 새 메일로 이어쓰기 정도가 현실적이다.

### 결정 필요
**로컬 임시보관을 서버(IMAP APPEND)로 옮길 것인가?**
지금은 브라우저에 저장돼서 **다른 PC·폰에서 안 보인다.** 공용 계정 시나리오(1번)에서는
B가 쓰다 만 메일을 C가 볼 수 없다는 뜻이기도 하다.
`useMailDrafts.ts:9-13` 주석에 이미 이관 경로가 적혀 있다
("`MailGateway`에 `saveDraft`/`deleteDraft`를 더하고 이 훅의 내부만 바꾼다").
저장할 때마다 서버 왕복이 생기고 오프라인 저장이 안 되는 것이 대가다.

## 6. 휴지통 메일 표시 및 완전 삭제

### 현재 상태
- 휴지통 **이동은 된다** (`moveMail` → `TRASH`). 휴지통 폴더 조회·복원도 된다.
- **완전 삭제는 없다. 그리고 의도적으로 뺀 것이다.**
  - `imap.js:234` 주석: "영구 삭제(`\Deleted` + `EXPUNGE`)는 되돌릴 수 없어 열지 않는다."
  - `src/data/mail/mail.gateway.ts:40-41`: "영구 삭제는 열지 않는다."
  - 레포 전체에 `EXPUNGE` / `\Deleted` 사용처 0건.
  - `main.js`의 14개 action 중 메일 삭제는 없다(`deleteAccount`는 계정 삭제).
- 휴지통 폴더에서는 **삭제 버튼 자체가 없고**, 휴지통 비우기 경로도 없다.

### 결정 — **완전 삭제는 보류** (2026-08-24)

사용자가 많아 실수로 눌렀을 때 파장이 크다는 판단으로 **열지 않기로 했다.**
되돌릴 수단이 전혀 없고(실계정 연결 시 실제 메일이 사라짐), 현재의 "휴지통으로 이동"만으로도
사용자가 체감하는 삭제는 충족된다.

따라서 이 항목은 **휴지통 폴더 조회·복원까지만** 유지한다.
`imap.js:234`와 `mail.gateway.ts:40-41`의 "영구 삭제는 열지 않는다" 주석은 **그대로 둔다.**

나중에 다시 논의하게 되면 안전장치 후보는 다음과 같다:
- 휴지통 폴더에서만 노출 + 2단계 확인
- "휴지통 비우기"는 열지 않고 개별 삭제만 허용
- 30일 지난 것만 삭제 허용

## 7. 일정관리 개인/공유 분리

### 요청

"프로젝트 그룹 기준 공유"는 `workProject.memberUserIds`를 그대로 쓰면 된다.

### 걸림돌 두 가지

**(a) 사용자-부서 연결이 FK가 아니라 이름 문자열 매칭이다.**
`user.dept`가 부서 **이름**(문자열)이고 `department.name`과 맞춰본다.
같은 변환이 이미 세 곳에 중복 구현돼 있고 공용 헬퍼가 없다:
- `src/modules/gw/task/TaskScreen.tsx:27`
- `src/features/survey/useSurveyResponse.ts:17`
- `src/modules/gw/resource/ReservationForm.tsx:37`

캘린더에 TEAM 범위를 넣으면 네 번째 중복이 생긴다. **이때 헬퍼로 묶는 것을 권한다.**

**(b) 캘린더 저장소가 전건을 읽어와 코드에서 거른다.**
`src/data/calendarEvent/calendarEvent.repo.ts:105` — `list()`가 전체를 받아
`.filter(e => e.ownerUserId === actor.userId)`로 거른다. 주석에도 명시돼 있다.
Appwrite에 `ownerUserId` 인덱스가 이미 있는데 안 쓴다.
공유를 붙이면 읽을 양이 더 늘어나므로 **이때 서버측 질의로 바꾸는 것이 맞다.**
