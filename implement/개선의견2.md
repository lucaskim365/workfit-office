네. 이번 수정본은 이전 버전과 비교하면 **상용 전자결재를 실제로 개발하기 위한 설계 문서에 상당히 가까워졌습니다.**
특히 제가 이전에 지적했던 핵심 문제인 **시행 업무의 독립 엔티티화, 담당자 Claim 동시성, 권한 분리, 처리 이력, 결재 완료와 시행 완료의 분리**가 대부분 반영됐습니다. 

제 판단으로는 현재 **약 85~90점 수준**입니다.

다만 아직 몇 가지는 **개발 전에 반드시 확정해야 하는 핵심 설계 이슈**가 있습니다. 특히 **Firestore의 `history` 배열, 시행 Snapshot의 정합성, 반송의 의미, Security Rules, 시행 생성 시점**은 지금 확정하지 않으면 나중에 구조를 다시 손봐야 할 가능성이 높습니다.

# 2. 가장 잘 수정된 부분: `documentExecutions`

이전에는:

```text
ApprovalDoc
 └─ executors[]
```

에 많은 책임을 부여하고 있었습니다.

이번에는:

```text
approvalDocs
       │
       │ 1:N
       ↓
documentExecutions
```

구조가 됐습니다.

이건 제가 실제 개발 책임자라면 **채택할 구조**입니다.

왜냐하면 이제 다음과 같은 조회가 가능해지기 때문입니다.

```text
내가 담당자인 시행업무
부서 미지정 시행업무
처리중 시행업무
완료된 시행업무
반송된 시행업무
```

를 `documentExecutions` 중심으로 설계할 수 있습니다.

문서에서도 이를 명확하게 **"독립 조회용 Task 인덱스 컬렉션"**으로 정의하고 있습니다. 

### 이 부분은 그대로 유지하는 것을 추천합니다.

# 3. `ApprovalDoc`의 Snapshot도 좋은 선택입니다

이번에는:

```typescript
executionsSnapshot?: DocumentExecutionSnapshot[];
```

을 두었습니다. 

이것도 좋은 판단입니다.

예를 들어 2026년에:

```text
개발팀
담당자 김철수
```

였는데 2027년에 조직개편이 일어났다고 해서 2026년 문서가:

```text
AI개발팀
담당자 박민수
```

로 바뀌어서는 안 됩니다.

따라서

```text
documentExecutions
→ 현재 업무 상태

executionsSnapshot
→ 문서가 만들어질 당시의 기록
```

이라는 방향은 적절합니다.

### 단, 여기서 아주 중요한 문제가 하나 있습니다.

**Snapshot의 `status`, `assigneeId`, `assigneeName`은 누가 업데이트합니까?**

현재:

```typescript
DocumentExecutionSnapshot {
  deptId
  deptName
  status
  assigneeId
  assigneeName
}
```

이고,

```typescript
DocumentExecution {
  targetDeptId
  assigneeId
  status
}
```

도 있습니다.  

그러면 동일한 데이터가 **두 군데에 존재**합니다.

예:

```text
ApprovalDoc
  executionsSnapshot
    총무팀
    status = UNASSIGNED

DocumentExecution
    총무팀
    status = IN_PROGRESS
```

이런 상태가 발생할 수 있습니다.

---

# 4. 따라서 "Source of Truth"를 반드시 명시하세요

이건 현재 문서에서 가장 중요한 추가 사항 중 하나입니다.

저라면 명확하게 이렇게 정의합니다.

> **실시간 시행 상태의 원본(Source of Truth)은 `documentExecutions`이다.**
>
> `ApprovalDoc.executionsSnapshot`은 문서 표시 및 당시 시행처 기록을 위한 Snapshot이며, 실시간 업무 상태 조회에 사용하지 않는다.

그러면:

```text
ApprovalDoc
└─ executionsSnapshot
       ↓
   기록용 / 문서 표시용

DocumentExecution
       ↓
   실제 업무 상태의 원본
```

이 됩니다.

그리고 `ApprovalDoc.executionsSnapshot.status`와 `assigneeId`까지 정말 필요한지 다시 생각해볼 수 있습니다.

### 제가 더 추천하는 형태

```typescript
interface DocumentExecutionSnapshot {
  executionId: string;
  deptId: string;
  deptName: string;
}
```

즉 **"어디로 시행했는가"만 Snapshot**으로 남기고,

```text
status
assignee
processedAt
history
```

는 `documentExecutions`에서만 관리하는 방식입니다.

이게 데이터 정합성 측면에서 훨씬 안전합니다.

---

# 5. `history`를 배열로 넣은 것은 수정이 필요합니다

현재:

```typescript
interface DocumentExecution {
  ...
  history: ExecutionHistoryEvent[];
}
```

입니다. 

개념적으로는 좋습니다.

하지만 **Firestore 상용 서비스에서는 이 부분을 그대로 구현하는 것을 추천하지 않습니다.**

왜냐하면 하나의 시행 업무가 오래 살아남으면:

```text
DISPATCHED
ASSIGNED
RELEASED
ASSIGNED
RETURNED
ASSIGNED
COMPLETED
...
```

이력이 계속 누적됩니다.

Firestore 문서는 크기 제한이 있기 때문에 **무제한 배열로 감사 로그를 쌓는 구조는 피하는 게 좋습니다.**

또한:

```typescript
history: [
  ...data.history,
  newEvent
]
```

방식으로 전체 배열을 다시 써야 합니다. 현재 Claim 예제에서도 이 방식이 사용되고 있습니다. 

### 저는 이렇게 바꾸겠습니다.

```text
documentExecutions/{executionId}
```

```text
documentExecutionEvents/{eventId}
```

또는

```text
documentExecutions/{executionId}/history/{eventId}
```

구조입니다.

그러면:

```text
documentExecutions
 └─ execution001
       ├─ status
       ├─ assigneeId
       └─ ...

       history
         ├─ event001
         ├─ event002
         ├─ event003
         └─ ...
```

이 됩니다.

**상태 = 현재 문서**

**History = append-only 이벤트**

로 완전히 분리하는 게 좋습니다.

# 6. 현재 Claim Transaction은 방향이 정확합니다

이번 수정에서 가장 마음에 드는 부분 중 하나입니다.

```typescript
await runTransaction(db, async (transaction) => {
    const execDoc = await transaction.get(execRef);

    if (data.assigneeId !== null) {
        throw new Error(...)
    }

    transaction.update(...)
});
```

구조입니다. 

이전 버전에서 제가 지적했던:

> 동시에 여러 사람이 "내가 담당하기"를 눌렀을 때 마지막 사람이 담당자가 되는 문제

를 제대로 해결하고 있습니다.

### 다만 조건을 하나 추가하세요.

현재는:

```typescript
if (data.assigneeId !== null)
```

만 확인합니다.

하지만 다음도 확인해야 합니다.

```text
status === UNASSIGNED
```

즉:

```typescript
if (
  data.status !== 'UNASSIGNED' ||
  data.assigneeId !== null
) {
  throw ...
}
```

그래야 이미:

```text
COMPLETED
RETURNED
CANCELLED
```

된 업무를 다시 Claim하는 것을 막을 수 있습니다.

# 7. `id = {documentId}_{deptId}`는 생각보다 위험합니다

현재:

```typescript
id: string; // {documentId}_{deptId} 조합의 고유 식별자
```

입니다. 

**대부분의 경우에는 작동합니다.**

하지만 상용 시스템이라면 저는 `executionId`를 별도로 생성하겠습니다.

왜냐하면 향후 요구사항이:

```text
문서 A
 ├─ 총무팀 → 자산 지급
 └─ 총무팀 → 차량 배정
```

처럼 **동일 부서에 여러 시행 업무를 부여하는 경우**가 생길 수 있기 때문입니다.

또는:

```text
총무팀
 ├─ 1차 시행
 └─ 재시행
```

같은 상황도 발생할 수 있습니다.

따라서:

```typescript
executionId: string;
documentId: string;
targetDeptId: string;
```

로 별도의 ID를 두는 게 미래 확장성이 좋습니다.

### 단,

WorkFit의 정책상

> **문서 하나당 동일 부서는 반드시 한 번만 시행**

이라고 확정한다면 현재 방식도 충분합니다.

이건 개발자가 임의로 결정하지 말고 **업무 규칙으로 확정**해야 합니다.

# 8. 상태 설계는 상당히 좋아졌지만 `RETURNED`를 다시 정의해야 합니다

현재:

```typescript
WAITING
UNASSIGNED
IN_PROGRESS
COMPLETED
RETURNED
CANCELLED
```

입니다. 

이전보다 훨씬 좋습니다.

특히:

```text
결재 반려
≠
시행 반송
```

을 명시한 것은 아주 좋습니다.

그런데 현재 마지막 정책:

> 모든 지정 부서의 `COMPLETED` 또는 `RETURNED`가 되면 전체 시행 업무를 "최종 시행 종결"

이라고 되어 있습니다. 

여기는 **업무적으로 위험할 수 있습니다.**

예를 들어:

```text
인사팀 → COMPLETED
총무팀 → RETURNED
개발팀 → COMPLETED
```

이면:

> "전체 시행 완료"

라고 볼 수 있을까요?

일반적인 사용자는 **아니라고 생각할 가능성이 높습니다.**

`RETURNED`는 "업무가 끝났다"가 아니라:

> "이 시행 업무를 현재 상태로는 처리할 수 없다"

이기 때문입니다.

---

# 9. `RETURNED`는 "종결"과 "처리 실패"를 분리하는 게 좋습니다

예를 들어 총무팀이:

> 견적서가 누락되어 처리할 수 없습니다.

라고 반송했다면 다음 단계가 필요할 수 있습니다.

```text
RETURNED
   ↓
기안자 보완
   ↓
재시행
   ↓
IN_PROGRESS
   ↓
COMPLETED
```

따라서 현재 구조에서는 최소한 다음 중 하나를 결정해야 합니다.

### A안 — 반송도 최종 종결

```text
COMPLETED
RETURNED
CANCELLED
```

모두 종료 상태.

### B안 — 반송은 재처리 가능 상태

```text
RETURNED
   ↓
재시행
   ↓
IN_PROGRESS
```

저는 **B안을 더 추천**합니다.

그리고 전체 시행 상태도:

```text
WAITING
IN_PROGRESS
PARTIALLY_COMPLETED
COMPLETED
RETURNED
CANCELLED
```

처럼 **집계 상태를 별도로 정의**하는 것이 좋습니다.

# 10. Security Rules는 현재 문서의 가장 큰 미완성 부분입니다

현재:

```javascript
allow read: if request.auth != null && (
  resource.data.assigneeId == request.auth.uid ||
  getUserDept(request.auth.uid) == resource.data.targetDeptId
    && isDeptManager(request.auth.uid)
);
```

입니다. 

문서에서 앞서:

> 전체 공개형 시행문서는 해당 부서 전체 열람

이라고 정의했습니다. 

그런데 **현재 Rules에는 "전체 공개형" 조건이 없습니다.**

현재 Rule대로라면:

```text
일반 부서원
assignee 아님
부서장 아님
```

이면 읽을 수 없습니다.

즉 **정책과 실제 Rule이 불일치합니다.**

# 11. 그래서 `visibility` 또는 `accessLevel`이 필요합니다

예를 들어:

```typescript
accessLevel:
  | 'DEPARTMENT'
  | 'ASSIGNEE_ONLY'
  | 'MANAGER_ONLY'
```

를 둡니다.

그러면:

```text
DEPARTMENT
→ 해당 부서 전체

ASSIGNEE_ONLY
→ 담당자 + 관리자

MANAGER_ONLY
→ 부서장만
```

처럼 Rule을 설계할 수 있습니다.

이것은 단순히 보안 문제가 아니라 **제품 요구사항을 코드로 명확히 표현하는 것**입니다.

용어 정의에서는:

targetDeptId

입니다. 

그러면 외부기관은 표현할 수 없습니다.

# 13. 시행 업무 생성 시점도 반드시 명확히 해야 합니다

현재 상태에는:

```text
WAITING
```

이 있고,

> 원본 결재가 완료된 후 각 DocumentExecution이 활성화

된다고 되어 있습니다.  

그렇다면 질문이 하나 생깁니다.

### `documentExecutions`는 언제 생성합니까?

#### 방법 1

기안 작성 시:

```text
documentExecutions 생성
status = WAITING
```

#### 방법 2

최종 결재 완료 시:

```text
documentExecutions 생성
status = UNASSIGNED
```

저는 **방법 2를 추천합니다.**

왜냐하면 결재가 반려되거나 회수된 문서에 실제 시행 업무가 존재할 필요가 없기 때문입니다.

즉:

```text
기안
 ↓
결재 진행
 ↓
최종 승인
 ↓
DocumentExecution 생성
 ↓
UNASSIGNED
```

가 더 깔끔합니다.

그러면 사실 `WAITING` 상태도 필요 없어질 수 있습니다.

---

# 14. 더 중요한 것은 "최종 승인 → 시행 생성"의 원자성입니다

상용 시스템에서 아주 중요한 부분입니다.

다음 상황이 생기면 안 됩니다.

```text
결재 상태 = 완료
시행 문서 = 생성 실패
```

그러면:

> 결재는 완료됐는데 시행부서에는 문서가 안 온 상황

이 발생합니다.

반대로:

```text
시행 생성
↓
결재 완료 업데이트 실패
```

도 문제가 됩니다.

따라서 이 부분은 **Firestore Transaction/Batch만으로 해결할 수 있는 범위인지, Cloud Function 등 서버 측 처리로 할 것인지** 결정해야 합니다.

특히 현재 구조가 Firebase Client SDK 중심의 Serverless 아키텍처라면 이 부분은 **보안상 클라이언트에게 최종 시행 생성 권한을 직접 주는 것은 신중해야 합니다.**

# 15. `receivedAt`의 주석도 수정하는 게 좋습니다

현재:

```typescript
receivedAt: string | null;
// 부서 이관 완료 일시 (결재 완료 시점)
```

입니다. 

여기서:

> 결재 완료 시점

과

> 부서가 실제로 수신한 시점

은 다를 수 있습니다.

예를 들어:

```text
14:00 결재 완료
14:00 시행 생성
14:01 알림 발송
14:05 부서 시스템 수신
```

이럴 수 있습니다.

따라서:

```text
dispatchedAt
receivedAt
```

를 분리하는 것을 추천합니다.

# 16. 시간 필드는 `string`보다 Firestore Timestamp를 권장합니다

현재:

```typescript
receivedAt: string
assignedAt: string
completedAt: string
updatedAt: string
```

입니다. 

그리고 실제 Claim 코드에서도:

```typescript
new Date().toISOString()
```

을 사용하고 있습니다. 

MVP에서는 괜찮습니다.

하지만 Firestore 기반이면 저는:

```typescript
Timestamp
```

를 사용하겠습니다.

이유는:

* 날짜 범위 검색
* 정렬
* 서버 시간
* 시간대 문제
* 클라이언트 시간 조작 방지

때문입니다.

특히 전자결재는 **감사/법적 증빙 관점에서 시간 데이터가 중요**합니다.

가능하면:

```typescript
serverTimestamp()
```

를 사용하는 게 좋습니다.

# 17. `RELEASED` 이벤트는 의미를 명확하게 해야 합니다

현재 이벤트:

```typescript
'DISPATCHED'
'ASSIGNED'
'RELEASED'
'COMPLETED'
'RETURNED'
'CANCELLED'
```

입니다. 

`RELEASED`가 무엇인지 문서에서 정의되지 않았습니다.

아마:

> 담당자가 담당을 포기하여 다시 미지정 상태로 돌림

을 의미하는 것 같습니다.

그렇다면 매우 좋은 기능입니다.

다만 명시적으로:

> `RELEASED`: 기존 담당자가 담당 업무를 반납하여 `UNASSIGNED`로 되돌리는 행위

라고 정의해야 합니다.

그리고 다음 상태 전이를 허용해야 합니다.

```text
UNASSIGNED
    ↓
IN_PROGRESS
    ↓
RELEASED
    ↓
UNASSIGNED
```

이걸 문서에 넣으면 개발자가 훨씬 정확하게 구현할 수 있습니다.

# 18. UX는 이번 버전에서 상당히 좋아졌습니다

이 부분은 일반 사용자 입장에서 상당히 좋습니다.

```text
부서 시행 미지정
내 진행 업무
부서 처리 완료
```

로 나눈 것은 직관적입니다. 

특히 상세 화면:

```text
■ 인사팀 | 담당자 홍길동 | 완료
■ 총무팀 | 담당자 미지정 | 담당자 지정 필요
■ 개발팀 | 담당자 김철수 | 처리중
```

은 실제 사용자에게 필요한 정보를 잘 보여줍니다. 

### 다만 "부서 시행 미지정"이라는 명칭은 조금 애매합니다.

일반 사용자는:

> "시행 부서가 지정되지 않았다"

로 이해할 수도 있습니다.

저라면:

**`담당자 미지정`**

또는

**`부서 대기`**

라고 하겠습니다.

예:

```text
📥 부서 대기       3
👤 내 담당 업무    5
✓ 완료             12
```

이게 더 직관적입니다.

# 19. 지금 단계에서 반드시 추가할 "상태 전이표"

현재 문서는 상태가 잘 정의되어 있지만 **상태 간 이동 규칙이 아직 없습니다.**

이걸 추가하면 문서의 완성도가 확 올라갑니다.

예를 들어:

```text
결재 완료
   │
   ▼
UNASSIGNED
   │
   │ 담당자 지정
   ▼
IN_PROGRESS
   │
   ├──── 담당 반납 ────→ UNASSIGNED
   │
   ├──── 처리 완료 ────→ COMPLETED
   │
   └──── 처리 불가 ────→ RETURNED

UNASSIGNED
   │
   └──── 관리자 취소 ───→ CANCELLED
```

이 표가 있으면 프론트/백엔드/QA가 동일한 상태 머신을 공유할 수 있습니다.

# 20. 그리고 "담당자 변경"이 빠져 있습니다

현재는:

```text
내가 담당하기
```

가 있습니다.

그런데 실제 회사에서는:

> 김철수에게 배정했는데 김철수가 휴가를 갔다.

가 아주 흔합니다.

따라서 최소한:

```text
담당자 변경
담당자 반납
관리자 강제 재배정
```

이 필요합니다.

특히 **부서장/관리자는 담당자를 강제로 변경할 수 있어야 합니다.**

예:

```text
총무팀
현재 담당자: 김철수

[담당자 변경]
→ 이영희
```

그리고 이 행동은 반드시:

```text
ASSIGNED
REASSIGNED
```

이력으로 남겨야 합니다.

제가 현재 문서를 실제 개발팀에 넘긴다고 가정하면 다음과 같이 판단하겠습니다.

### 🟢 설계 완료 수준

* 시행처 개념
* 담당자 개념
* 시행 업무 엔티티
* 원본문서 Snapshot

* 기본 상태
* 결재/시행 분리
* 기본 UX
* 부서별 병렬 처리

### 🟡 개발 전 확정 필요

* Snapshot과 `documentExecutions` 중 Source of Truth
* 동일 부서 복수 시행 허용 여부
* 시행 업무 생성 시점
* `RETURNED`의 의미
* 반송 후 재시행 가능 여부
* 담당자 변경/재배정 정책
* 외부기관 시행 지원 여부
* 공개/비공개 권한 정책
* `receivedAt` / `dispatchedAt`
* 상태 전이표

### 🔴 반드시 수정 권장

1. `history[]`를 본문 배열로 계속 누적하지 않기
2. `executionsSnapshot.status`와 `documentExecutions.status`의 중복 책임 제거
3. Security Rules와 실제 권한 정책 일치시키기
4. `documentId_deptId` ID 정책 재검토
5. 시간 필드를 Firestore Timestamp로 변경
6. 최종 결재 → 시행 생성 실패에 대한 트랜잭션/재처리 전략 수립
