커뮤니티와 기능이 겹치지 않도록 **“게시판 = 공식적인 정보 전달·열람”**, **“커뮤니티 = 자유로운 소통”**으로 경계를 명확하게 두는 것을 추천합니다.

# 그룹웨어 게시판 기능 설명서

## 1. 기능 개요

### 1.1 기능명

**게시판(Board)**

### 1.2 목적

회사의 공지사항, 경조사, 사내 규정 및 주요 업무 안내사항 등을 게시하고 임직원이 이를 열람할 수 있도록 제공한다.

게시판은 단순한 글 작성 공간이 아니라 **회사에서 공식적으로 전달해야 하는 정보를 관리하는 공간**을 목적으로 한다.

### 1.3 주요 대상

| 사용자     | 주요 기능                        |
| ------- | ---------------------------- |
| 일반 사용자(USER)  | 게시글 조회, 검색, 첨부파일 다운로드, 댓글 작성 |
| 게시판 관리자(OPERATOR) | 게시글 작성·수정·삭제, 공지 관리, 게시글 관리  |
| 시스템 관리자(ADMIN) | 게시판 생성·수정·삭제, 게시판 권한 관리      |

---

# 2. 게시판 구성

초기에는 게시판을 다음과 같이 구성한다.

| 게시판  | 용도             | 예시             |
| ---- | -------------- | -------------- |
| 공지사항 | 전사 또는 부서 주요 공지 | 휴무일 안내, 시스템 점검 |
| 경조사  | 임직원 경조사 안내     | 결혼, 부고         |
| 사내규정 | 회사 규정 및 정책 안내  | 취업규칙, 복무규정     |
| 자료실  | 임직원이 참고할 자료 게시 | 업무 매뉴얼, 양식     |

> 단, 실제 시스템에서는 게시판을 고정된 메뉴로 만들기보다는 **관리자가 게시판을 추가할 수 있는 구조**로 설계하는 것이 좋습니다.

예를 들어 향후 다음과 같은 게시판을 추가할 수 있습니다.

* 인사공지
* 업무공지
* 교육자료
* 안전공지
* 부서공지

# 9. 댓글

게시글에 대한 간단한 의견이나 문의를 작성할 수 있다.

### 기능

* 댓글 작성
* 댓글 수정
* 댓글 삭제
* 댓글 작성자 표시
* 작성일 표시

예:

```text
댓글 2

김철수

08.10 14:32

이영희
부서별 일정도 동일한가요?
```

### MVP 범위

댓글은 **1단계 답글 구조 없이 단순 댓글**로 시작하는 것을 추천합니다.

즉,

```text
게시글
 ├─ 댓글
 ├─ 댓글
 └─ 댓글
```

까지만 지원합니다.

대댓글까지 추가하면 게시판의 복잡도가 빠르게 증가합니다.

# 10. 조회 및 읽음 처리

게시글을 열람하면 조회수를 증가시킨다.

다만 **공지사항의 경우 단순 조회수만으로는 실제 직원이 공지를 확인했는지 판단하기 어렵습니다.**

따라서 향후 다음 기능을 추가할 수 있습니다.

### 읽음 확인

```text
공지사항

2026년 하계 휴가 일정 안내

[읽음 확인]

확인자 37 / 전체 42명
```

관리자는 다음 정보를 확인할 수 있다.

| 직원  | 상태  | 확인일         |
| --- | --- | ----------- |
| 김철수 | 확인  | 08.10 09:31 |
| 이영희 | 확인  | 08.10 09:42 |
| 박민수 | 미확인 | -           |

### MVP 권장

**일반 게시판 → 조회수만 제공**

**공지사항 → 읽음 여부 제공**

이 정도로 차별화하는 것이 적절합니다.

# 12. 권한 관리

게시판은 그룹웨어에서 상당히 중요한 부분입니다.

특히 **사내 규정이나 부서 공지**는 모든 직원이 작성할 수 있어서는 안 됩니다.

### 기본 권한

| 권한      | 조회 | 작성 | 수정 | 삭제 | 관리 |
| ------- | -: | -: | -: | -: | -: |
| 일반 사용자  |  ○ |  △ | 본인 | 본인 |  X |
| 게시판 담당자 |  ○ |  ○ |  ○ |  ○ |  △ |
| 시스템 관리자 |  ○ |  ○ |  ○ |  ○ |  ○ |

### 게시판별 권한

게시판마다 접근 권한을 설정할 수 있도록 한다.

예:

```text
공지사항
조회 권한 : 전 직원
작성 권한 : 인사팀, 총무팀
관리 권한 : 시스템 관리자

부서게시판
조회 권한 : 개발팀
작성 권한 : 개발팀
관리 권한 : 개발팀장
```

# 14. 게시글 상태

게시글은 최소한 다음 상태를 관리한다.

| 상태          | 설명    |
| ----------- | ----- |
| `DRAFT`     | 임시 저장 |
| `PUBLISHED` | 게시 중  |
| `HIDDEN`    | 비공개   |
| `DELETED`   | 삭제    |

다만 **MVP에서는 `PUBLISHED / DELETED` 정도만 구현하고 임시저장은 추후 추가**해도 됩니다.

# 15. 삭제 정책

게시판에서는 삭제 방식이 중요합니다.

특히 사내 규정이나 공식 공지는 단순 물리 삭제보다 이력 관리가 필요할 수 있습니다.

### 일반 게시글

작성자 또는 관리자

→ 삭제 가능

### 중요 공지 / 규정

관리자만 삭제 가능

또는

→ 삭제 대신 **게시 종료/비공개 처리**

를 권장합니다.

예를 들어 사내 규정의 경우:

```text
취업규칙 v1.0
상태 : 게시 종료

취업규칙 v2.0
상태 : 현재 적용
```

처럼 관리하면 향후 문서관리 기능과도 자연스럽게 연결할 수 있습니다.

# 17. 데이터 구조

현재 사용 중인 Firebase/Firestore 구조를 고려하면 대략 다음 형태가 적절합니다.

```text
boards
 └─ boardId
      ├─ name
      ├─ description
      ├─ type
      ├─ order
      ├─ isActive
      ├─ permissions
      ├─ allowComment
      ├─ createdAt
      └─ updatedAt


boardPosts
 └─ postId
      ├─ boardId
      ├─ title
      ├─ content
      ├─ authorId
      ├─ authorName
      ├─ isPinned
      ├─ viewCount
      ├─ status
      ├─ createdAt
      ├─ updatedAt
      └─ attachments[]


boardComments
 └─ commentId
      ├─ postId
      ├─ authorId
      ├─ authorName
      ├─ content
      ├─ createdAt
      └─ updatedAt
```

읽음 확인을 지원한다면 별도로:

```text
boardPostReads
 └─ readId
      ├─ postId
      ├─ userId
      └─ readAt
```

정도로 분리할 수 있습니다.

# 18. MVP 기능 범위

지금 진행하고 있는 **그룹웨어 초기 모델**이라는 점을 고려하면 게시판 기능을 처음부터 너무 크게 만들 필요는 없습니다.

### 반드시 필요한 기능

* 게시판 목록
* 게시글 목록
* 게시글 상세
* 게시글 작성
* 게시글 수정/삭제
* 첨부파일
* 중요 공지 고정
* 검색
* 기본 권한 관리

### 있으면 좋은 기능

* 댓글
* 조회수
* 게시글 읽음 여부
* 내부 알림

### 후순위 기능

* 대댓글
* 게시 예약
* 게시기간
* 이메일 알림
* 모바일 Push
* 게시글 템플릿
* 게시글 버전 관리
* 통계/분석
* 개인별 미확인 공지 대시보드

| 작성 권한  | 제한적        | 구성원 중심     |
| 콘텐츠    | 공지, 규정, 안내 | 자유로운 글     |
| 중요 공지  | ○          | △          |
| 읽음 확인  | ○          | X          |
| 댓글     | △          | ○          |
| 추천/좋아요 | X          | ○          |
| 대댓글    | X          | ○          |
| 파일 첨부  | ○          | ○          |
| 권한 관리  | 중요         | 상대적으로 낮음   |
| 관리자 관리 | 강함         | 기본 관리      |
| 대표 사례  | 사내 공지      | 동호회, 자유게시판 |

즉,

> **게시판은 “회사에서 직원에게 전달하는 공간”**
> **커뮤니티는 “직원들이 서로 소통하는 공간”**

으로 정의하면 이후 기능을 확장할 때 상당히 깔끔해집니다.

## 20. 최종 MVP 화면 구조

전체 그룹웨어 메뉴에서 보면 다음 정도로 시작하는 것이 가장 적절해 보입니다.

```text
게시판
│
├─ 공지사항
│   ├─ 게시글 목록
│   ├─ 게시글 상세
│   └─ 게시글 작성
│
├─ 경조사
│   ├─ 게시글 목록
│   └─ 게시글 상세
│
├─ 사내규정
│   ├─ 게시글 목록
│   └─ 게시글 상세
│
└─ 자료실
    ├─ 게시글 목록
    └─ 게시글 상세
```

그리고 관리자 영역에서는:

```text
게시판 관리
│
├─ 게시판 관리
│   ├─ 게시판 생성
│   ├─ 게시판 수정
│   ├─ 게시판 순서
│   └─ 권한 관리
│
└─ 게시글 관리
    ├─ 전체 게시글
    ├─ 공지 관리
    └─ 삭제/비공개 관리
```

### 핵심적으로는

**게시판 자체를 관리하는 `boards`와 게시글을 관리하는 `boardPosts`를 분리**하고, 게시판별 **조회/작성 권한**을 갖게 하는 구조가 좋습니다.

그리고 현재 단계에서는 **읽음 확인·알림·대댓글·예약게시·버전관리까지 한꺼번에 넣기보다는**, `게시판 → 게시글 → 첨부파일 → 권한`이라는 핵심 흐름을 먼저 완성하는 것을 추천합니다. 특히 `사내규정`은 이후 만들 예정인 **문서관리(document)** 와 역할이 겹칠 수 있으므로, 초기에는 “공지성 규정 안내”만 게시판에 두고 실제 최신 규정 파일/버전 관리는 문서관리로 넘기는 구조가 깔끔합니다.
