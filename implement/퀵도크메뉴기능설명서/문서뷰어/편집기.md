좋아요. 지금까지 이야기한 **Excel / Word / PowerPoint / HWPX**를 하나의 기준으로 묶어서 정리하면, WorkFit의 **“무료 개발 + 상용화 가능 + 그룹웨어 내 문서 편집”**이라는 목표에 맞는 방향이 꽤 명확해집니다.

# 1. 전체 결론부터

현재 WorkFit의 조건을 기준으로 가장 현실적인 방향은 다음입니다.

| 문서             | 웹 편집기               | 파일 처리                | MVP 추천       |
| -------------- | ------------------- | -------------------- | ------------ |
| **Excel**      | FortuneSheet        | Python `openpyxl`    | 🟢 적극 추천     |
| **Word**       | Tiptap              | Python `python-docx` | 🟢 적극 추천     |
| **PowerPoint** | 자체 Slide Editor     | PptxGenJS            | 🟡 2차 추천     |
| **HWPX**       | 자체 Editor / RHWP 검토 | Python `python-hwpx` | 🟢 Export 우선 |

핵심 원칙은 하나입니다.

> **웹 편집기와 Office 파일 처리 엔진을 분리한다.**

즉,

```text
브라우저
   │
   ├── Excel → FortuneSheet
   ├── Word  → Tiptap
   ├── PPT   → 자체 Slide Editor
   └── HWPX  → 자체 Editor / RHWP 검토
                 │
                 ↓
          WorkFit 내부 데이터
                 │
                 ↓
        Office 파일 변환 계층
                 │
       ┌─────────┼─────────┐
       ↓         ↓         ↓
     XLSX       DOCX      PPTX/HWPX
```

이 구조가 가장 중요합니다.

---

# 2. 왜 "Office를 그대로 복제"하면 안 되는가?

네 가지 모두 공통적으로 문제가 있습니다.

사용자가 원하는 것은 단순히 파일을 생성하는 것이 아니라:

> **웹에서 Office처럼 편집하고 → 저장하고 → 다시 Office 파일로 Export**

하는 것이기 때문입니다.

그런데:
* `openpyxl`
* `python-docx`
* `python-pptx`
* `python-hwpx`

같은 라이브러리는 **편집 UI가 아닙니다.**

반대로:
* FortuneSheet
* Tiptap
* 자체 Slide Editor

등은 **파일 포맷 자체를 완벽하게 처리하는 엔진이 아닙니다.**

따라서 역할을 나눠야 합니다.

예를 들어:

```text
전자결재

 ↓

 ↓

```

또는:

```text

 ↓
```

이런 기능은 일반 PowerPoint 편집기를 만드는 것보다 **그룹웨어에서는 훨씬 가치가 높습니다.**

# 9. HWPX

HWPX는 네 가지 중에서 **한국형 그룹웨어에서는 중요도가 상당히 높습니다.**

먼저:

```text
.hwp
```

와

```text
.hwpx
```

를 구분해야 합니다.

### HWP

기존 한글의 바이너리 형식.

### HWPX

XML 기반 개방형 문서 형식이며 OWPML/KS X 6101 기반입니다.

따라서 무료 오픈소스를 이용해 접근하려면:

> **HWP보다 HWPX를 먼저 지원**

하는 것이 훨씬 현실적입니다.

---

# 10. HWPX의 구조

개념적으로:

```text
HWPX
 │
 └── ZIP 컨테이너
       ├── XML
       ├── XML
       ├── 스타일
       ├── 이미지
       └── 기타 리소스
```

형태입니다.

그래서 DOCX/XLSX/PPTX와 마찬가지로 프로그램에서 구조적으로 접근할 수 있습니다.

---

목표는:

* HWPX 읽기
* HWPX 생성

* 원본 데이터 보존

등입니다.

따라서:

```text
Python API

   ├── openpyxl

```

처럼 통합할 수 있습니다.

# 18. 그런데 Python을 어디까지 사용할 것인가?

여기서 중요한 선택지가 하나 있습니다.

### 방법 A — Python을 Office 파일 처리 서버로 통합

```text
React
  ↓
Python API
  ├── openpyxl
  ├── python-docx
  ├── python-pptx
  └── python-hwpx
```

장점:

* Office 처리 로직 통일
* 서버에서 파일 변환
* 향후 PDF 변환 등 확장 가능
* Python 생태계 활용

단점:

* Python 서버 추가
* 운영 복잡성 증가
* Vercel과 별도 서버가 필요할 수 있음

---

### 방법 B — 가능한 것은 프론트에서 처리

```text
React
 ├── FortuneSheet
 ├── Tiptap
 ├── PptxGenJS
 └── HWPX 처리
```

장점:

* 아키텍처 단순
* 서버 비용 절감
* Firebase/Vercel 구조 유지

단점:

* 브라우저에서 처리하기 어려운 파일 작업 존재
* 대용량 문서 처리 어려움
* HWPX/복잡한 Office 파일 처리 한계

---

# 24. 가장 중요한 개발 원칙 5개

### ① Office를 100% 복제하지 않는다

**호환 가능한 업무문서 편집기**를 만든다.

### ② 웹 편집기와 파일 변환기를 분리한다

```text
Editor ≠ File Engine
```

### ③ Export를 Import보다 먼저 완성한다

특히:

```text
WorkFit → XLSX
WorkFit → DOCX
WorkFit → PPTX
WorkFit → HWPX
```

를 먼저 안정화합니다.

### ④ 기존 복잡한 Office 파일의 완벽한 왕복 보존은 MVP에서 포기한다

```text
Import → Edit → Export
```

의 100% 원본 보존을 처음부터 목표로 하면 개발 규모가 급격히 커집니다.

### ⑤ WorkFit 전용 기능을 Office보다 우선한다

예를 들어:

```text
{{기안자}}
{{부서명}}
{{문서번호}}
{{결재금액}}
{{작성일}}
```

같은 **그룹웨어 데이터 연동 기능**이 단순한 Office 호환성보다 WorkFit에 더 큰 가치가 있습니다.

### 한마디로 정리하면

**WorkFit의 무료 Office 전략은 `Office 복제`가 아니라 `Office 호환 업무문서 플랫폼`으로 가는 것이 가장 현실적입니다.**

특히 MVP에서는 **Word + Excel을 먼저 안정화하고, HWPX는 Export를 지원하며, PowerPoint는 템플릿 기반 생성/Export부터 시작**하는 것이 개발 규모와 실제 그룹웨어 활용성을 모두 고려했을 때 가장 합리적입니다.
