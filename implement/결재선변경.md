## 1. WorkFit 전자결재 기능 아키텍처 분류

WorkFit 전자결재 시스템은 핵심 결재 무결성을 보장하는 **기본 기능(Core)**과 조직 정책에 따라 관리자가 자유롭게 선택할 수 있는 **커스텀 설정 기능(Custom Options)**으로 분리하여 관리합니다.

```
                                  WorkFit 전자결재 아키텍처
                                              │
                    ┌─────────────────────────┴─────────────────────────┐
                    │                                                   │
        [기본 전자결재 기능 (Core)]                        [커스텀 설정 가능 기능 (Custom)]
          • 설정에서 ON/OFF 불가 (항상 가동)                  • `/base/approval-process`에서 ON/OFF 토글
          • 전결, 결재, 참고(참조), 수신, 시행                 • 대결, 후결(사후승인), 선결(선승인), 합의
                                                                         │
                                                             ┌───────────┴───────────┐
                                                             │                       │
                                                      [결재 순차/병렬]        [합의 순차/병렬]
                                                      (기본 프로세스 제어)      (합의 ON 시 서브 옵션)
```

### 1.1 기본 결재 기능 (Fixed Core Features - ON/OFF 불가)
시스템의 기본 뼈대가 되는 기능으로 관리자 옵션에서 끄거나 켤 수 없이 상시 제공됩니다.
1. **전결 (Arbitrary Decision)**: 규정 금액/조건 충족 시 전결권자 승인으로 최종 승인 또는 차상급 자동 전결.
2. **결재 (Approval)**: 순차 또는 병렬로 상급자가 문서를 검토 및 승인/반려하는 기본 행위.
3. **참고 / 참조 (Reference)**: 문서 진행 상황 및 최종 결과를 공유받아 열람하는 비동기 권한자.
4. **수신 (Recipient)**: 최종 승인 완료 문서를 전달받아 처리하는 부서/담당자 수신함 배부.
5. **시행 (Enforcement)**: 대외/사내 공문 발송 및 시행문 변환, 시행함 관리 기능.

### 1.2 커스텀 설정 가능 기능 (Configurable Options - ON/OFF 토글)
`/base/approval-process` (결재 프로세스 설정) 메뉴에서 관리자가 켜고 끌 수 있는 부가 기능입니다.
1. **대결 (Proxy Approval)**: 결재자 부재(출장/휴가) 시 대리 결재자를 지정하여 결재 처리 (`proxy_approval`).
2. **후결 / 사후 승인 (Post Approval)**: 긴급 선조치 후 사후 승인을 받는 역방향 승인 (`post_approval`).
3. **선결 / 선승인 (Pre Approval)**: 하위 승인 대기와 상관없이 상급자가 미리 승인 처리 (`pre_approval`).
4. **합의 (Agreement)**: 타 부서 또는 관련 담당자의 동의/합의를 구하는 프로세스 (`dept_agreement`).

## 2. `/base/approval-process` 내 순차·병렬 제어 설정 사양

결재 및 합의 진행 시 여러 명의 승인자/합의자가 존재하는 경우, 이들의 승인 방식을 **순차(Sequential)** 또는 **병렬(Parallel)**로 처리하도록 제어하는 옵션을 설정 화면에 추가합니다.

### 2.1 카테고리별 순차·병렬 설정 구성

```
[1. 결재 프로세스 카테고리]
  ├─ ⚖️ 기본 결재 승인 방식 선택: [🔵 순차 결재 (기본)] / [⚪ 병렬 결재 (동시 진행)]
  ├─ 🛡️ 대결자 지정 (ON/OFF)
  ├─ ⚖️ 전결 승인 (ON/OFF)
  ├─ 🚨 사후 결재 / 후결 (ON/OFF)
  └─ ⚡ 선결 / 선승인 (ON/OFF)

[2. 합의 프로세스 카테고리]
  └─ 🤝 부서 간 합의 (ON/OFF 토글)
        └─ (합의 ON 시 서브 설정 노출)
              └─ 🤝 합의 승인 방식 선택: [🔵 순차 합의] / [⚪ 병렬 합의 (기본)]
```

### 2.2 설정 제어 데이터 구조 사양

```typescript
// src/data/approvalProcess/approvalProcess.repo.ts (확장 안)

export interface ApprovalProcessConfig {
  // 결재 순차/병렬 설정 ('sequential' | 'parallel')
  approvalExecutionType: 'sequential' | 'parallel';
  
  // 합의 기능 ON/OFF 및 순차/병렬 설정
  agreementEnabled: boolean;
  agreementExecutionType: 'sequential' | 'parallel';
  
  // 기타 커스텀 옵션 토글
  proxyApprovalEnabled: boolean;  // 대결
  postApprovalEnabled: boolean;   // 후결
  preApprovalEnabled: boolean;    // 선결
  midRouteEditEnabled: boolean;   // 진행 중 결재선 변경
}
```

- **순차 결재 (Sequential Approval)**: 1차 결재자 승인 완료 후 2차 결재자에게 문서 알림 및 결재 권한 부여.
- **병렬 결재 (Parallel Approval)**: 동일 결재 스테이지 내 모든 결재자에게 동시 결재 권한 부여 (전원 승인 시 다음 스테이지 이동).
- **순차 합의 (Sequential Agreement)**: 지정된 합의 순서대로 순차적 합의 진행.
- **병렬 합의 (Parallel Agreement)**: 합의 대상 부서/담당자 모두에게 동시 합의 요청 (기본값).

## 3. WorkFit 결재선 중간 변경(진행 중 결재선 변경) 통합 사양

### 3.1 상용 그룹웨어 벤치마킹 & WorkFit 3단계 권한 모델

주요 상용 그룹웨어(네이버웍스, 하이웍스 등)의 정책을 분석하여, 서식 정책 기반 통제와 관리자 강제 변경을 분리 결합합니다.

```
                           결재선 변경 요청
                                  │
                 ┌────────────────┴────────────────┐
                 │                                 │
           일반 결재선 변경                   관리자 강제 변경
                 │                                 │
        기안자 / 서식 허용 결재자                시스템/전자결재 관리자
                 │                                 │
       Future Node 범위만 제한                 퇴직·부재·조직개편 예외
                 │                                 │
      서식 정책 & 전결 규정 재검증              강제 결재자 교체
                 │                                 │
                 └────────────────┬────────────────┘
                                  │
                    Transaction & Audit Log (Subcollection)
```

1. **기안자 (Drafter)**: 본인 문서 진행 중, 정책상 허용 시 미승인 Future 노드 변경.
2. **서식 허용 결재자**: 서식 마스터(`approvalForms`)에서 "결재선 변경 허용" 옵션이 ON일 때만 진행 중 결재자의 미래 결재선 조율 허용.
3. **결재 관리자 (Admin)**: 퇴직, 부재, 부서 폐지 등 예외 시 **[관리자 전용 진행문서 결재자 변경]** 메뉴를 통한 강제 교체.

---

### 3.2 변경 작업별 허용 및 제한 규칙 (Matrix)

| 변경 유형 | 일반 사용자 (기안자/결재자) | 관리자 (Admin) | 비고 및 통제 룰 |
| :--- | :---: | :---: | :--- |
| **결재자 교체 (Replace)** | ✅ (Future 노드만) | ✅ (Past 제외 전 영역) | 동일 직급/직책 권한 유효성 재검증 |
| **결재자 추가 (Insert)** | ✅ (Future 노드만) | ✅ | 전결 규정 최고 권한자 라인 유지 |
| **결재자 삭제 (Delete)** | ⚠️ (제한적 허용) | ✅ | **전결 필수 결재자 및 최종 결재자 삭제 원천 금지** |
| **순서 변경 (Reorder)** | ⚠️ (Future 노드 내) | ✅ | 병렬/순차 구조 범위 내에서만 허용 |
| **결재 $\leftrightarrow$ 합의 변경** | ❌ (기본 차단) | ⚠️ (정책 승인 시) | 커스텀 옵션(합의 ON/OFF) 상태 및 Workflow 변질 방지 |
| **결재 $\rightarrow$ 참조 변경** | ❌ (원천 금지) | ❌ (원천 금지) | 결재 승인 권한 무단 박탈 방지 |
| **기승인 노드 수정** | ❌ (원천 금지) | ❌ (원천 금지) | 과거 승인 이력 불변성(Immutable) 보장 |

## 4. 데이터 모델 및 이력 구조 설계 (`ApprovalDoc`)

### 4.1 노드 상태, 스테이지, 동시성 제어 구조

```typescript
// src/domain/approvalDoc/schema.ts (개선 확장안)

/** 결재 노드 상태 */
export type ApprovalNodeStatus =
  | 'waiting'       // 아직 차례가 오지 않음 (Future Node)
  | 'processing'    // 현재 결재 진행 중
  | 'approved'      // 승인 완료
  | 'rejected'      // 반려 완료
  | 'delegated'     // 대결/위임 처리 (커스텀 대결 ON 시)
  | 'post_approved' // 긴급 선조치 사후 승인 (커스텀 후결 ON 시)
  | 'skipped'       // 전결 등으로 자동 건너뜀 (기본 전결)
  | 'cancelled'     // 결재선 변경으로 인해 취소/제외됨
  | 'replaced';     // 타 인원으로 교체됨

/** 변경 동작 세부 유형 */
export type ApprovalChangeType = 'added' | 'removed' | 'replaced' | 'reordered' | 'type_changed';

/** 결재선 구성원 노드 */
export interface ApprovalLineMember {
  nodeId: string;           // 노드 고유 ID (예: 'node-1', 'node-2')
  stageId: string;          // 결재 단계 ID (병렬/순차 스테이지 구별용)
  userId: string;
  userName: string;
  userPosition: string;
  deptId: string;
  deptName: string;
  type: 'draft' | 'approve' | 'agree' | 'refer'; // 기안 | 결재 | 합의 | 참조
  executionType?: 'sequential' | 'parallel';     // 해당 단계 승인 방식
  status: ApprovalNodeStatus;
  actedAt?: string;         // 실제 처리 일시
  comment?: string;          // 결재 의견
  changeType?: ApprovalChangeType; // 변경 이력 구분 플래그
}

/** 결재 문서 메인 스키마 (Mutable Current State + Versioning) */
export interface ApprovalDoc {
  id: string;
  docNo: string;
  title: string;
  status: 'draft' | 'processing' | 'approved' | 'rejected';
  currentStageId: string;      // 현재 진행 중인 스테이지 ID
  currentStageIndex: number;   // 현재 진행 중인 스테이지 순번
  approvalLineVersion: number; // 동시성 제어용 버전 번호 (Optimistic Lock)
  approvalLine: ApprovalLineMember[]; // 현재 최신 결재선
}
```

### 4.2 이력 추적성(Audit Trail) 보존을 위한 Subcollection 구조

Firestore 단일 문서 용량 초과 방지 및 감사 로그 강화를 위해 변경 이력은 독립 Subcollection으로 관리합니다.

`approvalDocs/{docId}/approvalLineHistories/{historyId}`

```typescript
/** 세부 변경 내역 (Diff Record) */
export interface ApprovalLineDiff {
  operation: ApprovalChangeType;
  nodeId?: string;
  previousNode?: Partial<ApprovalLineMember>;
  newNode?: Partial<ApprovalLineMember>;
}

/** 결재선 변경 이력 레코드 (Audit Log Document) */
export interface ApprovalLineChangeHistory {
  id: string;
  docId: string;
  version: number;             // 변경 후 결재선 버전
  changedAt: string;           // 변경 일시 (ISO String)
  changedByUserId: string;     // 변경 작업자 ID
  changedByUserName: string;   // 변경 작업자 이름
  isAdminChange: boolean;      // 관리자 강제 변경 여부
  category: 'absence' | 'reorg' | 'work_change' | 'other'; // 사유 카테고리
  reason: string;              // 상세 사유 (공백 제외 2자 이상 필수)
  diffs: ApprovalLineDiff[];   // 세부 변경 Diff 항목
  previousLineSnapshot: ApprovalLineMember[]; // 변경 전 전체 스냅샷
  newLineSnapshot: ApprovalLineMember[];      // 변경 후 전체 스냅샷
}
```

## 5. Past / Future Scope Lock & Firestore Transaction 동시성 제어

### 5.1 불변성(Immutable) vs 가변성(Mutable) 영역 구분

- **[불변 영역 (Immutable Archive)]**: 기승인 노드 행위 이력, 승인/반려 시각 및 의견, `approvalLineHistories` Subcollection 스냅샷.
- **[가변 영역 (Mutable State)]**: 현재 최신 결재선 배열(`approvalLine`), 현재 진행 스테이지(`currentStageId`), 동시성 버전(`approvalLineVersion`).

### 5.2 Firestore Transaction 기반 동시 변경 충돌 방지

```typescript
await runTransaction(db, async (transaction) => {
  const docRef = doc(db, 'approvalDocs', docId);
  const docSnap = await transaction.get(docRef);
  
  if (!docSnap.exists()) throw new Error('문서를 찾을 수 없습니다.');
  const currentData = docSnap.data() as ApprovalDoc;

  // 동시성 버전 충돌 검증 (Optimistic Lock)
  if (currentData.approvalLineVersion !== clientPayload.expectedVersion) {
    throw new Error('다른 사용자에 의해 결재선이 변경되었습니다. 최신 결재선을 확인해주세요.');
  }

  const newVersion = currentData.approvalLineVersion + 1;
  transaction.update(docRef, {
    approvalLine: clientPayload.newLine,
    approvalLineVersion: newVersion,
    currentStageId: clientPayload.newCurrentStageId,
  });

  const historyRef = doc(collection(db, `approvalDocs/${docId}/approvalLineHistories`));
  transaction.set(historyRef, {
    ...clientPayload.historyRecord,
    version: newVersion,
  });
});
```
