# 대결(代決) 및 후열(後閱) 프로세스 정립 및 구현 계획서

본 문서에서는 전자결재 시스템의 **대결(代決)** 및 **후열(後閱)** 프로세스의 개념을 정의하고, **양방향 동시 대기 방식(Dual-Routing)**을 포함한 전체 워크플로 및 현재 코드베이스(`workfit-office`)에 적용하기 위한 구체적인 구현 계획을 정리합니다.

---

## 1. 개요 및 핵심 개념 정의

### 1.1 대결 (代決, Proxy Approval)
- **정의**: 결재권자(부서장, 임원 등)가 휴가, 출장, 병가 등으로 부재중일 때, 사전에 지정된 대리자(대결자)가 권한을 위임받아 문서를 대리 승인하는 행위입니다.
- **표기 제약**: 대결자가 승인하더라도 서명/인장란 및 결재선 이력에 원결재자의 이름과 함께 **'대(代)'** 자 및 실제 대결자 정보가 투명하게 표기됩니다 (`delegatedFromId`).

### 1.2 후열 (後閱, Post-Read Verification)
- **정의**: 부재 기간 동안 대결자가 원결재자를 대신하여 처리(승인)한 문서들을, 원결재자가 업무에 복귀한 후 사후에 조회/확인하는 **단순 조회 전용(Read-Only)** 프로세스입니다.
- **특징**: 문서 승인 흐름이나 결재 완료 상태에 영향을 주지 않으며, 원결재자의 '후열 확인' 시각 및 이력만 남습니다.

---

## 2. 대결 프로세스 문서 이동 경로 & 전체 워크플로

### 2.1 문서 이동 경로 (Workflow Path)

```
[기안자 상신]
      │
      ▼
[양방향 동시 대기함] ─── (원결재자 대기함 & 대결자 대기함 동시 꽂힘: Dual-Routing)
      │
      ├───────────────────────────────┐
      │ (원결재자 직접 승인 시)           │ (대결자 먼저 승인 시)
      ▼                               ▼
[일반 결재 승인 완결]            [대결 승인 완결 ('대' 표기)]
                                      │
                                      ▼
                             [원결재자 후열함 입고]
                                      │ (복귀 후 사후 확인)
                                      ▼
                             [후열 확인 완료 (Read-Only)]
```

### 2.2 단계별 상세 처리 흐름

1. **1단계 (지정 및 활성화)**
   - 결재권자가 사전에 사용자 프로필/설정 화면에서 대결자(`delegateUserId`)와 부재 기간(시작일시 ~ 종료일시), 사유를 등록합니다.
   - 설정된 기간이 되면 시스템이 자동으로 부재 상태를 인식합니다.

2. **2단계 (상신 및 Dual-Routing 양방향 동시 대기)**
   - 기안자가 문서를 상신하면, 결재선에 있는 원결재자의 대기함과 사전 지정된 대결자의 결재대기함에 **동시에 문서가 전달(Dual-Routing)**됩니다.

3. **3단계 (대리 승인 및 동시성 제어 / Concurrency Lock)**
   - 원결재자 또는 대결자 중 한 명이 먼저 승인 버튼을 클릭하는 순간, 백엔드에서 원자적 락(Atomic Lock)을 획득하여 선점 승인을 처리합니다.
   - **대결자가 먼저 승인할 경우**: `approverId = 대결자`, `delegatedFromId = 원결재자`, '대' 자 뱃지 및 대결자 결재 정보 기록 ➔ 원결재자 대기함에서 즉시 제거 ➔ 결재 완결 또는 차순위 진행.
   - **원결재자가 직접 승인할 경우**: 일반 승인 처리 ➔ 대결자 대기함에서 즉시 제거.

4. **4단계 (사후 보고 및 후열 확인)**
   - 대결자에 의해 대결 승인된 문서는 최종 업무 종결 시 원결재자의 **'후열함'**에 자동 입고됩니다.
   - 복귀한 원결재자는 후열함에서 대결 처리 내역을 조회하고 '후열 확인'을 수행합니다 (Read-Only).

## 4. 구체적인 단계별 구현 계획 (Implementation Plan)

### Step 1: 데이터 스키마 및 타잎 확장 (`schema.ts`)
1. **User / Absence 스키마**:
   ```ts
   export interface UserAbsenceConfig {
     userId: string;
     isAbsent: boolean;
     startDate: string; // ISO
     endDate: string;   // ISO
     delegateUserId: string; // 대결자 ID
     reason?: string;
   }
   ```
2. **ApprovalBox 타잎 확장**:
   - `export const APPROVAL_BOXES = ['대기', '상신', '완료', '참조', '임시', '수신', '시행', '후열'] as const;`
3. **ApprovalStep 스키마 확장**:
   ```ts
   /** 후열 확인 시각(ISO) — 대결 승인건에 대해 원결재자가 사후 확인한 시각. */
   postReadAt: z.string().nullable().default(null),
   ```

### Step 2: 대결자 지정 마스터 UI 및 저장소 구축
1. **프로필 / 환경설정 (`ProfileScreen.tsx` 또는 `SettingsScreen.tsx`)**:
   - 부재 기간 설정 (시작일시 ~ 종료일시, 사유 입력)
   - 대결자 검색 및 지정 선택창 구축
2. **부재 정보 Repository (`absence.repo.ts`)**:
   - 사용자별 부재 설정 저장 및 현재 시점 기준 부재 여부 판별 함수 `getActiveAbsence(userId)` 구현

### Step 3: Dual-Routing (양방향 동시 대기함 꽂힘) 구현
1. **`approvalDoc.repo.ts` 의 `matchesBox` 수정**:
   - `box === '대기'` 조건 검사 시:
     - (1) 본인이 직접 결재선 노드의 `approverId`인 경우
     - (2) 본인이 현재 부재 중인 결재자(`approverId`)의 active 대결자로 지정되어 있는 경우
     - 위 2가지 경우 모두 '대기함' 목록에 동시 노출되도록 필터링 확장

### Step 4: 승인 처리 & 백엔드 동시성 락 (Concurrency Lock)
1. **승인 로직 분기 (`approveStep` / `delegateStep`)**:
   - 대결자가 먼저 승인 시: `approverId = 대결자`, `delegatedFromId = 원결재자`, '대' 자 뱃지 표기 ➔ 원결재자 대기함 자동 제거 및 후열 대상 등록
   - 원결재자가 먼저 승인 시: 일반 승인 처리 ➔ 대결자 대기함 자동 제거
2. **동시성 락 (Atomic Lock)**:
   - Firestore 트랜잭션 또는 메모리 락을 통해 동일 step에 대해 두 승인 요청이 동시 진입하더라도 먼저 들어온 1건만 정상 승인 처리

### Step 5: 원결재자 후열함 (`후열`) 및 사후 확인 기능 구축
1. **`ApprovalScreen.tsx` 내 '후열함' 탭 추가**:
   - `boxes: ['대기', '상신', '완료', '참조', '임시', '수신', '시행', '후열']`
   - 후열함 대상 문서: 본인이 `delegatedFromId`로 기록된 대결 완결 문서 중 `postReadAt === null` 또는 확인 완료건
2. **후열 확인 처리**:
   - 원결재자가 후열함에서 문서 조회 ➔ [후열 확인] 버튼 클릭 ➔ `postReadAt = now()` 기록 후 확인 완료 상태로 전환 (Read-Only)

## 5. 검증 계획 (Verification Plan)

### 5.1 시나리오 테스트
1. **부재 설정 & Dual-Routing 검증**: A(원결재자)가 B(대결자)를 지정 후 기안 상신 시, A와 B 모두의 대기함에 문서 노출 확인.
2. **대결자 선승인 검증**: B가 대결 승인 시 문서에 '대' 뱃지 표시, A의 대기함에서 삭제, A의 후열함으로 입고 확인.
3. **원결재자 선승인 검증**: A가 먼저 승인 시 일반 승인 완료, B의 대기함에서 삭제 확인.
4. **후열 확인 검증**: A가 복귀 후 후열함에서 문서 조회 및 [후열 확인] 클릭 시 `postReadAt` 기록 확인.

### 5.2 UI 검증
- 결재선 뷰어(`ApprovalDocumentView.tsx`)에서 대결 서명/인장 및 '대(代)' 뱃지 정상 표출 확인.
- 후열함(`ApprovalScreen.tsx`)에서 Read-Only 조회 및 후열 확인 버튼 동작 확인.
