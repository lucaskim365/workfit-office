파일 전체를 기준으로 검토했습니다. 결론부터 말하면, **현재 문서는 “기능 아이디어/초기 설계안”으로는 상당히 타당하지만, 상용 전자결재에 실제 적용할 아키텍처 명세로는 아직 부족합니다.**

특히 **“복수 시행부서 + 부서별 담당자 지정 + 병렬 처리”라는 업무 모델 자체는 타당**합니다. 실제 상용 그룹웨어에서도 수신 부서 지정 → 접수 → 담당자 지정 → 처리라는 구조가 사용되고 있습니다. 예를 들어 다우오피스도 수신 부서/사용자를 지정하고, 수신부서에서 접수한 뒤 담당자를 지정하여 업무를 처리하는 흐름을 제공합니다. ([다우오피스][1])

다만 현재 문서의 **Firestore 데이터 모델과 상태/권한 설계는 그대로 구현하면 운영 단계에서 문제가 생길 가능성이 높습니다.**

| 권한 설계                   |     ★★☆☆☆ | 대폭 보완 필요              |

# 2. 가장 먼저 짚어야 할 문제: "시행자"와 "담당자"의 개념

현재 문서에서는

> 복수 시행 부서 지정
> → 부서원이 담당 집행자로 지정
> → 처리 완료

라는 모델을 사용하고 있습니다. 

이 흐름 자체는 좋습니다.

그런데 **용어가 조금 위험합니다.**

현재 스키마:

```text
DocumentExecutor
 ├─ deptId
 ├─ deptName
 ├─ assigneeId
 ├─ assigneeName
 └─ status
```

여기서 실제로 표현하고 있는 것은 사실상

> **시행처/수신부서별 업무 처리 인스턴스**

입니다.

`executor`라는 이름은 영어권 개발자에게는 "실행자/집행자"로 읽힐 가능성이 높고, `assignee`가 실제 담당자입니다.

### 저는 이렇게 구분하는 것을 권장합니다.

```text
ApprovalDocument
 └─ executions[]
      ├─ targetDept       // 시행/수신 부서
      ├─ assignee         // 실제 업무 담당자
      ├─ status           // 처리 상태
      └─ history          // 처리 이력
```

또는 더 명확하게:

```text
DocumentExecution
```

을 사용하는 것이 좋습니다.

즉,

> **시행자 = 사람**

으로 만들지 말고,

> **시행처/수신처 = 부서 또는 사용자**
> **담당자 = 실제 업무를 수행하는 사람**

으로 명확하게 정의하는 것을 추천합니다.

실제 상용 시스템에서도 "수신부서"와 "담당자"를 별개의 개념으로 취급합니다. 다우오피스 역시 수신부서를 지정한 뒤 수신부서 측에서 담당자를 지정할 수 있도록 되어 있습니다. ([다우오피스][1])

# 3. 가장 좋은 부분: 복수 시행을 배열로 모델링한 것

파일의 핵심 구조:

```typescript
executors?: DocumentExecutor[];
```

는 **개념적으로 매우 적절합니다.** 

예를 들어:

```text
문서 A
 ├─ 인사팀 → 김철수 → 완료
 ├─ 총무팀 → 이영희 → 처리중
 └─ 개발팀 → 박민수 → 대기
```

이런 구조를 하나의 문서에서 표현할 수 있습니다.

그리고

> "다른 시행 부서의 집행 진척도에는 영향을 주지 않는다"

라는 설계도 매우 좋습니다. 

이것은 **병렬 시행 업무의 핵심 요구사항**입니다.

---

# 4. 하지만 `executors[]`를 그대로 Firestore의 핵심 조회 구조로 사용하면 문제가 생깁니다

여기가 엔지니어 관점에서 가장 중요한 부분입니다.

파일에서는

> 메인 문서 안에 배열을 넣으면 `updateDoc` 한 번으로 상태 갱신이 가능하다

고 판단하고 있습니다. 

**작은 규모에서는 맞습니다.**

하지만 상용 서비스에서는 이걸 그대로 밀고 가면 문제가 발생합니다.

---

## 문제 ① "내 시행 문서함" 조회가 어려워집니다

예를 들어 직원 김철수가 있습니다.

김철수가 보고 싶은 것은:

> 내가 담당자인 시행 문서

입니다.

데이터가:

```text
ApprovalDoc
  executors:
    [
      {
        deptId: "D01",
        assigneeId: "USER001"
      },
      {
        deptId: "D02",
        assigneeId: "USER002"
      }
    ]
```

처럼 들어있으면,

```text
assigneeId == USER001
```

인 문서를 효율적으로 조회하는 것이 단순하지 않습니다.

특히 Firestore에서 **배열 내부 객체의 특정 필드만을 기준으로 일반적인 관계형 DB처럼 자유롭게 검색하는 모델**은 적합하지 않습니다.

---

## 문제 ② "시행 문서함 배지"도 문제가 됩니다

파일에서는

> 해당 부서 팀원들의 시행 문서함 배지 개수가 리액티브하게 카운트업

된다고 되어 있습니다. 

그런데 실제로는

```text
내가 처리해야 할 문서 수
내가 담당 중인 문서 수
우리 부서 미접수 문서 수
우리 부서 처리중 문서 수
```

를 계속 계산해야 합니다.

문서 수가 100건일 때는 괜찮습니다.

10만 건이 되면 이야기가 달라집니다.

# 5. 그래서 저는 "본문 데이터"와 "조회용 인덱스"를 분리하겠습니다

가장 현실적인 구조는 다음과 같습니다.

```text
ApprovalDoc
│
├─ 기본 결재 정보
│
├─ recipients[]
│
└─ executions[]
       │
       ├─ executionId
       ├─ deptId
       ├─ assigneeId
       ├─ status
       └─ ...
```

그리고 별도로:

```text
DocumentExecution
│
├─ executionId
├─ documentId
├─ deptId
├─ assigneeId
├─ status
├─ receivedAt
├─ assignedAt
├─ completedAt
└─ ...
```

를 둡니다.

Firestore에서는 예를 들어:

```text
approvalDocs/{documentId}

documentExecutions/{executionId}
```

같은 형태입니다.

### 그러면

**원본문서**

```text
approvalDocs
```

→ 문서의 전체적인 상태/내용

**시행 업무**

```text
documentExecutions
```

→ 시행함 / 담당자 / 처리 상태 / 검색

으로 역할이 분리됩니다.

# 6. 그렇다고 `executors[]`를 완전히 없앨 필요는 없습니다

오히려 다음처럼 **둘 다 사용하는 것이 좋습니다.**

```typescript
interface ApprovalDoc {
  id: string;

  // 원본 결재 정보
  title: string;
  status: ApprovalStatus;

  // 당시 지정된 시행처의 Snapshot
  executions: DocumentExecutionSnapshot[];
}
```

그리고 별도의:

```typescript
interface DocumentExecution {
  id: string;
  documentId: string;

  deptId: string;
  assigneeId: string | null;

  status: ExecutionStatus;

  receivedAt: Timestamp;
  assignedAt?: Timestamp;
  completedAt?: Timestamp;

  updatedAt: Timestamp;
}
```

### 왜 이렇게 하느냐?

상용 시스템에서는 **"현재 데이터"와 "문서 당시 기록"을 구분하는 것이 중요**하기 때문입니다.

예를 들어:

2026년 8월

```text
개발팀
담당자 홍길동
```

이었다가

2027년 2월

```text
홍길동 퇴사
개발팀 조직개편
```

이 발생할 수 있습니다.

그렇다고 2026년 문서의 담당자가 사라지면 안 됩니다.

따라서

```text
ID = 불변 식별자
Name = 당시 표시값 Snapshot
```

을 함께 보존하는 것이 좋습니다.

현재 문서가 `deptId/deptName`, `assigneeId/assigneeName`을 함께 저장하고 있는 방향 자체는 이 부분에서는 좋습니다.

# 7. 상태값은 반드시 다시 설계해야 합니다

현재:

```typescript
status:
  '대기중'
  | '처리중'
  | '완료'
  | '반려'
```

입니다. 

상용 전자결재에서는 **이 상태만으로는 부족합니다.**

제가 추천하는 것은:

```typescript
type ExecutionStatus =
  | 'WAITING'       // 원본문서 결재 중 / 아직 시행 전
  | 'RECEIVED'      // 시행처에 도착
  | 'UNASSIGNED'    // 담당자 미지정
  | 'IN_PROGRESS'   // 담당자 지정 및 처리중
  | 'COMPLETED'     // 처리 완료
  | 'RETURNED'      // 시행처에서 반송
  | 'CANCELLED';    // 시행 취소
```

그런데 여기서 더 중요한 게 있습니다.

**"반려"와 "반송"을 구분해야 합니다.**

전자결재의 결재자 반려와 시행부서의 업무 반송은 의미가 다릅니다.

실제로 상용 시스템에서도 수신문서에 대해 **접수/반송**이라는 개념을 사용하고, 수신문서의 반송은 원본 결재문서의 결재완료 상태와 별개로 처리합니다. ([다우오피스][1])

따라서:

```text
결재 반려
≠
수신 반송
≠
시행 처리 완료
```

를 분리하는 게 좋습니다.

---

# 8. "담당자 미지정인데 문서 열람 가능"은 재검토가 필요합니다

현재 문서는:

> 담당자 미지정 상태에서는 시행부서원이 문서를 열람할 수 있다

고 되어 있습니다. 

이건 **일반 업무 문서라면 괜찮지만 상용 전자결재에서는 위험한 정책**입니다.

예를 들어 문서가:

> "임직원 연봉 조정안"

이라면

```text
인사팀 전체
```

가 문서를 볼 수 있어서는 안 될 수도 있습니다.

실제 상용 그룹웨어도 수신부서와 지정 담당자의 열람 권한을 세밀하게 구분합니다. 다우오피스의 경우에도 수신부서 문서에 대한 부서장/부서문서함 담당자와 일반 부서원의 접근 권한이 다르고, 비공개 문서에서는 더욱 제한됩니다. ([다우오피스][2])

따라서 최소한:

```text
문서 열람권한
├─ 수신부서 전체
├─ 수신부서 관리자
├─ 지정 담당자
└─ 지정 사용자
```

정책을 가져야 합니다.

# 9. "부서원 누구나 담당자로 Claim"도 그대로 구현하면 안 됩니다

파일에서는:

> 부서원 중 실무자가 `[담당 집행자로 지정]` 버튼을 클릭하면 현재 로그인 사용자로 업데이트

한다고 되어 있습니다. 

UX 자체는 좋습니다.

하지만 기술적으로는 **동시성 문제가 있습니다.**

예:

```text
김철수 ── 클릭
이영희 ── 클릭
박민수 ── 클릭
```

이 동시에 발생하면?

Firestore에서 단순:

```typescript
updateDoc()
```

하면 마지막 요청자가 담당자가 될 수 있습니다.

이건 상용 시스템에서는 위험합니다.

### 반드시 원자적 Claim이 필요합니다.

개념적으로:

```text
if assigneeId == null
    → 현재 사용자 지정
else
    → 이미 다른 담당자가 지정됨
```

을 **transaction**으로 처리해야 합니다.

즉:

```text
READ
 ↓
assigneeId 확인
 ↓
null인가?
 ↓
YES
 ↓
현재 사용자 지정
 ↓
COMMIT
```

을 원자적으로 처리해야 합니다.

# 10. `processedAt` 하나만으로는 이력이 부족합니다

현재:

```typescript
processedAt?: string;
```

하나가 있습니다. 

하지만 상용 시스템에서는 최소한:

```typescript
receivedAt
assignedAt
completedAt
updatedAt
```

정도는 필요합니다.

그리고 더 중요한 것은 **누가 어떤 행동을 했는지**입니다.

예:

```text
08/07 09:02
최종결재 완료

08/07 09:03
총무팀 시행 도착

08/07 09:17
김철수 담당자 지정

08/07 11:42
김철수 처리 완료

08/07 11:42
처리의견: 자산 지급 완료
```

이런 Timeline이 필요합니다.

실제 상용 전자결재에서도 결재/반송/회수/재기안/발송 등의 전체 이력을 타임라인으로 조회하는 요구가 존재합니다. ([G2B][3])

따라서:

```typescript
executionHistory[]
```

또는 별도의:

```text
documentExecutionEvents
```

구조를 권장합니다.

# 11. 특히 "완료" 상태를 너무 단순하게 보면 안 됩니다

예를 들어:

```text
인사팀 → 완료
총무팀 → 완료
개발팀 → 처리중
```

이면 원본문서 전체 상태는 무엇인가?

이 정의가 문서에 없습니다.

저라면:

```text
시행 전체 상태

WAITING
↓
IN_PROGRESS
↓
PARTIALLY_COMPLETED
↓
COMPLETED
```

를 둡니다.

예:

```text
인사팀   완료       ✓
총무팀   완료       ✓
개발팀   처리중     ...
```

→ 전체 시행 상태:

```text
부분완료
```

모든 부서가 완료되면:

```text
시행완료
```

로 바뀝니다.

그리고 **이 시행완료가 원본문서의 결재완료와 동일한 것은 아닙니다.**

이 둘을 분리해야 합니다.

# 12. 가장 중요한 업무 설계 문제: "최종 결재 완료 = 시행 시작"의 관계

파일에서는:

> 최종 결재 완료 순간 시행부서의 상태를 활성화

하도록 되어 있습니다. 

이것은 기본값으로는 매우 좋습니다.

다만 상용화를 고려하면 다음 옵션이 필요할 수 있습니다.

```text
① 최종 결재 즉시 시행
② 예약 시행
③ 특정 날짜 시행
④ 수동 발송
⑤ 결재 완료 후 발송 전 검토
```

실제 그룹웨어 요구사항에서도 최종 결재 완료 후 수신처로 발송하는 구조와 예약상신/자동발송 등의 기능이 함께 요구되는 사례가 있습니다. ([G2B][3])

따라서 향후 확장성을 생각하면:

```typescript
executionDispatchType:
  | 'AUTO'
  | 'MANUAL'
  | 'SCHEDULED'
```

정도를 고려할 가치가 있습니다.

# 13. "최종 승인 시 executors 상태를 초기화"는 수정해야 합니다

이 부분은 기술적으로 조금 위험합니다.

현재:

> 최종 완료 순간 `executors`의 각 상태를 `'대기중'`으로 초기화

한다고 되어 있습니다. 

그런데 실제로는 **초기화라는 표현보다 상태 전이**가 맞습니다.

예:

```text
작성 중
    ↓
결재 진행
    ↓
최종 승인
    ↓
시행 발송
    ↓
시행 대기
```

그리고 중요한 점:

**최종 결재가 완료되기 전에 `executors`가 수정될 수 있어야 하는가?**

예를 들어:

```text
기안자
 ├─ 인사팀
 ├─ 총무팀
 └─ 개발팀
```

으로 결재를 올렸는데,

결재 중에

```text
총무팀 → 삭제
```

하고 싶다면?

상용 전자결재에서는 이 부분을 명확하게 규정해야 합니다.

저라면:

### 결재 진행 전

```text
시행처 수정 가능
```

### 결재 진행 중

```text
기본적으로 수정 불가
```

### 최종 승인 후

```text
원칙적으로 수정 불가
```

### 단, 관리자/문서관리자가

```text
시행처 변경
담당자 변경
시행 취소
```

를 할 수 있게 합니다.

# 14. "복수 시행"과 "복수 수신"은 구분하는 게 좋습니다

현재 파일은 사실 두 가지 개념이 섞여 있습니다.

### A. 문서를 전달하는 것

```text
수신처
```

### B. 실제 업무를 수행하는 것

```text
시행처 / 집행처
```

예를 들어:

> "출장비 지급 관련 결재"

라고 해봅시다.

```text
수신:
총무팀

업무 담당:
김철수
```

와

```text
수신:
총무팀
인사팀
재무팀
```

은 완전히 다른 의미입니다.

상용 시스템에서는 이 차이가 중요합니다.

다우오피스의 문서수신도 **원본 결재 완료 후 수신부서로 전달하고, 수신부서에서 접수 후 별도의 업무를 진행**하는 모델입니다. ([다우오피스][1])

따라서 WorkFit에서도:

```text
수신처
   ↓
시행 인스턴스 생성
   ↓
담당자 지정
   ↓
업무 처리
```

라는 계층을 명확하게 하는 것을 추천합니다.

# 15. 제가 가장 추천하는 최종 구조

현재 구조를 조금 발전시키면 다음과 같습니다.

```text
ApprovalDocument
│
├─ id
├─ title
├─ approvalStatus
├─ ...
│
└─ executions[]
      │
      ├─ executionId
      ├─ targetType
      ├─ targetDeptId
      ├─ targetDeptNameSnapshot
      │
      ├─ assigneeId
      ├─ assigneeNameSnapshot
      │
      ├─ status
      ├─ receivedAt
      ├─ assignedAt
      ├─ completedAt
      ├─ comment
      └─ ...
```

그리고 Firestore에는:

```text
approvalDocs/{documentId}
```

와 별도로

```text
documentExecutions/{executionId}
```

를 둡니다.

필요하다면:

```text
documentExecutionEvents/{eventId}
```

까지 둡니다.

# 16. 권장 데이터 구조 예시

제가 실제 개발한다면 대략 이렇게 시작하겠습니다.

```typescript
type ExecutionStatus =
  | 'WAITING'
  | 'RECEIVED'
  | 'IN_PROGRESS'
  | 'COMPLETED'
  | 'RETURNED'
  | 'CANCELLED';

interface DocumentExecution {
  executionId: string;
  documentId: string;

  // 시행처
  targetDeptId: string;
  targetDeptName: string;

  // 담당자
  assigneeId: string | null;
  assigneeName: string | null;

  // 상태
  status: ExecutionStatus;

  // 시간
  receivedAt: Timestamp | null;
  assignedAt: Timestamp | null;
  completedAt: Timestamp | null;
  updatedAt: Timestamp;

  // 처리 결과
  comment: string | null;
}
```

그리고 이력:

```typescript
interface ExecutionEvent {
  eventId: string;
  executionId: string;
  documentId: string;

    | 'RECEIVED'
    | 'ASSIGNED'
    | 'REASSIGNED'
    | 'COMPLETED'
    | 'RETURNED'
    | 'CANCELLED';

  actorId: string;
  actorName: string;

  comment?: string;

  createdAt: Timestamp;
}
```

이렇게 하면 나중에

> "이 문서는 누가 언제 담당했고 왜 반송했는가?"

라는 질문에 정확하게 답할 수 있습니다.

# 17. 일반 사용자 관점에서는 현재 UX가 오히려 복잡합니다

현재 문서의 UX는:

> 시행 문서함 → 문서 열람 → 담당 집행자로 지정 → 처리 → 완료

입니다. 

개발자가 보면 명확합니다.

하지만 일반 사용자는 이런 생각을 할 수 있습니다.

> "이 문서를 내가 처리해야 하는 건가?"

> "이미 다른 사람이 처리 중인가?"

> "내가 담당자로 지정하면 다른 사람은 못 하는 건가?"

따라서 목록에서부터 명확하게 보여줘야 합니다.

### 예:

| 문서       | 시행부서 | 담당자 | 상태        |
| -------- | ---- | --- | --------- |
| 자산 지급 요청 | 총무팀  | 김철수 | 🟢 처리중    |
| 계정 생성 요청 | 개발팀  | 미지정 | 🟡 담당자 필요 |
| 인사발령 통보  | 인사팀  | 홍길동 | ✓ 완료      |

그리고 문서 상세에서는:

```text
시행 처리

총무팀
└ 김철수
  처리중

개발팀
└ 담당자 미지정
  [내가 담당하기]

인사팀
└ 홍길동
  완료
```

처럼 보여주는 것이 훨씬 직관적입니다.

# 19. 특히 "반려"는 다시 생각하는 게 좋습니다

현재:

```typescript
'반려'
```

가 들어가 있습니다. 

그런데 시행업무에서는 일반 결재의 "반려"와 다른 의미가 필요합니다.

예를 들어 총무팀이:

> "첨부된 견적서가 없습니다."

라고 돌려보내는 것은 **결재 반려가 아니라 시행문서 반송**에 가깝습니다.

따라서 UI에서도:

```text
[반려]
```

보다는

```text
[반송]
```

을 사용하는 것이 사용자에게 훨씬 명확합니다.

실제 상용 전자결재에서도 수신문서 처리 과정에서 **접수 / 반송**을 별도의 처리로 구분합니다. ([다우오피스][1])

# 21. 제가 실제 WorkFit 개발자라면 이렇게 결정하겠습니다

**현재 문서를 폐기하지 않고, 다음 방향으로 발전시킵니다.**

```text
                  ┌───────────────┐
                  │ ApprovalDoc   │
                  │ 원본문서       │
                  └───────┬───────┘
                          │
                 최종 결재 완료
                          │
            ┌─────────────┼─────────────┐
            ↓             ↓             ↓
        인사팀 시행     총무팀 시행     개발팀 시행
            │             │             │
        담당자 지정     담당자 지정     담당자 지정
            │             │             │
          처리완료       처리중         대기
            │             │             │
            └─────────────┼─────────────┘
                          ↓
                   전체 시행 완료
```

그리고 데이터는:

```text
ApprovalDoc
     │
     ├── Approval Workflow
     │
     └── Execution Tasks
             │
             ├── 인사팀
             ├── 총무팀
             └── 개발팀
```

으로 **결재 프로세스와 시행 업무 프로세스를 분리**합니다.

이렇게 해야 나중에 WorkFit이 단순한 "전자결재 데모"가 아니라 **실제 회사에서 사용하는 그룹웨어**로 발전했을 때 구조를 갈아엎지 않아도 됩니다.

특히 네이버웍스 같은 상용 제품도 결재 메인에서 대기/예정/처리/완료처럼 사용자가 해야 할 업무 상태를 분리해서 보여주는 방향을 취하고 있습니다. ([웍스모바일 도움말][4])

**한 줄로 정리하면:**

> **이 문서의 업무 개념은 맞습니다. 다만 `ApprovalDoc.executors[]` 하나로 모든 것을 해결하려는 부분은 상용화 전에 반드시 수정해야 합니다. "시행처 → 시행업무 → 담당자 → 처리이력"을 독립적인 업무 객체로 보는 것이 가장 중요한 개선점입니다.**
