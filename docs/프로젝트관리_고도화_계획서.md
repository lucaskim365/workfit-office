# 프로젝트 관리 고도화 계획서

작성 2026-08-28 · 대상 모듈 `업무관리`(`src/modules/gw/task`)

기존 업무관리(프로젝트 CRUD + 라이트 WBS)를 **사업 단위 프로젝트 관리**로 확장한다.
프로젝트를 재원별로 나누고, 프로젝트마다 정의한 트랙을 병렬로 돌리고, 과업을 대→중→소로
쪼개 진행률을 집계하고, 그 결과를 회의·보고용 장표로 뽑는 것까지가 범위다.

---

## 0. 무엇을 만들고 무엇을 안 만드는가

| 만든다 | 안 만든다 |
| --- | --- |
| 프로젝트 유형(수주/자체) + 재원(국책/민간) | 계약·정산 금액 관리(회계 영역) |
| **프로젝트별 자유 정의 트랙**(병렬, 0~N개) | 전사 트랙 단위 집계 |
| 대→중→소 **가변 깊이 과업 트리** | 간트 차트(1차 범위 밖) |
| 진행률 **자동 롤업** | 상위 과업 진행률 수동 입력 |
| **진행 이력** 적재 | 감사 로그·되돌리기 |
| 댓글 · 파일 첨부 | 멘션·알림 연동 |
| 일간/주간/월간/전체 **리포트 + 인쇄** | 정기 자동 생성·메일 발송 |
| 달력에 과업 표시 | 과업↔일정 복사 생성 |

리포트는 **인쇄·다운로드용 회의 자료**다. 서식을 한 번 정해두면 데이터가 그 자리에 채워져
한 장으로 이어진다. 사람이 채우는 칸은 없다.

## 1. 용어와 분류 체계

```
프로젝트
├─ 수주사업        외부 발주처·계약이 있다
│   ├─ 국책        정부지원 R&D 과제
│   └─ 민간        기업 발주
└─ 자체사업        발주처 없이 내부 투자로 만든다
```

**대분류를 `수주사업 / 자체사업`으로 두고 재원(국책·민간)을 그 아래 속성으로 내린 이유**:
실제로 일하는 방식이 갈리는 경계는 "발주처가 있는가"다. 정산·검수·보고 의무, 매출 인식,
산출물 소유권이 전부 여기서 갈린다. 국책이냐 민간이냐는 그 아래에서 보고 주기와 정산
서식만 다르다. 나중에 지자체·출연연 같은 재원이 늘어도 대분류를 건드리지 않는다.

`국책 / 수주 / 자체` 3분류를 한 층에 두는 안은 버렸다 — 민간 수주가 갈 자리가 애매해지고
재원이 늘 때마다 enum 전체가 흔들린다.

> **유형과 트랙은 직교한다.** 자체사업이라고 영업이 없는 게 아니다. 영업팀도 사업관리팀도
> 각자 자체 사업을 할 수 있고, 어느 구분에도 맞지 않는 자체 사업도 있다. 유형이 트랙 구성을
> 제약하지 않는다(§2).

## 2. 트랙 — 프로젝트마다 정의하는 병렬 레인

트랙은 **순차 단계가 아니라 동시에 도는 레인**이다. 사업관리는 개발이 도는 내내 같이 돈다.
그래서 트랙마다 진행률을 따로 낸다 — 개발 80%인데 정산 0%인 상황을 숫자 하나로 뭉개면
리포트가 거짓말을 한다.

**트랙 이름은 프로젝트마다 자유롭게 정한다.** 코드에 박힌 enum이 아니라 데이터다.

```
프로젝트 A (수주·국책)   [영업] [사업관리] [개발]
프로젝트 B (자체)        [영업]                      영업팀 단독 자체 사업
프로젝트 C (자체)        [기획] [디자인] [퍼블]      다른 구분이 맞는 사업
프로젝트 D (자체)        (없음)                      트랙 구분이 안 맞는 사업
```

- 개수는 **0~N개**. 0개면 트랙 레이어 자체가 없고 대과업이 최상위가 된다.
- 프로젝트 생성 시 `영업 / 사업관리 / 개발` 3개를 **템플릿으로 미리 채워준다.** 지우거나
  이름을 바꾸거나 그대로 쓰면 된다. 편의일 뿐 강제가 아니다.
- 유형(수주/자체)이 트랙 구성을 제약하지 않는다.

### 트랙은 프로젝트 안에서만 의미를 갖는다

이름이 자유라서 프로젝트 A의 "개발"과 프로젝트 C의 "퍼블"을 시스템이 같은 것으로 볼 수 없다.
그래서 **"전사 개발 진행률" 같은 트랙 단위 합산은 만들지 않는다.**

이건 손실이 아니다. 전사 리포트는 애초에 프로젝트 리포트를 이어 붙이는 방식이라(§8)
트랙을 가로질러 합산할 일이 없다.

## 3. 과업 트리 — 가변 깊이

```
[트랙]  ← 있을 수도 없을 수도. 트리 바깥의 별도 레이어
 └─ level 1  대과업
    └─ level 2  중과업
       └─ level 3  세부과업
          └─ level 4~5  (필요할 때만)
```

기본은 대·중·소 3단이고 필요하면 5단까지 내려간다. 화면 들여쓰기 가독성 때문에 5단에서 막는다.

**트랙은 트리의 층이 아니라 과업이 매달리는 옆칸이다.** 트랙을 트리의 level 0으로 넣지 않은
이유는 두 가지다 — 트랙은 담당자·기간·진행률을 입력받는 대상이 아니고(이름·순서·색만 가진다),
트랙 유무에 따라 level 번호가 밀리면 "리포트를 몇 단까지 볼지"가 프로젝트마다 다른 뜻이 된다.
트랙이 있든 없든 **level 1은 항상 대과업**이다.

### `path` 를 두는 이유 (필수)

**Appwrite에는 재귀 쿼리도 조인도 없다.** "이 대과업 밑 전부"를 가져오려면 단계마다 쿼리를
날려야 하고 그러면 N+1로 터진다. 그래서 조상 경로를 문자열로 materialize 한다.

```
대과업        path = "0002"
 └ 중과업     path = "0002.0005"
    └ 세부    path = "0002.0005.0001"
```

- 하위 전체 조회 = `trackId` 일치 + `startsWith(path, "0002.")` 한 번
- 트리 정렬 = `path` 오름차순 하나로 끝
- 각 마디는 형제 순번 4자리 제로패딩. 5단이면 24자 → 속성 크기 120이면 충분하다.
- `path`는 **같은 `trackId` 그룹 안에서 유일**하다. 트랙 미사용 프로젝트는 `trackId = null`
  그룹 하나만 존재한다.
- **부모를 옮기면 하위 전체의 `path`를 다시 써야 한다.** 이동은 서브트리 일괄 갱신으로
  구현하고, 갱신 도중 실패하면 `path`가 깨지므로 `parentId`를 진실의 원천으로 두고
  `path`는 파생값으로 다룬다(불일치 시 `parentId`로 재계산).
- 과업을 다른 트랙으로 옮기는 것도 같은 서브트리 갱신이다(`trackId` + `path` 동시 변경).

## 4. 진행률 롤업

```
세부과업(리프)   ← 사람이 입력하는 유일한 지점
중·대·트랙       ← 기간 가중 평균으로 자동 계산
```

```
weight(task) = max(1, dueAt - startAt + 1일)      // 기간 미지정이면 1
progress(부모) = Σ(progress(자식) × weight(자식)) / Σ weight(자식)
```

**기간 가중인 이유**: 단순 평균은 3개월짜리 과업과 하루짜리를 같은 무게로 취급해 숫자를
왜곡한다.

**상위 진행률을 DB에 저장하지 않는다.** 저장하면 리프가 바뀔 때마다 조상 전부를 갱신해야
하고, 그 중 한 번이라도 실패하면 영구히 어긋난다. Appwrite에는 트랜잭션이 없어서 더 그렇다.
트리를 읽은 뒤 순수함수로 계산하면 화면·리포트가 같은 함수를 쓴다.

트랙 진행률도 같은 함수로 낸다 — 트랙에 직속된 대과업들을 자식으로 보면 된다.

```ts
// src/domain/workProject/rollup.ts (신규)
export function rollupProgress(nodes: WorkTask[]): Map<string, number>
```

> **알려진 한계**: 사업관리처럼 하위 작업으로 잘 쪼개지지 않는 일은 자동 집계가 어색할 수
> 있다. 그때 해당 과업만 수동으로 고정하는 옵션을 필드 1개(`progressMode`)로 추가할 수 있게
> 계산 함수를 그 지점에서 분기 가능하게 짜둔다. 지금은 넣지 않는다.

## 5. 진행 이력 — 리포트의 원천

현재 `workTasks`에는 **진행률의 현재값만** 있고 변경 이력이 없다. "이번 주에 뭐가 진행됐나"를
자동으로 뽑으려면 *지금 60%*가 아니라 ***월 40% → 금 60%, 누가, 무슨 근거로***가 남아야 한다.
이력이 없으면 리포트는 현재 상태 스냅샷밖에 못 만들고 그건 장표가 아니라 목록이다.

**`workTaskLogs`가 이 기능 전체의 핵심 테이블이다.** 댓글·파일보다 우선순위가 높다.

기록 시점: 진행률 변경 · 상태 변경 · 생성 · 담당자 변경 · 완료.

## 6. 댓글 · 파일

- 댓글은 과업 단위. 답글은 1단까지(스레드 무한 중첩 안 함).
- 파일은 **기존 저장소 추상화를 그대로 쓴다** — `src/shared/lib/storage.ts`의
  `fileStorage.put()/remove()`. 드라이버(S3/Garage · Firebase · dataURL)는 `VITE_STORAGE_DRIVER`가
  고른다. 새로 만들 것이 없다.
- 파일은 과업에 붙이거나(`taskId`) 프로젝트 직속으로 둔다(`taskId = null`).

## 7. 달력 연동

`calendarEvents`에는 이미 `projectId`와 `PROJECT` 공유 범위가 있다.

과업을 달력 일정으로 **복사 생성하지 않는다.** 복사하면 수정할 때마다 두 곳이 어긋나고
어느 쪽이 진실인지 알 수 없게 된다. 대신 달력 화면이 `workTasks`를 같이 읽어 그리고,
"프로젝트 과업 표시" 토글로 켜고 끈다.

## 8. 리포트

```
입력   기간(일간/주간/월간/전체) × 깊이(1~5단) × 프로젝트(또는 전사)
원천   workTaskLogs(기간 내) + workTasks(현재 트리) + workTracks
출력   화면에서 즉시 조립 → 인쇄 CSS → PDF 저장
```

### 섹션 구성

1. **트랙별 진행률** 기초 → 기말 (증감) — *트랙이 없는 프로젝트는 이 섹션을 건너뛴다*
2. **과업별 변화** — 선택한 깊이까지 펼침
3. **금기간 완료 / 신규 / 지연** — 지연 = `dueAt` 경과 & `progress < 100`
4. **다음 기간 예정** — `startAt`이 다음 기간에 걸치는 과업

### 출력 예 — 트랙이 있는 프로젝트 (주간 · 깊이 2단)

```
[주간] AI물류최적화 (수주사업·국책)   2026-08-24 ~ 08-30

■ 개발                          50% → 62%  (+12)
  ├ 대: 추론엔진 구현            40% → 55%
  └ 대: 데이터 파이프라인        70% → 75%
■ 사업관리                      30% → 30%  (변동없음)
  └ 대: 중간정산                  0% →  0%   ⚠ 마감 D-5
■ 영업                          80% → 100% ✅ 완료

금주 완료 3건 · 지연 1건 · 신규 2건
```

### 출력 예 — 트랙이 없는 프로젝트

```
[주간] 사내 워크플로 개선 (자체사업)   2026-08-24 ~ 08-30

대: 현황 조사                    40% → 60%  (+20)
  중: 인터뷰                     60% → 80%
  중: 자료 취합                  20% → 40%
대: 개선안 설계                   0% → 20%  (+20)

금주 완료 1건 · 지연 0건 · 신규 2건
```

깊이를 1단으로 접으면 대과업 줄만, 3단으로 펴면 세부까지 — **같은 데이터에서 깊이만 바꿔**
뽑는다. 서식은 고정이고 데이터만 갈아 끼운다.

### 전사 리포트 = 프로젝트 리포트를 이어 붙인 것

별도의 집계 화면을 만들지 않는다. 프로젝트를 여러 개 골라 각각의 리포트를 순서대로 이어
붙이면 그게 곧 **전체 프로젝트 대장**이다.

- 프로젝트마다 페이지를 나눈다(`break-before: page`) — 인쇄물에서 프로젝트가 페이지 중간에
  잘리지 않게
- 맨 앞에 목차 한 장 — 프로젝트명 · 유형 · 기간 · 전체 진행률 한 줄씩
- 그 뒤로 위 서식 그대로 프로젝트별 본문

**새로 계산할 것이 없다.** 프로젝트 리포트를 N번 그리고 사이에 페이지 나눔을 넣으면 끝이다.
따로 뽑아 둔 PDF들을 나중에 합쳐도 같은 결과가 나온다.

### PDF

인쇄 CSS(`@media print`) + `window.print()`. 서버 렌더(headless PDF)를 쓰지 않는 이유:
추가 인프라가 0이고, 화면과 PDF가 항상 일치하며, 현재 Appwrite 함수 배포가 간헐적으로
실패하는 상태(nginx 60초 타임아웃·빌드 큐 정체)와 무관하게 동작한다. 정기 자동 생성·메일
발송이 나중에 필요해지면 이 화면이 그대로 토대가 된다.

## 9. 권한

**별도 열람 규칙을 두지 않는다.** 프로젝트 관리 대상(수주사업·자체사업)은 전부 사내 공개이고,
리포트도 전 프로젝트를 대상으로 한다. 어차피 내부에서 공유되는 내용이라 규칙을 만들면
관리 비용만 생긴다.

- 유형이 붙은 프로젝트는 `visibility`를 쓰지 않는다(항상 전사).
- 기존 `PRIVATE / TEAM`은 개인 메모성 프로젝트에만 남긴다. 이들은 리포트 대상에서 제외한다.
- **쓰기 권한은 유지한다** — 과업 수정은 프로젝트 참여자, 삭제는 소유자.

> 전제: 현재 Appwrite 컬렉션 권한이 `Any`(누구나 CRUD)라 이 구분은 화면 수준에서만 성립한다.
> 실제 강제는 Appwrite Auth 도입 이후다(별건).

## 10. Appwrite 스키마 변경 명세

빌더 헬퍼는 `scripts/appwrite-schema.ts` 기준 — `S`(문자열) `SA`(문자열배열) `EN`(enum)
`INT`(정수) `BOOL`(불리언) `IX`(인덱스) `UQ`(유일인덱스).

> ⚠ `INT`는 min/max를 반드시 지정한다. 생략하면 Appwrite 1.9.6 워커가 `processing`에서
> 멈추고 뒤따르는 인덱스 생성까지 막힌다(실측).

### 10.1 `workProjects` — 속성 추가

```ts
EN('projectType', ['CONTRACT', 'INTERNAL']),
EN('fundingType', ['GOVERNMENT', 'PRIVATE']),   // INTERNAL이면 미사용
S('clientName', 100),                            // 발주처
S('contractNo', 60),
S('contractStartAt', 40),
S('contractEndAt', 40),
```

인덱스 추가: `IX('prjType', ['projectType'])`

도메인 규칙(`superRefine`): `projectType === 'INTERNAL'`이면 `fundingType`·`clientName`·
`contractNo`를 비운다. 자체사업인데 발주처가 적힌 데이터가 생기면 리포트가 어긋난다.

트랙 구성은 여기 두지 않는다 — 별도 컬렉션(§10.2)이다.

### 10.2 `workTracks` [신규]

```ts

S('projectId', 64, true),
S('name', 40, true),
INT('sortOrder', false, 0, 0, 9999),
S('color', 16),
S('createdAt', 40, true),
S('updatedAt', 40),
```

인덱스: `IX('trackProject', ['projectId', 'sortOrder'])`, `UQ('trackName', ['projectId', 'name'])`

유일 인덱스를 거는 이유: 한 프로젝트에 같은 이름 트랙이 둘 생기면 리포트에서 어느 쪽인지
구분할 방법이 없다. DB에서 막는다.

프로젝트 생성 시 `영업 / 사업관리 / 개발` 3건을 기본 생성한다(템플릿). 사용자가 지우거나
이름을 바꿀 수 있고, 0건으로 만들어도 된다.

## 12. 구현 순서

| 단계 | 내용 | 단독 출시 |
| --- | --- | --- |
| **1** | 프로젝트 유형 + 트랙 CRUD + 과업 트리(`trackId`/`parentId`/`level`/`path`) + 롤업 | ✅ |
| **2** | 진행 이력 + 리포트 화면 + 인쇄 | ✅ |
| **3** | 댓글 + 파일 | ✅ |
| **4** | 달력 과업 표시 토글 | ✅ |

1단계만 나가도 지금 업무관리보다 낫고, **2단계가 이번 요청의 본체**다.

### 기존 데이터 이관 (1단계 안에서)

현재 구조는 `workPhases`(단계) + `workTasks`(단계 아래 평면)로 2단이다. 이걸 트리로 옮긴다.

1. 각 `workPhase` → `level 1` 과업으로 승격. **트랙은 만들지 않는다**(`trackId = null`) —
   기존 단계가 트랙인지 대과업인지 데이터만 보고는 알 수 없다. 트랙 구성은 사용자가
   프로젝트를 열어 직접 정한다.
2. 그 아래 `workTask` → `level 2`, `parentId`는 승격된 과업
3. 전 과업 `path` 재계산
4. 검증 통과 후 `workPhases` 컬렉션과 `workTasks.phaseId` 제거

**검증 전에 레거시를 지우지 않는다.** 순서를 지키지 않으면 원본이 영구 유실된다.

## 13. 열린 항목

- **전사 트랙 집계** — 만들지 않는다. 전사는 프로젝트를 이어 붙이는 방식이라 필요가 없다(§8).
  훗날 트랙을 가로질러 합산할 일이 생기면 `workTracks`에 표준 분류 매핑 필드(`standardType`)
  하나를 붙이면 되고, 스키마 변경 1개로 끝나므로 미리 만들지 않는다.
- **지연 판정** — `dueAt` 경과 & `progress < 100`으로 시작. 유예일 개념이 필요하면 추가.
- **리포트 서식** — §8 구성으로 1차 구현 후 실제 회의에 써 보고 조정한다.
- **정기 자동 생성·메일 발송** — 1차 범위 밖. 필요해지면 §8 화면을 토대로 Function을 얹는다.
- **컬렉션 권한** — 현재 전 컬렉션 `Any`. Appwrite Auth 도입 시 일괄 정리(별건).
