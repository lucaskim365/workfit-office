# A. 배포로 화면 파일 이름이 바뀜

> 배포하면 화면 파일의 이름이 전부 바뀌는데, 이미 접속해 있던 브라우저는 옛 이름을 계속
> 들고 있다. 그 상태에서 새 화면을 열거나 저장을 누르면 없는 파일을 찾게 되고,
> 앱이 **묻지도 않고 새로고침**해 작성 중이던 내용이 사라졌다.

## A-1. 현상

근무 시간 중 배포가 나간 직후, 전자결재로 계약보고서를 작성하던 중 화면이 새로고침되면서
작성 중이던 내용이 사라졌다.

- 사용자 입장에서는 **아무것도 안 했는데 화면이 혼자 새로고침된 것**처럼 느껴진다.
  실제로는 버튼을 누른 순간 벌어지지만, 클릭과 새로고침이 이어져 보이지 않는다.
- **업무관리만 수정한 배포였는데도 전자결재에서 발생했다.** 배포 산출물은 앱 전체이기 때문이다.

---

## A-2. 원인

네 단계가 순서대로 맞물려 일어난다. 각 단계는 그 자체로는 정상 동작이고,
**마지막 하나만 우리가 정한 것**이다.

### ① 빌드가 파일 이름에 내용 지문을 박는다

화면마다 별도 파일로 쪼개고(청크), 내용을 계산한 해시를 이름에 붙인다.

```
ApprovalScreen-DT0pnIjN.js
                ^^^^^^^^ 내용으로 계산한 지문
```

내용이 한 글자만 바뀌어도 이름이 달라진다. **브라우저 캐시 때문에 반드시 필요한 방식이다** —
이름이 늘 같으면 코드를 고쳐 배포해도 브라우저가 옛 파일을 캐시에서 계속 쓴다.

### ② 배포가 파일 묶음을 통째로 갈아치운다

새 이름의 파일들이 올라가고 옛 이름의 파일은 서버에서 사라진다.
업무관리만 고쳐도 공통 코드가 섞여 있어 **98개 파일 이름이 전부 바뀐다.**

### ③ 이미 열려 있던 브라우저는 옛 이름을 들고 있다

접속할 때 받는 것은 화면 코드가 아니라 **"무슨 파일이 어디 있다"는 주소록**뿐이다.
실제 화면 코드는 그 화면에 들어갈 때 가져온다.

```
$ grep -o "assets/[^\"]*\.js" dist/assets/index-WGuihXe2.js | sort -u | wc -l
98        ← entry 번들 안에 청크 파일명 98개가 문자열로 박혀 있다
```

**주소록은 새로고침 전까지 갱신되지 않는다.** 아침에 접속한 사람은 아침 주소록을 하루 종일 쓴다.

### ④ 없는 파일을 찾고, 앱이 즉시 새로고침한다

여기가 우리가 정한 부분이다. `src/app/App.tsx` 의 lazy 래퍼가 실패 시 곧바로
`window.location.reload()` 를 호출하고 있었다. **저장할 기회가 없다.**

### 실제로 벌어지는 순서

```
아침  접속       주소록 수신 — ApprovalScreen-DT0pnIjN.js
                 (결재선 팝업 파일은 아직 안 받음)

낮    배포       서버 파일이 새 이름으로 교체
                 DT0pnIjN 은 더 이상 존재하지 않음

낮    팝업 클릭  GET /assets/ApprovalScreen-DT0pnIjN.js
                 404 Not Found
                 → 자동 새로고침 → 작성 내용 소실
```

### 함께 확인된 것 — 자동저장 결함

전자결재에는 자동저장이 **이미 있었지만**, 세 가지 결함으로 *저장은 되는데 꺼내지 못하는*
상태였다. `src/modules/gw/approval/ApprovalDraftScreen.tsx` 기준.

| | 결함 | 결과 |
| --- | --- | --- |
| A | 복구 검사가 `if (editDoc) return` 으로 막혀 있었다 | **임시저장 문서를 이어 쓰거나 반려 문서를 고치던 중이면 복구 제안이 아예 안 떴다.** 저장은 계속 하고 있었는데도 |
| B | 복구 플래그를 조건 없이 지웠다 | 화면에 잠깐 들렀다 나가기만 해도 다음 복구 제안이 사라졌다(내용은 남아 있는데도) |
| C | `relatedDocs` 가 보관 목록에서 빠져 있었다 | 이탈 방지 감시에는 들어 있는데 저장을 안 해서, 복구해도 관련문서만 사라졌다 |

> 이번 사례가 정확히 어느 경로였는지는 **당사자 확인 없이 단정할 수 없다.**
> 코드에서 재현·확인 가능한 결함만 정리해 모두 수정했다.

## A-3. 해결

막는 층이 셋이다. 위쪽이 근본이고 아래쪽은 그래도 뚫렸을 때의 안전망이다.
근본은 인프라 결정이 필요해, 아래 두 층을 먼저 채웠다.

### 근본 — 옛 파일을 지우지 않는다 〔검토 필요〕

해시 이름은 내용이 다르면 이름도 다르므로 **겹칠 일이 없다. 그냥 쌓아두면 된다.**
애초에 해시를 붙이는 이유가 이걸 가능하게 하려는 것이다.

**사내 서버(nginx)라면** 배포 스크립트에서 `--delete` 를 빼는 것으로 끝난다.

```bash
# ❌ 이것이 원인
rsync -av --delete dist/ /var/www/workfit/

# ✅ 자산은 추가만, 주소록(index.html)만 교체
rsync -av dist/assets/ /var/www/workfit/assets/
cp dist/index.html /var/www/workfit/index.html

# 오래된 것만 정리 (탭을 90일 켜두는 사람은 없다)
find /var/www/workfit/assets -type f -mtime +90 -delete
```

nginx 설정에서 주의할 점:

```nginx
location /assets/ {
    expires 1y;
    add_header Cache-Control "public, immutable";
    try_files $uri =404;          # ⚠ 반드시 404 로 끝낼 것
}

location = /index.html {
    add_header Cache-Control "no-cache, must-revalidate";
}

location / {
    try_files $uri /index.html;   # SPA 라우팅
}
```

> ⚠ `/assets/` 를 따로 잡지 않으면 없는 JS 를 요청했을 때 404 대신 `index.html`(HTML)이
> 돌아가고, 브라우저가 그것을 JS 로 파싱하다 `Unexpected token '<'` 라는 엉뚱한 오류를 낸다.

**Vercel이라면** Skew Protection 설정이 같은 역할을 한다. 다만 이 기능은 브라우저가
"나는 배포 A 사람"이라는 표식을 보내야 동작하고, **그 표식을 붙이는 주체는 앱 코드**다.
Next.js·SvelteKit은 프레임워크가 자동으로 해주지만 Vite는 자동이 아니다.
대시보드에 토글이 있는지, 켰을 때 실제로 동작하는지 확인이 필요하다.

확인 방법(문서보다 확실하다): 탭 하나를 열어둔 채 배포하고, **그 옛 탭에서 아직 안 열어본
화면으로 이동**해 본다. 정상이면 동작하는 것이다.

### 완충 — 재시도 후, 물어본다 〔완료〕

`src/app/App.tsx`

```
화면 파일 404
  → 0.8초 뒤 한 번 더 시도        ← 전파 지연·일시 오류면 여기서 끝
  → 그래도 실패하면 묻는다
     "새 버전이 배포되어 이 화면을 열 수 없습니다.
      작성 중인 내용이 있다면 먼저 저장해 주세요.
      지금 새로고침하시겠습니까?"   [확인] [취소]
```

취소하면 하던 화면에 그대로 머문다. **저장하고 새로고침할 수 있다.**

### 최후 — 자동저장 결함 3건 수정 〔완료〕

- **A** 보관본에 `docId` 를 남기고, 지금 열고 있는 문서의 것일 때만 복구를 제안한다.
  `editDoc` 을 통째로 막던 것보다 안전하면서 실제로 동작한다
- **B** 복구 제안을 실제로 띄웠을 때만 플래그를 내린다
- **C** `relatedDocs` 를 보관·복구 목록에 추가

공용 자동저장 훅 `src/shared/lib/formDraft.ts` 도 함께 두었다. 다른 긴 폼(자원예약·설문 등)에
같은 보호를 붙일 때 쓴다. `localStorage` 를 쓰는데, **막으려는 사고가 새로고침이라 메모리는
답이 될 수 없고**, 서버에 매번 쓰면 네트워크가 끊겼을 때 쓰던 글을 저장조차 못 하게 된다.

## A-4. 배포 한 번만 협조 요청

**방어 코드는 자기 자신이 배포되는 순간은 막지 못한다.** 지금 접속 중인 사람들은
방어 코드가 없는 옛 버전으로 실행 중이기 때문이다.

```
현재       사람들 브라우저에 방어 없는 옛 빌드가 돌고 있음
  ↓
방어 배포   그 사람들은 여전히 옛 코드 → 이번 배포에서도 그대로 겪는다
  ↓
그 이후    새로고침해 새 빌드를 받은 뒤부터 보호된다
```

→ **이번 배포만 사용자가 적은 시간에** 진행하고, 그 이후로는 근무 시간에 배포해도 된다.

# B. 알림 클릭이 페이지를 다시 엶

> 조사 원본: `jwheo/refs/알림_리프레시_장애_수정_인계.md` (원인 확정·수정 지점 특정 완료)

## B-1. 현상

2026-08-27(목) 10:35~13:00, 일정 리마인더 테스트 중 접속자 화면이 **5분 주기로 리로드**되어
작업이 유실됐다. 주기가 리마인더 크론(`*/5 * * * *`)과 일치했고, **알림 권한을 허용해 FCM
토큰이 저장된 사용자만** 겪었다.

## B-2. 원인

| # | 하는 일 | 주체 |
| --- | --- | --- |
| 1 | 5분마다 알림 문서 N건 생성 | `calendar-reminder` (서버) |
| 2 | 알림 문서 생성 → OS 푸시 발송 | `push-notifications` (서버) |
| 3 | 배너가 자동으로 안 사라져 사용자가 클릭 | 서비스워커 |
| 4 | 클릭 → 열린 탭 하드 내비게이션 = **리로드** | 서비스워커 `navigate()` |

**리마인더는 1번만 담당한다. 화면을 건드리는 코드가 한 줄도 없다.** 2~4는 알림 공통 기능이라
결재 알림에도 그대로 적용돼 있었다 — 리마인더가 없어도 존재하던 결함이고, 지금까지도 결재
알림을 누르면 작업 중이던 화면이 날아갔다. 목적지가 마침 보려던 결재 문서라 장애로 인식되지
않았을 뿐이다.

리마인더가 한 일은 **규모와 빈도**(5분 주기 × 전 사원)를 처음 만든 것이다.

### 함께 드러난 것 — 알림 1건마다 전 접속자가 목록 전체를 재조회

Appwrite Realtime 은 채널에 쿼리 필터를 걸 수 없어 구독이 **컬렉션 전체**다. 그래서 누구의
알림이 생기든 모든 클라이언트가 이벤트를 받는데, payload 를 보지 않고 무조건 목록을 다시
읽고 있었다. 게다가 같은 구독이 **화면당 4곳**에서 중복 마운트됐다.

→ 전 사원 발송 시 클라이언트 1대당 **(수신자 수 × 4)회 재조회**. 브라우저가 멎는 수준이다.

Firestore 시절에는 서버측 `where('userId','==',userId)` 가 이 역할을 했다.
Appwrite 이관 과정에서 그 필터가 사라진 것이 원인이다.

## B-3. 해결 〔완료〕

| 항목 | 조치 |
| --- | --- |
| **하드 내비게이션 제거** | 서비스워커가 `client.navigate()` 대신 `workfit-open-link` 를 앱에 넘기고, `AppShell` 이 react-router 로 이동한다. 페이지가 다시 로드되지 않는다. PWA 경로도 동일 |
| **구독 필터** | 이벤트 payload 의 `userId` 가 본인이 아니면 재조회를 건너뛴다. 못 읽는 형태면 안전하게 재조회 |
| **구독 공유** | 사용자당 구독을 하나만 두고 여러 화면이 나눠 쓴다. 구독자가 0이 되면 실제 구독도 끊는다 |
| **결재 구독 합치기** | 결재 문서는 사용자별로 가를 수 없어(관련자 모두가 봐야 함) 필터 대신 150ms 합치기. 일괄 결재 시 전체 재조회가 수십 번 돌던 것을 한 번으로 |
| **알림 쌓임 해소** | 일정 알림에 `tag`(병합) 부여 + `requireInteraction` 해제(자동 소멸). 치우려고 클릭하게 만들면 그 클릭이 곧 화면 이동이다. 알림센터에는 남는다 |
| **리마인더 부하** | 알림 생성을 25건씩 나눠 만들고, `Promise.all` → `allSettled`. 기존에는 500건 중 1건만 실패해도 `reminded` 플래그가 안 서서 **5분 뒤 전원이 다시 받았다** |

### 바꾸지 않은 것

- **일정 알림은 전 사원이 받는다.** 수신자 축소는 해결책이 아니다
- **리마인더 5분 주기 유지.** 해결은 전부 "받는 쪽"에서 했다

### 남은 배포

```
node scripts/deploy-calendar-reminder.mjs --prod
```

## 용어 (A·B 공통)

**청크(chunk)**
앱 전체를 한 덩어리로 만들지 않고 화면별로 쪼갠 자바스크립트 파일. 현재 116개.
로그인만 해도 모든 화면 코드를 받는 일이 없도록 쪼갠다.
전부 합치면 2.6MB, 지금은 첫 접속에 1.5MB만 받는다.

**해시(hash)**
파일 이름 뒤에 붙는 `-DT0pnIjN` 같은 문자열. 사람이 정하는 것이 아니라 파일 내용을 계산해
자동으로 붙는 지문. 이름이 늘 같으면 브라우저가 옛 파일을 캐시에서 계속 쓰기 때문에 필요하다.

**왜 JSP·ASP 에서는 없던 문제인가**
그쪽은 화면을 옮길 때마다 서버에서 HTML 을 새로 받으므로 **주소록도 매번 갱신된다.**
지금 방식(SPA)은 접속할 때 주소록을 한 번만 읽고 화면 이동은 브라우저 안에서 처리한다.
그래서 그 사이에 파일 이름이 바뀌면 어긋난다.

| | JSP/ASP | SPA(현재) |
| --- | --- | --- |
| 화면 이동 | 서버에 HTML 재요청 | 브라우저 안에서 처리 |
| 파일 주소록 | 이동할 때마다 갱신 | 접속할 때 한 번만 |
| 작성 중 배포 | 영향 없음 | 다른 화면 열려는 순간 404 |

**프레임워크 문제인가**
아니다. Vite·webpack·Next.js·Vue 모두 같다. **SPA + 코드 분할** 조합의 구조적 특성이고,
`ChunkLoadError` 라는 이름이 붙어 있을 만큼 흔하다.
코드 분할을 안 하면(한 덩어리) 이 문제는 사라지지만 첫 로딩이 1.7배로 무거워진다.
