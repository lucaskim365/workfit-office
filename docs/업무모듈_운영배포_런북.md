## 2. 순서 — 그리고 왜 이 순서인가

```
① 권한 방침 결정  →  ② prod 컬렉션 생성  →  ③ gitlab/main 병합
                                              →  ④ GitHub main 반영  →  ⑤ 운영 검증
```

**②를 ③보다 먼저 하는 것이 이 런북의 핵심이다.**

2026-08-18 오전, `integ/gw-modules`를 gitlab에 push한 지 **14분 만에** 다른 개발자가
그것을 GitHub main으로 병합했다(그 뒤 되돌림). 즉 **gitlab/main에 올리는 순간
누군가 운영으로 승격시킬 수 있다.** 그 시점에 prod 컬렉션이 없으면 업무 모듈 5개
화면이 전부 404를 맞는다 — `crudBackend.loadAll`에 try/catch가 없어 **graceful
degrade가 아니라 화면이 깨진다.**

컬렉션을 먼저 만들어 두는 것은 무해하다. 코드가 배포되기 전까지는 빈 컬렉션이
놀고 있을 뿐이다. 순서를 뒤집을 이유가 없다.

## 3. 단계별 절차

### ① 권한 방침 결정 (사람의 판단 — 자동화 불가)

신규 11종은 기존 37종과 동일하게 `POC_PERMISSIONS`(= `Role.any()` 전체 CRUD)로 만들어진다.

- dev에서는 무해했다. **운영에는 실제 회사 데이터가 있고 projectId는 브라우저 번들에 공개돼 있다.**
- 기존 37종이 이미 전부 `Any`라 일관성은 있다(컷오버 런북 §5에도 "운영 보안 부채"로 기재).
- 좁히려면 Appwrite Auth 도입이 선행돼야 한다. 자체 로그인(users 컬렉션 + 자체 해시)을
  쓰는 현재 구조에서는 `Any` 외에 선택지가 마땅치 않다.

**결정 결과를 여기 기록할 것:** `[ ] Any 유지(부채 인정)` / `[ ] 좁힘 — 방식: ______`

### ② prod 컬렉션 11종 생성

```bash
APPWRITE_ENDPOINT=https://appwrite.widdyax.com/v1 \
APPWRITE_PROJECT_ID=6a6bf85e002acb7f71d6 \
APPWRITE_DATABASE_ID=workfit \
APPWRITE_API_KEY=<prod 서버 API 키> \
npm run appwrite:schema
```

- **env를 반드시 명시할 것.** 생략하면 `.env.local`의 `VITE_APPWRITE_*`(= **dev**)로
  폴백해 또 dev에 돌아간다. 이 저장소에서 dev/prod를 가르는 것은 오직 env뿐이다.
- 스크립트는 멱등이다. 기존 37종은 `getCollection`이 성공하면 건너뛰므로
  **컬렉션·속성·권한 어느 것도 덮어쓰지 않는다.** 없는 11종만 생성한다.
- 필요 스코프: `databases` / `collections` / `attributes` / `indexes` read+write.
- **데이터 이관은 필요 없다.** 11종 모두 문서 0건에서 시작한다(옮겨올 원본이 없다).

생성 확인:

```bash
# 익명 프로브 — 11종이 404 → 200 으로 바뀌면 성공
node -e '…'   # §4 검증 스니펫 참조
```

### ③ gitlab/main 병합

```bash
git push gitlab feat/gw-appwrite-wiring
# → gitlab에서 main으로 MR/병합
```

②가 끝난 뒤에 할 것. 병합 직후 다른 개발자가 GitHub로 승격시켜도 안전한 상태가 된다.

### ④ GitHub main 반영 → Vercel 자동 배포

- **jwheo 계정은 GitHub 쓰기 권한이 없다**(`403 Permission to lucaskim365/workfit-office.git denied to hjw3417`, 2026-08-18 재확인). 권한을 받거나 lucaskim365/hongchaerish이 수행해야 한다.
- CI 정의 파일은 저장소에 없다(`.github/` 0건). 배포 트리거는 **Vercel Git 연동뿐**이다.
- 배포 전 Vercel → Deployments에서 **실제 빌드 명령**을 확인할 것(§1 각주).

## 5. 롤백

> **⚠ 컷오버 런북 §4의 "브리지 덕에 롤백이 안전하다"는 더 이상 사실이 아니다.**
> `bfd9409`(2026-08-17)로 듀얼 라이트 브리지 `bridge-a2f`가 제거되고
> "Firestore로 향하는 런타임 연결이 0"이 됐다. Firestore 데이터는 그날 이후로 **정지 상태**다.

- **쓰면 안 되는 레버:** Vercel env에서 `VITE_DB_DRIVER`를 `firestore`로 바꾸거나 지우는 것.
  앱 전체가 08-17에 멈춘 Firestore를 보게 되어, 그 뒤 Appwrite에 쌓인 운영 데이터가
  **화면에서 사라진다.** 업무 모듈만의 문제가 아니라 전 모듈에 영향을 준다.
- **써야 할 레버:** Vercel → Deployments → 직전 배포로 **Instant Rollback**.
  코드만 되돌아가고 데이터는 그대로다.
- 컬렉션은 롤백 대상이 아니다. 빈 컬렉션이 남아 있어도 해가 없고, 재배포 시 그대로 쓰인다.

## 6. 이번 배포에서 제외되는 것

| 모듈 | 상태 | 이유 |
| --- | --- | --- |
| **메일** | 화면은 배포되나 동작 안 함 | 운영 Function 미이식. 별도 백엔드에 붙일지 방향 재검토 중 |
| **근태** | 화면은 배포되나 조회 실패 | prod에 `employees`/`attendance` 없음 + caps-ingest Function 미배포 + 아래 권한 문제 |

근태는 컬렉션을 만들어도 열리지 않는다. 개인정보라 **서버 전용 권한(`permissions: []`)**으로
프로비저닝되고, 브라우저는 projectId만 가진 익명 클라이언트라 **401을 받는다**(dev에서 실측).
Appwrite Auth + 문서 권한이나 서버 경유 조회가 선행돼야 한다.

도크에서 두 타일을 내릴지(`GW_READY_APPS`), 깨진 채 노출할지는 배포 전 결정할 것.

## 7. 함정 (전부 실측으로 확인된 것)

1. **`scripts/appwrite-deploy-functions.mjs`는 제거된 `bridge-a2f`를 되살린다.**
   이 스크립트는 `push-notifications` + `bridge-a2f` + `caps-ingest`를 함께 배포한다.
   근태 Function을 올리려고 무심코 실행하면 Firestore 듀얼 라이트가 부활한다.
   푸시 단독 배포용으로 `scripts/deploy-push-only.mjs`가 따로 있는 이유가 이것이다.
   **caps-ingest만 올리는 스크립트는 아직 없다.**

2. **함수 매니페스트 5개가 prod 프로젝트 ID를 하드코딩하고 있다.**
   `appwrite/{bridge/appwrite-to-firestore,functions/caps-ingest,functions/push-notifications,functions/widdy-chat,functions/widdy-login}/appwrite.json`이
   전부 `6a6bf85e…`다. 반면 배포 스크립트는 `.env.local`의 `VITE_APPWRITE_PROJECT_ID`(= dev)를 읽는다.
   **목적지가 실행자에 따라 갈린다.**

3. **dev 프로젝트 ID는 커밋 이력에 단 한 번도 없다**(`git log --all -S` 0건).
   코드·문서만 따라가면 기본값이 전부 prod로 수렴한다. dev는 오직 `.env.local`에만 존재한다.

4. **Appwrite `listAttributes`는 기본 25건만 반환한다.**
   속성이 그보다 많은 컬렉션(`resources` 29개)에서 무한 대기에 빠졌다. `8a15f01`에서
   `Query.limit(500)` 명시로 수정했다. 지우지 말 것.

5. **integer 속성에는 min/max를 반드시 넘겨야 한다**(1.9.6). 생략하면 워커가 `processing`에서
   멈춘다. `INT()` 헬퍼가 기본값을 채운다.

6. **프록시 5xx로 속성 생성이 중단되면 고아가 남는다.** `workPhases.id`가 `processing`에
   박혀 재실행해도 안 풀렸다. 해당 속성을 DELETE한 뒤 스크립트를 다시 돌리면 복구된다.

7. **배포 거버넌스 문서(`AGENTS.md`, `jwheo/DEPLOY_PREP.md`, `DEVELOPMENT_PROGRESS.md`)는
   `gitlab/feat/gw-resource` 브랜치에만 있다.** main에도 이 브랜치에도 없다.
