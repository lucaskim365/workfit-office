### 0.1 사용자 규칙 — 화면·데이터 기준 (2026-11-25 프관 세션에서 넘겨받음, 모든 단계에 적용)
1. **가짜 데이터 금지**: 샘플 회사·사람·날짜를 지어 넣지 않는다. 없는 값은 비워 두고 "미입력"으로 보여 준다. 규칙은 테스트 파일 안의 작은 데이터로만 확인한다.
2. **숫자는 눌러서 무엇인지**: 모든 숫자·배지·경고는 누르면 그 항목 목록이 나오고, 처리 버튼도 거기에 같이 있어야 한다.
3. **새로 손으로 입력할 칸을 늘리지 않는다**: 있는 데이터에서 계산해 보여 주는 기능을 먼저 만든다.
4. **양식에 없는 칸은 먼저 묻는다**: 회사 실제 양식이나 사용자 요청에 없는 입력 칸·측정값(예: 업무별 시간)은 넣지 않는다. 필요해 보이면 [제안]으로 올리고 동의 뒤 넣는다.
5. **빈 칸·빈 구역을 숨기지 않는다**: 0건이어도 자리는 둔다(늘 같은 곳). 대신 "무엇을 하면 채워지는지"를 보여 준다.
6. **메뉴를 빼거나 옮기는 건 사용자 결정**: '정리'라며 메뉴 항목을 숨기거나 옮기지 않는다.
7. **모양**: 그룹웨어 틀(상단 바·탭·머리말·글꼴·색·카드·버튼 모양)은 지킨다. 내용 영역(표·보드·간트·밀도)은 일에 맞게 짜도 되지만 그룹웨어 옆에서 "다른 세상"처럼 보이면 안 된다. 팔레트 밖의 새 색·글꼴은 먼저 묻는다.
8. **참고 사이트는 배치만 빌린다**: 다른 서비스 화면을 통째로 베끼지 않는다.
9. **버튼은 글자로**: 나이 많은 사용자가 많다. 아이콘만 있는 버튼은 피한다.
10. **사용량이 적다고 기능을 빼지 않는다**: 데모는 테스트 버전이라 적게 쓰인 게 정상. 알림은 그룹웨어 메신저, 로그인·권한은 그룹웨어 것을 쓴다는 전제로 만든다.
11. **모르는 규칙은 지어내지 않는다**: "확인 필요"로 표시하고 묻는다.

## 2. 만드는 방식

그룹웨어 규칙([DB_이관_대비_설계원칙](../../DB_이관_대비_설계원칙.md))을 따른다.

```
src/domain/pm/      데이터 모양(zod) + 계산 규칙(진척·지연·손익). DB 모름. 테스트(node:test) 붙임
src/data/pm/        저장소. createCrudBackend 로 Appwrite (개발 중엔 메모리)
src/features/pm/    화면용 훅 (TanStack Query)
src/modules/gw/pm/  화면 (React + Tailwind, shared/ui 공용 부품)
```

### 2.1 쓰는 기술 (데모 → 그룹웨어)
| 데모 | 그룹웨어 |
|---|---|
| 순수 JS + 문자열로 HTML 만들기(`innerHTML`) | **React 19 + TypeScript 5.8** (Vite 6) |
| CSS 107KB (`--faint` 등 변수) | **Tailwind 4** + `src/index.css` 의 `@theme` 토큰(`bg-panel`·`text-ink2`·`border-border`·`bg-navy`…) |
| 전역 객체 `S` | 데이터 모양 = **zod** 스키마, 화면 데이터 = **TanStack Query** 훅(`useQuery`/`useMutation`, 저장 후 다시 읽기) |
| `/api/state` 로 통째 저장 | **Appwrite** 컬렉션별 저장 (`createCrudBackend`, `VITE_DB_DRIVER` = appwrite / 없으면 메모리) |
| IndexedDB 파일 | `fileStorage` (`src/shared/lib/storage.ts`, Appwrite Storage) |
| 사용자 선택 창 | `useAuth()` 로그인한 사람 · `useAuthz().can('키')` 권한 · 라우트 `ProtectedRoute` |
| `#/task/wbs` 해시 주소 | react-router 7 (`/gw/task?view=...`) |
| 직접 만든 표·창·그래프 | `shared/ui`: DataTable · Modal · Button · Pill · Kpi · FilterBar · form(Field·TextField·SelectField·DateInput) · charts(Donut·LineChart·GroupedBars·Gauge…) · 아이콘 lucide-react |
| 입력 폼 | react-hook-form + zod |
| PDF·엑셀 | jspdf · html2canvas-pro · pdfjs-dist (이미 있음) |
| 테스트 없음 | node:test (`npx tsx --test`) |

- 새 코드는 `pm` 이름 아래로 모은다 → 업무계획(`modules/gw/task` 의 WorkPlan*)과 섞이지 않음.
- `TaskScreen.tsx` 는 `modules/gw/pm` 의 첫 화면을 부르는 한 줄짜리로 바꾼다 (라우트 `/gw/task` 그대로).
- 화면 틀 = 그룹웨어 앱 공통: `GwHead`(그룹웨어 / 프로젝트, 아이콘 제목) + `GwSideNav`(왼쪽 메뉴 카드) + `GwSplit`.
  데모 메뉴 6개가 왼쪽 메뉴의 묶음, 화면들이 그 항목. 내용 영역은 데모 배치를 따른다.
- 사람: 데모는 이름 글자("박명규 부장")로 연결 → 그룹웨어 **사용자 ID** 로 연결. 로그인한 사람이 '나'(데모의 사용자 선택 창 없앰).
- 알림: 데모 🔔 → 나중에 그룹웨어 알림·메신저로 (1차 범위 밖).

## 3. 데이터 설계

### 3.1 원칙
1. **사업은 PM이 따로 가진다 (`pmProjects`, 11/24 사용자 결정).** 사업관리(`workProjects`)에 맞추느라 데모 기능을 줄이지 않는다.
   `workProjects` 는 읽지도 쓰지도 않는다 → 사업관리·캘린더에 영향 없음. 나중에 이어야 하면 `pmProjects` 에 연결 칸 하나(`workProjectId`)만 더한다.
2. **PM 전용 데이터는 새 컬렉션 `pm*` 으로 따로 둔다.** 기존 데이터와 섞지 않는다.
3. 기존 `workTasks`·`workTracks`·`workTaskNotes` 는 새 화면에서 쓰지 않는다. 지우지 않고 그대로 둔다 (데이터 정리는 나중에 따로 결정).
4. 연결은 이름이 아니라 고정 ID로. 날짜는 ISO 문자열, 금액은 정수(원).

> **사업관리와 겹침 (11/24 사용자 결정)**: 사업관리(동료, `docs/superpowers/specs/2026-11-13-biz-company-master-design.md`)도
> 정부사업·도입/매입기업·사업구분·매입 결제를 다룬다. 겹쳐도 **PM을 주로 가져가며 PM 기능은 하나도 빼지 않는다.**
> 정리가 필요하면 사업관리 쪽에서 덜어낸다. → PM은 사업·기업·사업구분·손익을 자기 데이터(`pm*`)로 온전히 가진다.
> 단 **이 작업에서는 PM만 만진다.** 사업관리 등 다른 기능은 고치지도 덜어내지도 않는다 — 덜어내기는 담당자와 협의·통보 뒤 따로.

### 3.2 컬렉션 (1차 안)

| 컬렉션 | 데모 원본 | 주요 칸 |
|---|---|---|
| `pmProjects` | 사업 정보 + 계획서 정보(`plan-data`) | id(P1~) · 도입기업 · 사업 구분(정부일반형 등) · 사업번호(SF…) · 주관기관 · 공급기업 · PM · 요약 · 계획서(KPI·사업비 A~G·목표) |

- 칸은 메뉴를 만들 때마다 확정한다 (한 번에 다 만들지 않음). **업무 목록 양식은 아직 미확정** → `pmTasks` 는 칸을 나중에 늘리기 쉽게(필수 칸 최소) 잡는다.
- **업무 목록 양식 — 바뀔 수 있는 것** (프관 답 1124, 11/16 사용자와 이야기한 방향, 확정 아님 · 신광 v4도 초안):
  - 구조는 **3단 고정**: 묶음 → 업무 → 세부(세부 작업/FP 기능).
  - **부서** 칸이 생길 수 있음: 영업 / PMO / 버티컬 / 개발 / PLC (지금은 개발 TASK만).
  - 날짜·관리기준 일정은 **협약일에서 자동 계산**하는 방향 (지금은 날짜 비어 있음).
  - 진척은 완료 체크·티켓으로(MD 가중), 연결은 이름이 아닌 **고정 번호**.
  - **PLC(설비 연계) 업무**: 엑셀엔 별도 시트, 데모엔 없음, 개발 진척에서 뺌 → 들어오면 "진척 계산 제외" 표시가 필요.

  - 공수 기준(신규 3 / 출력·알림 등 5 / 변경 1 / 재사용 0.5)은 팀장님 확인 전 초안 — 엑셀에서 MD를 정할 때 쓰는 규칙이고, PM 화면은 MD 값을 그대로 쓴다.
  - → `pmTasks` 에 **선택 칸**만 열어 둔다: `dept`(부서) · `excludeFromProgress`(PLC 등 진척 제외) · `fpExcluded`(FP 제외 n) · 날짜 자동 계산 근거(예: 협약일 기준 몇째 주). 지금 데이터엔 비워 둠.
  - 업무 목록 작성 규칙 전체: `프관/새로운 태스크/개발TASK_작성_프롬프트.md`.
- 새 컬렉션은 `scripts/appwrite-schema.ts`(공용 파일)에 적는다 → **먼저 알리고 고침, 실제 생성은 허락 후** (`--only=pm... --new-only`).

### 3.2.1 다른 데이터에 영향이 안 가게 (격리 장치)
1. PM 코드(`data/pm/*`)는 `pm` 로 시작하는 컬렉션 이름만 가진다. 다른 컬렉션 repo를 부르지 않는다.
2. 컬렉션 만들기는 `appwrite-schema.ts --only=pm...,pm... --new-only` 로만 → 이미 있는 컬렉션은 속성 하나도 안 건드림 (스크립트가 `--only` 없이 `--new-only` 를 거부).
3. 옮기기 스크립트는 `pm*` 에만 쓰고, 먼저 `--dry-run`(쓰기 없음) 결과를 보여 준 뒤 허락받고 실행. 개발 DB → 확인 → 운영 DB 순.
4. 개발 중에는 메모리 모드라 DB를 아예 안 씀.
5. 파일은 Storage에 `pm/` 경로로만.
6. **(2차에만 해당) 예외 — 3.5 연결**: 1차에는 연결이 없으므로 이 예외도 쓰지 않는다 (11/25). 2차에서: 업무계획·캘린더·알림에는 그 기능의 기존 저장 함수로만 쓰고(코드·칸 변경 없음), 무엇을 만들었는지는 `pmLinks` 에 남긴다. PM이 만든 기록만 고치거나 지운다. 자원예약·근태·외근은 읽기만.

### 3.2.2 화면 부품
공용 부품(`shared/ui`)으로 표현이 안 되는 것(간트, 단계 카드, 진척 막대 등)은 **새로 만들어도 됨** (11/24 사용자). 새 부품은 `modules/gw/pm/ui/` 에 두고 `shared/ui` 는 고치지 않는다 → 다른 화면에 영향 없음.

**규칙의 이유 (대화에만 있던 것)**
- 자동 완료 없앰: 세부 작업을 다 끝내도 다음 날 세부 작업을 더 적을 수 있어서.
- 엑셀 상태 '지연' 무시: 엑셀 올린 날에 멈춘 값이라 오늘 기준으로 다시 판정.
- 탭 숫자 = 보드 카드 수: 11/9 검수에서 숫자와 카드 수가 달라 혼란 → 맞춤.
- **숫자는 눌러서 무엇인지 보이게**: 모든 숫자·경고는 누르면 그 항목 목록 (사용자 규칙).
- **빈 화면 숨기지 않기**: 비어 있으면 "무엇을 하면 채워지는지"를 보여 준다 (11/12 B-3).
- "재사용 기능 1개 = 0.5MD" 는 엑셀(TASK 작성 규칙)에서 MD를 정할 때의 규칙. **PM 화면은 MD 값을 그대로 쓴다** (화면에서 다시 계산하지 않음).

- 그 밖의 규칙(관리기준 일정, 손익)은 해당 메뉴를 옮길 때 데모 코드에서 그대로 옮기고 테스트로 데모와 같은 숫자인지 확인한다.

### 3.5 그룹웨어에 이미 있는 기능과 겹치는 것 — **2차 설계 (이관 후, 피드백 받은 뒤)**

> **[결정 11/25 사용자] 1차 이관은 "데모 그대로 옮기기만". 그룹웨어 다른 기능과의 연결은 1차에서 하나도 구현하지 않는다.**
> 이유: PMS가 아직 온전하지 않아, 지금 연결하면 업무계획·캘린더·알림 등 기존 기능에 어떤 영향이 생길지 모름. 연결·추가 기능은 옮긴 뒤 다른 부서·회사 피드백을 받아 정한다.
> - 아래 3.5 · 3.5.1 · 3.5.2 는 지우지 않고 **2차 설계**로 둔다 (업무계획 반영·불러오기, 캘린더 반영, 메신저·푸시 알림, 휴가·외근·공휴일 불러오기, 회의 흐름 순서 변경 등 전부).
> - 1차에는 그룹웨어 다른 기능의 데이터를 **읽거나 쓰는 코드도 없다**. 예외(연결이 아니라 바탕): 로그인·사람 = 그룹웨어 사용자(읽기), 저장 = 그룹웨어 DB `pm*` 컬렉션(7단계).
> - **업무계획**: 데모 기능 그대로 PM 메뉴 안에 옮긴다 (오늘 할 일·추천·넘김·주간·PDF 등). 그룹웨어 업무계획 앱과는 따로.
> - **자원예약**: 옮기지 않는다 — 데모에서도 화면 함수 `schedBook` 이 어디서도 불리지 않는 죽은 코드(메뉴로 못 들어감), `bookings` 0건.
> - **알림**: 데모처럼 PM 화면 안 🔔 목록만.

**(2차) 원칙 (사용자 11/24): 겹치는 건 웬만하면 전부 연결한다. 겹치면 PM이 주(主)다.**
- 회사 업무 방식상 **계획·일정은 PM에서 정하고 그룹웨어(업무계획·캘린더)에 자동으로 들어가게** 한다. 반대로 업무계획·캘린더에 이미 적힌 것을 PM으로 **불러오는** 길도 둔다.
- PM이 직접 하지 않는 기능(자원예약 등)도 연결할 부분이 있으면 그룹웨어 정보를 **불러와서 보여 준다**.
- 그룹웨어에서 꺼져 있는 기능(문서관리 등)은 대부분 PM 때문에 꺼 둔 것 → 그 역할은 **PM이 맡는다**.

**연결 방식 (그룹웨어 다른 기능의 코드·칸은 고치지 않는다)**
- 불러오기 = 그 기능의 기존 데이터 함수로 **읽기만**.
- 자동 반영 = 그 기능의 기존 저장 함수로 **일반 사용자가 쓰는 것과 같은 모양**의 기록을 만든다 (업무계획 = 그 사람·그 날 칸, 캘린더 = 일정). 남의 컬렉션에 새 칸을 더하지 않는다.
- 어느 PM 항목이 어느 업무계획·일정이 됐는지는 **PM 쪽 연결 표(`pmLinks`: PM 항목 ID ↔ 그룹웨어 기록 ID)** 에 적는다 → 다시 반영할 때 중복 안 생김, PM에서 지우면 PM이 만든 것만 지움, 사람이 직접 쓴 기록은 건드리지 않음.
- 세부 방식(업무계획 한 칸 글에 어떻게 넣을지, 양쪽에서 고쳤을 때 어느 쪽을 따를지)은 **3단계(대시보드·업무계획) 때 사용자 설명을 듣고 확정**.

## 4. 데이터 옮기기

| 원본 | 방법 |
|---|---|
| 데모 내장 데이터(`wbs-data`·`plan-data`·`fn-data`) | 옮기기 스크립트 `scripts/pm-import.ts` |
| NAS `state.json` (티켓·세부 작업·이슈·회의·손익·활동 기록·수정본 등) | 같은 스크립트가 읽음 (파일을 받아서) |
| 계획서 PDF | `프관/사업계획서/` 폴더 파일을 Storage에 올림 + **화면에서 직접 올린 PDF 대조** (아래) |

- **먼저 "미리보기(dry-run)"**: DB에 쓰지 않고 무엇이 몇 건 들어갈지, 연결이 끊긴 기록(아래 4.1)이 몇 건인지, 못 찾은 사람 이름이 누구인지 보고서만 출력.
- 사업: 데모 P1~P13 을 `pmProjects` 로 그대로 (사업관리와 짝짓지 않음).
- 사람 짝짓기: 데모 이름 → 그룹웨어 사용자. 못 찾은 이름은 목록으로 보여 주고 사용자 확인. 도입기업 담당·협력사는 사용자로 넣지 않고 이름 글자로.
- 실제 쓰기(개발 DB → 운영 DB)는 각각 허락 후. 기존 `approvalDocs`·`approvalForms` 등은 건드리지 않는다.
- 받은 `state.json` 은 저장소 밖 `C:\dev\pm-migration\state-YYYYMMDD.json` 에 둔다 (실제 이름·업무 기록이 있어 커밋 금지).
- 계획서 PDF: 화면에서 올린 PDF는 그 PC 브라우저(IndexedDB `ffpm-files`)에만 있다. 미리보기 보고서에 "사업별 PDF 등록 여부 vs `사업계획서/` 폴더" 대조표를 넣고, 폴더에 없는 것은 올린 사람 PC에서 받아 둔다.

### 4.1 데이터 우선순위 — 내장 데이터 vs NAS `state.json` (프관 검토 11/24)
사실 (11/24 확인):

- **NAS `state.json` 실제 내용 (11/24 읽기만 해서 받음, ver 323, 마지막 저장 11/16)**: 사업 10 · 사용자 39(역할: 관리자·PM·팀장·팀원·협력사·도입기업 담당) · 기업/기관 16 · 부서 8 · 코드 7묶음 · 티켓 11 · 세부 작업 10건(4개 업무) · 업무계획 2명 43건(이재원 39·신지웅 4, 11/2~11/16, 업무와 연결된 항목 0) · 손익(`money`: 설정·지원 기준·계약·비용·입금·재원) · 사업비 예산 7 · 계획서 적용 기록 7 · 업무 템플릿 7 · 기준선 10. 이슈·CR·회의록·액션·사업비 집행·KPI 측정·변경 이력 = 0건. `wbsImport` 없음.

### 4.2 넘어가는 날 (프관 검토 11/24) — 날짜는 사용자가 정함
옮기는 몇 주 동안에도 데모(NAS)로 업무계획·티켓을 실제로 쓰고 있다.
1. **그동안**: 데모가 정본. 그룹웨어 쪽은 개발·확인만.
2. **미리보기 리허설**: 1단계 직후부터 `state.json` 사본으로 미리보기를 돌려 본다 (5장 1.5단계). 넘어가기 전 한 번 더.
3. **넘어가는 날 (D)**: 팀에 미리 알림 → D 아침 데모 입력 멈춤(서버 끄기 또는 공지) → 마지막 `state.json` 받기 + 백업 보관 → 미리보기 → (허락) 운영 DB에 넣기 → 화면 확인 → 프로젝트 타일 켜기.
4. **같이 여는 기간**: D부터 1주. 데모는 **보기만** (입력은 그룹웨어에서만).
5. **되돌리기**: 그 1주 안에 큰 문제가 나면 데모 서버를 다시 연다 (`state.json` 은 D 그대로라 가능). 단 그 사이 그룹웨어에 새로 입력한 것은 손으로 옮겨야 하므로, 되돌리기는 D+2일 안에 결정하는 걸 권장.
6. **날짜**: 3단계(대시보드)가 끝난 뒤 사용자가 정함 (11/24).
