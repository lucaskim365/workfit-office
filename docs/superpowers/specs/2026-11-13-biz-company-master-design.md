# 사업관리 기업 정보(업무 기준정보) 개편 — 설계

2026-11-13 · 브랜치 `feature/workplan-merge-main`

## 1. 왜 하는가

회사는 정부사업 공고가 나면 **도입기업**과 협약을 맺어 사업을 신청하고 운영한다(우리 회사 = 공급기업).
사업에 필요한 물품·용역은 **매입기업**에서 산다. 그 과정에서 발주서·계약보고서·견적서가 나온다.
전체 운영 흐름을 관리하려면 기업들을 한곳에 정리해 두고, 정부사업이 시작되면 프로젝트로 등록해
기업과 이어야 한다. 이번에는 그 첫 단계로 **기업 정보 입력**을 만든다.

사용자 결정:
- **프로젝트가 곧 정부사업**이다. 프로젝트는 지금의 공용 프로젝트(`workProjects` — 과업·트랙·캘린더·모바일이 함께 씀) 하나로 통일한다.
- **중복되는 옛 구조는 쓰지 않고 새 구조만 쓴다**: `vendors`(거래처), `bizVendorProjects`(도입기업-사업 연결), `workProjects.clientName`(발주처 이름 글자 칸). 데이터는 지우지 않고 읽지도 쓰지도 않는다.
- 기업 정보는 기업마다 **한 번만** 등록한다. 기업 자체에는 도입/매입을 적지 않는다 — 같은 기업이 A사업에선 도입, B사업에선 매입일 수 있다(간혹 있음).
- **이번 범위는 기업 정보 입력만.** 프로젝트 등록·기업 연결은 다음 단계.
- 스키마는 **제3정규형**을 지킨다 — 같은 사실을 두 곳에 적지 않는다.

## 2. 목표 / 비목표 / 실패 조건

목표(이번)
- 기업 등록·수정·조회 화면: 기업명, 사업자등록번호, 대표자, 대표번호, 주소, 사용 여부.
- 기업당 **계좌 여러 개**: 은행(목록에서 선택), 계좌번호, 예금주, 기본 계좌 하나.
- 첨부파일(사업자등록증·통장 사본 등)을 받을 **데이터 자리만** 만든다(화면 없음).

비목표(이번엔 안 함)
- 프로젝트 등록 화면 개편, 기업분류·사업구분 컬렉션, 프로젝트-기업 연결, 프로젝트별 담당자 → 다음 단계(§6에 설계만).
- 견적서·계약보고서·발주서 등 문서 → 문서관리 고도화(버전 관리) 때. 자리만 생각해 둔다(§6.5).
- 파일 업로드 화면.
- 기존 운영 `vendors` 6건 옮기기 — 개발 초기 예시 데이터(`src/data/seeds/vendor.seed.ts`)와 같아 옮기지 않는다.

실패로 보는 것
- 같은 기업이 사업자등록번호만 다르게 혹은 같게 두 번 들어가는 것(중복 데이터).
- 은행 이름이 사람마다 다르게 적히는 것('국민은행'·'KB국민').
- 화면에 내부 ID·코드·개발용 안내문이 보이는 것(프로젝트 규칙).
- 결재 문서(`approvalDocs`)·서식(`approvalForms`)을 건드리는 것(프로젝트 규칙 — 이번 작업은 근처에도 가지 않는다).

## 3. 데이터 구조(이번에 만드는 것)

Appwrite 새 컬렉션 3개 + 공통코드 그룹 1개. 정의는 `scripts/appwrite-schema.ts`에 추가하고
`--only=... --new-only` 로 개발 → 운영 순서로 만든다(운영은 사용자 지시 후).

### 3.1 `companies` — 기업

| 칸 | 형식 | 필수 | 설명 |
|---|---|---|---|
| id | string 64 | O | `CMP-` + 시간·난수(문서 $id 와 같게) |
| name | string 128 | O | 기업명 |
| bizNo | string 10 | O | 사업자등록번호 **숫자 10자리만** 저장(표시는 `000-00-00000`) |
| ceoName | string 64 |  | 대표자 |
| phone | string 32 |  | 대표번호 |
| address | string 256 |  | 주소 |
| addressDetail | string 128 |  | 상세 주소 |
| use | boolean | O | 사용 여부(기본 true). 지우지 않고 '사용 안 함'으로 |
| note | string 1000 |  | 메모 |
| createdBy / createdAt / updatedBy / updatedAt | string |  | 기록 |

색인: `UQ('cmpBizNo', ['bizNo'])`(스키마 스크립트의 유일 인덱스 도우미 — DB가 중복을 막는다), `IX('cmpName', ['name'])`. 저장 때 유일 인덱스 충돌(409)은 "이미 등록된 사업자등록번호"로 보여 준다(두 사람이 동시에 같은 번호를 넣는 경우).

- 사업자등록번호 검증: 10자리 + 국세청 검증식(`isValidBizNoChecksum`, 이미 있음). 검증식이 틀리면 경고하되 저장은 막지 않는다(기존 화면과 같은 동작 — 정정 전 서류 번호를 그대로 적는 경우).
- 중복: 같은 번호의 기업이 있으면 저장 불가, '사용 안 함' 상태라면 "다시 사용으로 바꾸기"를 안내.

### 3.2 `companyBankAccounts` — 기업 계좌

| 칸 | 형식 | 필수 | 설명 |
|---|---|---|---|
| id | string 64 | O | `CBA-` + 시간·난수 |
| companyId | string 64 | O | `companies.id` |
| bankCode | string 16 | O | 공통코드 `BANK` 그룹의 code |
| accountNo | string 32 | O | 숫자와 `-` 만, 입력 그대로 보존 |
| holder | string 64 | O | 예금주(기업명과 다를 수 있어 따로 둔다) |
| isDefault | boolean | O | 기본 계좌 — 기업당 사용 중 계좌 중 하나만 true |
| use | boolean | O | 사용 여부 |
| note | string 200 |  | 메모(용도 등) |
| createdBy / createdAt / updatedBy / updatedAt | string |  | 기록 |

색인: `companyId`.

- 은행 이름은 저장하지 않는다(정규화) — `bankCode` 로 공통코드에서 찾는다.
- 기본 계좌 규칙(앱에서 지킴): 사용 중 계좌가 1개면 그게 기본. 기본을 바꾸면 이전 기본은 false. 기본 계좌를 '사용 안 함'으로 하면 남은 계좌 중 첫 번째가 기본.

### 3.3 `companyFiles` — 기업 첨부파일(자리만, 화면 없음)

| 칸 | 형식 | 필수 | 설명 |
|---|---|---|---|
| id | string 64 | O | `CFL-` + 시간·난수 |
| companyId | string 64 | O | `companies.id` |
| kind | enum | O | `BIZ_REG`(사업자등록증) · `BANKBOOK`(통장 사본) · `ETC` |
| accountId | string 64 |  | 통장 사본이면 `companyBankAccounts.id` |
| name | string 255 | O | 원래 파일 이름 |
| url / storagePath | string 512 | O | 파일서버(Garage S3) — 업로드 경로는 `chat/` 아래만 허용되는 제약(`chat/company/{companyId}/…`), 서명 URL 미지원이라 업로드 URL을 그대로 저장 |
| size / contentType | int / string |  | |
| uploadedBy / uploadedAt | string |  | |

색인: `companyId`. 이번엔 컬렉션·도메인 스키마·저장소 함수까지만 만들고 화면에서 쓰지 않는다.

### 3.4 은행 목록 — 공통코드 `BANK` 그룹

`commonCodes` 에 `groupCode='BANK'`, `groupName='은행'` 행을 넣는다(기존 컬렉션에 **새 행 추가만**, 기존 행 무변경).
초기값: 국내 주요 은행·지방은행·인터넷은행·증권 계좌가 흔한 곳(예: 국민, 신한, 우리, 하나, 농협, 기업, SC제일, 씨티, 수협, 대구(iM), 부산, 경남, 광주, 전북, 제주, 산업, 우체국, 새마을금고, 신협, 케이뱅크, 카카오뱅크, 토스뱅크). code 는 금융결제원 은행 코드 3자리(예: 국민 `004`).
관리자는 관리자 콘솔 › 공통코드에서 더하거나 끌 수 있다(시스템 기준정보).
넣는 방법: 스크립트(`--dry-run` 먼저), 이미 같은 groupCode+code 가 있으면 건너뜀.

## 4. 화면

위치: **사업관리 › 기업 정보** — 지금 '도입기업 정보'(`/biz/vendor`, 메뉴 `S_BIZ_VENDOR`) 자리를 그대로 쓰고 이름만 바꾼다.
권한: 지금의 `biz.vendor.view`(보기) / `biz.vendor.manage`(등록·수정)를 그대로 쓰고(운영 확인 11-13: 이 권한은 운영자·재무담당자·담당자 역할과 최고 관리자만 가짐 — 전 직원에게 계좌번호가 보이지 않는다), 권한 이름 표시만 '도입기업' → '기업 정보'로 바꾼다(키는 그대로 — 운영 역할 데이터가 키를 들고 있다).

목록
- 열: 기업명, 사업자등록번호(`000-00-00000`), 대표자, 대표번호, 기본 계좌(은행명 + 계좌번호), 사용 여부.
- 검색: 기업명 또는 사업자등록번호(숫자 3자리 이상 부분 일치). 거르기: 사용/사용 안 함. 기업명 가나다순, 쪽 나누기 — 지금 화면의 틀(`_biz` 의 BizHead·BizListCard·BizPager)을 그대로.
- 줄을 누르면 상세 창.

등록·수정 창(관리 권한이 있을 때)
- 기업 칸들 + 아래에 **계좌 목록**(줄 추가·삭제, 기본 계좌 고르기). 저장 한 번에 기업과 계좌가 함께 저장된다.
- 계좌 '삭제'는 아직 저장 안 한 줄만 실제로 빼고, 저장된 계좌는 '사용 안 함'으로 바꾼다(지우지 않음).

상세 창
- 기업 정보, 계좌 목록(사용 중 먼저, 기본 표시).
- 다음 단계에서 '참여 프로젝트'(도입/매입) 칸이 여기에 붙는다 — 이번엔 넣지 않는다.

지금 화면에서 빠지는 것: 구분(매입·매출·외주) 거르기·열, 진행 사업 수 열(옛 연결표 기반). 진행 사업은 다음 단계에서 새 연결로 다시 붙인다.

## 5. 옛 구조 정리(이번 단계 범위)

- 사업관리 › 기업 정보 화면은 `vendors`·`bizVendorProjects` 를 더 이상 읽지 않는다.
- `BizProjectScreen`(사업 현황)은 다음 단계에서 개편한다. 이번엔 손대지 않는다(운영 `bizVendorProjects` 0건, `workProjects` 0건이라 지금 보이는 것도 없다).
- 기준정보 › 거래처관리(`S_BASE_VENDOR`)는 이미 숨김 — 그대로.
- 옛 코드 삭제는 다음 단계에서 프로젝트 개편이 끝난 뒤 한꺼번에(지금 지우면 사업 현황 화면이 깨진다).

## 6. 다음 단계(설계만 — 이번엔 만들지 않음)

6.1 `companyClasses` — **기업분류(시스템 기준정보, 관리자 콘솔)**
`id, name(도입기업·매입기업…), maxPerProject(1 | null=여러 곳), order, use`. 화면 동작이 분류의 성격(maxPerProject)에 묶여 있어 담당자가 아니라 관리자가 관리.

6.2 `bizCategories` — **사업구분(업무 기준정보, 사업관리)**
`id, name(부처협업형·제조AI…), order, use`. 공고가 날 때마다 사업 담당이 추가.

6.3 정부사업 정보 — `workProjects` 에 **사업구분 칸(`bizCategoryId`)** 등 정부사업 항목을 붙인다. 프로젝트 = 정부사업이므로 1:1 별도 컬렉션을 두지 않고 프로젝트 칸으로 둔다(어느 항목인지는 다음 단계에서 사용자와 정함). `clientName` 은 쓰지 않는다(도입기업 연결로 대신).

6.4 `projectCompanies` — 프로젝트-기업 참여
`id, projectId, companyId, classId, createdBy/At`. 같은 (projectId, companyId, classId) 는 한 번만. 도입기업 분류는 프로젝트당 1곳(maxPerProject=1), 매입기업은 여러 곳.
`projectCompanyContacts` — 프로젝트별 담당자: `id, projectCompanyId, name, phone, email, role, note`(여러 명).

6.5 문서 자리 — 견적서·계약보고서·발주서는 문서관리에서 만들고, 문서가 `projectId`(+필요하면 `projectCompanyId`)를 가리킨다. 한 프로젝트에 같은 양식 여러 건 가능, 버전 관리는 문서관리 몫. 기업·프로젝트 쪽에는 문서 칸을 두지 않는다.

## 7. 정해진 방식 / 만드는 사람에게 맡긴 것

정해진 것: 위 컬렉션·칸 구조, 화면 위치·권한 키, 지우지 않고 '사용 안 함', 은행은 공통코드, 첨부는 자리만.

만드는 사람의 판단: 화면 세부 배치, 계좌번호 입력 모양, ID 생성 방식(기존 `rid` 와 같은 꼴), 저장 순서(기업 먼저 → 계좌), 테스트 범위(도메인 규칙: 사업자번호 정규화·검증·중복, 기본 계좌 규칙은 단위 테스트 필수).

검증: `npx tsc --noEmit`, `npx tsx --test …`, `npm run build`, 개발 화면에서 등록·수정·계좌 여러 개·중복 막기 확인.
운영 반영 순서: 운영 컬렉션 생성(`--dry-run` 먼저) → 은행 코드 넣기(`--dry-run` 먼저) → 배포. 모두 사용자 지시 후.

## 8. 이 문서에서 Claude 가 정한 것(사용자 확인 필요)

- 사업자등록번호는 숫자 10자리만 저장, DB 유일 인덱스로 중복 막음, **필수**(해외 업체처럼 번호가 없는 곳은 지금은 받지 않음 — 필요해지면 선택으로 바꾼다).
- 검증식이 틀려도 저장은 허용(경고만) — 지금 화면과 같은 동작.
- 은행 목록을 공통코드(`BANK`)로, 금융결제원 코드 3자리 사용.
- 계좌 삭제 대신 '사용 안 함', 기본 계좌 규칙(§3.2).
- 주소를 주소/상세 주소 두 칸으로.
- 메뉴 이름 '도입기업 정보' → '기업 정보', 권한 키는 그대로 이름만 변경.
- 기업분류·사업구분은 다음 단계에서 만든다.
- 정부사업 항목은 1:1 별도 컬렉션이 아니라 `workProjects` 칸으로(§6.3).
