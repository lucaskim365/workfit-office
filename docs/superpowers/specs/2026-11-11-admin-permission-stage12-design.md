# 관리자 콘솔 권한 고도화 1·2단계 설계

- 작성일: 2026-11-11
- 브랜치: `feature/admin-console` (콘솔 분리 a823c1bb, 콘솔 틀 정리 80cdcadd 위에서 진행)
- 범위: 1단계(권한 변경 기록, 최고 관리자 잠금 방지, 사람별 권한 확인) + 2단계(관리자 역할 나누기)
- 범위 밖: 3단계(맡는 조직 범위), 4단계(작업 단위 권한, 서버 쪽 강제)

## 0. 지금 구조 (코드 확인 결과)

| 항목 | 현재 |
|---|---|
| 역할 그룹 | `roleGroups` 컬렉션. 대상은 `userIds`·`deptIds`·`positionRanks`·`members`(옛 칸), 권한은 `menuPermissions[화면ID] = {access, create, update, delete}` |
| 최고 관리자 | `ADMIN`(또는 `ROLE_ADMIN`) 그룹에 해당하면 최고 관리자. 개발 DB에서는 **부서 1개 지정**으로 들어가 있음 |
| 기본 그룹 | `USER` 그룹은 사용 중인 모든 직원에게 자동 부여 |
| 판정 | `useSecurityContext.canMenuAccess / canMenuAction` — 최고 관리자는 근태 관제·업무 종합 현황을 뺀 모든 화면 통과, 나머지는 소속 그룹 중 하나라도 켜져 있으면 통과 |
| 콘솔 출입 | `useAdminConsoleAccess` = 최고 관리자만 |
| 콘솔 화면 보호 | 화면마다 `ProtectedRoute`(App.tsx) 가 `canAccess(url)` 확인 |
| 기록 | `systemLogs` 컬렉션(유형 `접속`·`변경`). 지금은 로그인만 기록, 권한 변경은 기록 안 함 |
| ADMIN 그룹 보호 | 삭제 불가, '사용' 끄기 불가(이미 있음). **대상자 빼기는 막지 않음** |
| 화면 안 작업 권한 | 사용자·부서·직급·공휴일 화면만 `canAction` 으로 버튼을 가림. 결재서식·결재선 규칙·결재 프로세스·결재문서 모니터링·회사 정보·공통코드·로그·백업·인터페이스는 화면에 들어오면 모든 작업 가능 |

개발 DB 역할 그룹(읽기만 확인): 관리자(ADMIN)·일반사원(USER)·임원(EXEC)·재무담당자(FINANCE). 콘솔 화면 권한이 켜진 일반 그룹은 없음.

## 1단계

### 1-1. 권한 변경 기록

**무엇을:** 그룹 권한 관리에서 저장·삭제할 때 바뀐 내용을 `systemLogs` 에 `변경` 유형으로 남긴다. 로그 관리 화면의 '전체 시스템 작업 로그' 탭에서 보인다.

**기록 형식:**

| 칸 | 값 |
|---|---|
| `type` | `변경` |
| `screen` | `그룹 권한 관리` |
| `user` | `홍길동 (2603)` (기존 로그인 기록과 같은 형식) |
| `detail` | 사람이 읽는 요약. 예: `'재무담당자' 그룹 — 대상 추가: 홍길동 / 대상 제외: 영업팀 / 공통코드: 수정 켬, 삭제 켬` |

- 새 그룹: `'결재 관리자' 그룹 만듦 — 대상 3명, 화면 4개 권한`
- 삭제: `'임시' 그룹 삭제 — 대상 2명이 있었음`
- 바뀐 게 없으면 기록하지 않는다.
- 이름은 사람 이름·부서 이름·직급 이름·화면 이름으로 적는다. ID·코드는 쓰지 않는다(화면에 개발용 값 금지 규칙).

**구현:**
- `src/domain/roleGroup/audit.ts` (새 파일, 순수 함수)
  - `diffRoleGroup(before: RoleGroup | null, after: RoleGroup | null, names: NameLookup): string | null`
  - `NameLookup` = 사용자 id→이름, 부서 id→이름, 직급 rank→이름, 화면 id→이름
- `systemLogRepo.recordChange({ user, screen, detail })` 추가 — `recordLogin` 과 같은 방식(새 ID로 바로 insert, 실패해도 저장 자체는 막지 않고 콘솔에만 남김).
- `AuthScreen` 의 저장·삭제 성공 콜백에서 호출.
- 데이터: 기존 `systemLogs` 컬렉션에 행만 추가. 칸 추가 없음.

### 1-2. 최고 관리자 잠금 방지

**무엇을:** 저장 결과 최고 관리자가 0명이 되는 변경을 막는다. 본인의 최고 관리자 권한이 빠지는 변경은 확인을 한 번 더 받는다.

**막는 경우:**
1. 그룹 권한 관리 — ADMIN 그룹에서 대상(사람·부서·직급)을 빼서 0명이 됨
2. 사용자 관리 — 마지막 최고 관리자를 '미사용'으로 바꾸거나, 부서·직급을 바꿔서 ADMIN 대상에서 빠짐

**메시지:**
- 0명: `최고 관리자가 한 명도 남지 않아 저장할 수 없습니다. 다른 사람을 먼저 최고 관리자로 지정하세요.`
- 본인 해제: `저장하면 본인의 최고 관리자 권한이 없어져 관리자 콘솔을 쓸 수 없게 됩니다. 계속할까요?`

**구현:**
- `src/domain/roleGroup/lockout.ts` (새 파일, 순수 함수)
  - `countSuperAdmins(users, groups, org): number` — 사용 중인 사용자 각각에 기존 `resolveUserRoles` 를 돌려 ADMIN 포함 여부를 센다(판정 기준을 새로 만들지 않음).
  - `checkLockout({ users, groupsAfter, orgAfter, me }): { block: boolean; selfLoss: boolean }`
- `AuthScreen.handleSave`, `UserScreen` 저장 직전에 호출.
- 사용자 `role === 'admin'` 칸(옛 방식)도 최고 관리자로 세는 지금 판정을 그대로 따른다.

### 1-3. 사람별 권한 확인

**무엇을:** 그룹 권한 관리에 세 번째 탭 `사람별 권한`을 둔다. 사람을 고르면 다음 두 가지를 보여준다.

1. **속한 그룹과 이유**

   | 그룹 | 들어온 이유 |
   |---|---|
   | 일반사원 | 전 직원 기본 |
   | 재무담당자 | 개인 지정 |
   | 관리자 | 부서: 경영기획팀 |

2. **화면별 결과** — 기존 권한표와 같은 모양(보기·작성·수정·삭제). 각 칸에 마우스를 올리면 그 권한을 준 그룹 이름이 보인다.
   - 최고 관리자는 `최고 관리자 — 모든 화면` 한 줄로 보여주고, 근태·휴가 관제 센터와 팀·전사 업무 종합 현황은 예외로 따로 표시한다.
   - 관리자 콘솔 출입 여부를 맨 위에 한 줄로 보여준다(`관리자 콘솔: 들어갈 수 있음 — 결재 관리자`).

**판정이 어긋나지 않게:** 지금 `useSecurityContext` 안에 있는 판정 로직을 순수 함수로 빼서 훅과 미리보기가 같은 함수를 쓴다.
- `src/domain/roleGroup/evaluate.ts` (새 파일)
  - `explainGroups(user, groups, org): { group: RoleGroup; via: '기본' | '개인' | '부서' | '직급' }[]` — `resolveUserRoles` 의 분기를 그대로 옮기고 이유를 덧붙임. `resolveUserRoles` 는 이 함수를 써서 다시 구현(동작 동일).
  - `evaluateMenu(groups, isSuperAdmin, screenIdOrUrl, action): { allowed: boolean; by: string[] }`
- `useSecurityContext.canMenuAccess / canMenuAction` 은 `evaluateMenu(...).allowed` 를 부른다.

## 2단계 — 관리자 역할 나누기

### 2-1. 원칙

- **새 칸을 만들지 않는다.** 관리자 역할도 지금의 역할 그룹이다. 콘솔 화면(menu-tree `area: 'admin'`)에 보기 권한이 하나라도 켜진 그룹이 곧 관리자 역할이다.
- 권한표 한 곳에서 업무 화면과 콘솔 화면을 같이 관리한다(따로 화면을 만들지 않음).

### 2-2. 콘솔 출입 기준

```
콘솔 출입 = 최고 관리자
          또는 (콘솔 화면 중 하나라도 보기 권한이 있음)
```

- `useAdminConsoleAccess` 한 곳만 바꾼다. 헤더의 '관리자 콘솔' 단추, `/admin` 진입, 옛 주소(`/base/*`·`/sys/*`) 넘김이 모두 이 결과를 따른다.
- 콘솔 왼쪽 메뉴와 콘솔 홈은 이미 `canAccess` 로 거른다 — 맡은 영역만 보인다.
- 콘솔 홈의 숫자 칸도 볼 수 있는 화면만 보인다.
- 머리 오른쪽 이름 옆에 역할을 작게 표시한다: `최고 관리자` 또는 맡은 관리자 그룹 이름(여러 개면 `결재 관리자 외 1`).

### 2-3. 최고 관리자 전용 화면

권한표로 줄 수 없고 최고 관리자만 쓰는 화면:

| 화면 | 이유 |
|---|---|
| 그룹 권한 관리 | 이 화면을 쓰면 본인에게 아무 권한이나 줄 수 있음 |
| 데이터 백업 | 전체 데이터 복원·삭제 |

- `SUPER_ADMIN_ONLY` 목록을 `src/domain/roleGroup/schema.ts` 에 두고, `evaluateMenu` 가 최고 관리자가 아니면 권한표 값과 상관없이 거부한다.
- 권한표에서는 이 두 줄을 잠그고 `최고 관리자 전용` 이라고 표시한다.

### 2-4. 기본 그룹(일반사원)은 콘솔 화면 권한 불가

- 전 직원 그룹에 콘솔 화면을 켜면 전 직원이 콘솔에 들어온다. 권한표에서 일반사원 그룹의 콘솔 화면 줄을 잠근다.
- `evaluateMenu` 도 일반사원 그룹에서 온 콘솔 화면 권한은 무시한다(데이터가 이미 그렇게 저장돼 있어도 안전).

### 2-5. 관리자 역할 서식

'새 권한 그룹' 을 만들 때 서식을 고를 수 있게 한다. 서식은 **권한표를 채워 주기만** 하고, 그룹은 관리자가 직접 저장해야 생긴다(코드가 DB에 그룹을 자동으로 만들지 않음).

| 서식 | 그룹 코드 예시 | 콘솔 권한 |
|---|---|---|
| 인사 관리자 | `ADM_PEOPLE` | 사용자·부서·직급 관리 전부, 공휴일 보기 |
| 결재 관리자 | `ADM_APPROVAL` | 결재서식·결재선 규칙·결재 프로세스 전부, 결재문서 모니터링 보기 |
| 운영 관리자 | `ADM_OPS` | 회사 정보·공휴일·공통코드 전부, 로그 관리 보기, 인터페이스 관리 보기 |
| 빈 그룹 | 직접 입력 | 없음 |

- 업무 화면 권한은 서식이 건드리지 않는다(일반사원 그룹으로 이미 받음).
- 코드가 이미 있으면 서식 선택 시 경고하고 저장을 막는다(중복 방지).

### 2-6. 화면 안 작업 권한 반영

지금 9개 콘솔 화면은 들어오기만 하면 추가·수정·삭제가 다 된다. 최고 관리자만 들어오던 때는 문제가 없었지만, 2단계부터는 "보기만 가능한 관리자" 가 생기므로 막아야 한다.

- 공통 훅 `useScreenActions(url)` → `{ canCreate, canUpdate, canDelete, readOnly }` (내부는 `canAction`)
- 화면별 적용:

| 화면 | 작성 | 수정 | 삭제 |
|---|---|---|---|
| 결재서식 관리 | 새 서식·폴더 추가, 복제 | 서식 편집·디자인 편집·사용 전환·순서 변경 | 서식 삭제 |
| 결재선 규칙 | 새 규칙 | 편집·사용 전환·순서 끌기 | 삭제 |
| 결재 프로세스 설정 | — | 켜기·끄기, 저장, 기본값 초기화 | — |
| 결재문서 모니터링 | — | (지금 화면에 수정 기능 없음 — 조회만) | — |
| 회사 정보 | 사업장·로고·직인 추가 | 모든 입력 칸(읽기 전용으로) | 사업장·로고·직인 삭제 |
| 공통코드 | 코드 추가 | 저장 | — |
| 로그 관리 | — | — | — |
| 인터페이스 관리 | I/F 추가 | 저장·연결 테스트 | — |
| 데이터 백업 | 최고 관리자 전용이라 해당 없음 | | |

- 권한이 없으면 단추를 숨기고, 입력 칸은 읽기 전용으로 바꾼다. 화면 위에 따로 안내 문구는 넣지 않는다.

### 2-7. 이미 있는 데이터에 미치는 영향

- 2단계 배포 순간, 콘솔 화면 보기 권한이 켜져 있는 일반 그룹의 사람은 콘솔 단추가 보이게 된다(콘솔 분리 전에 그 화면을 쓰던 사람들이 다시 쓸 수 있게 됨).
- 개발 DB에는 해당 그룹이 없다. **운영 DB는 배포 전에 읽기만 하는 스크립트로 확인해서 목록을 보고드린다.** 의도하지 않은 권한이면 배포 전에 관리자가 직접 끈다.
- 결재 문서(`approvalDocs`)·결재서식(`approvalForms`) 데이터는 읽지도 바꾸지도 않는다. `roleGroups` 는 관리자가 화면에서 저장할 때만 바뀌고, 코드나 스크립트가 바꾸지 않는다.

## 4. 검증

- **단위 테스트(`npx tsx --test`):**
  - `evaluateMenu`: 기존 판정과 같은 결과인지(최고 관리자 통과, 근태 관제 예외, 그룹 합산), 최고 관리자 전용 화면 거부, 일반사원 그룹의 콘솔 권한 무시
  - `explainGroups`: 개인·부서·직급·기본·옛 members 이유
  - `diffRoleGroup`: 추가·제외·권한 켬/끔·변화 없음은 null
  - `checkLockout`: 마지막 1명 제외, 부서 지정으로만 남은 경우, 본인 해제
  - 콘솔 출입: 최고 관리자 / 콘솔 권한 그룹 / 업무 화면만 있는 그룹
- **화면 확인(개발 서버, Playwright):** 개발 DB에 시험용 '결재 관리자' 그룹을 테스트 계정이 아닌 시험 사용자에게 만들어 확인한 뒤 지운다. 콘솔 메뉴가 전자결재만 보이는지, 그룹 권한 관리·백업 주소로 들어가면 막히는지, 보기 전용 화면에서 단추가 숨는지 확인. 시험 그룹을 만들고 지운 기록이 로그 관리에 보이는지 확인.
- 타입 검사, 전체 테스트, 빌드.

## 5. 작업 순서

1. `evaluate.ts` 로 판정 분리 + 테스트 (동작 변화 없음 — 여기서 한 번 커밋)
2. 권한 변경 기록
3. 잠금 방지
4. 사람별 권한 탭
5. 최고 관리자 전용·일반사원 잠금
6. 콘솔 출입 확장 + 역할 표시
7. 화면 안 작업 권한
8. 관리자 역할 서식
9. 운영 DB 읽기 전용 확인 후 보고 → 배포는 지시를 받고

## 6. 정해 둔 것 (사용자가 '임의로 진행' 지시)

- 관리자 역할은 새 칸 없이 기존 역할 그룹과 권한표로 표현
- 그룹 권한 관리·데이터 백업은 최고 관리자 전용
- 서식은 권한표만 채우고 자동 생성하지 않음
- 기록은 기존 `systemLogs` 의 `변경` 유형 사용
- 본인 권한 해제는 막지 않고 확인만, 0명은 막음
