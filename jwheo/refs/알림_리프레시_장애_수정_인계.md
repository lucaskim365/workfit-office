  일정 알림의 `linkUrl`은 `/gw/calendar?date=...`

### 배제된 원인 (확인 완료)

알림 **수신**만으로는 화면이 리로드되지 않는다. 아래 모두 확인했다:

- `useNotifications`의 상태 갱신은 App 루트 리렌더만 유발. 라우트 컴포넌트는 모듈 상수 + 안정 key라 remount 없음
- Suspense fallback(`src/app/shell/AppShell.tsx:193`)은 이미 로드된 청크에서 재노출되지 않음
- `AuthProvider`는 마운트 시 1회 세션 복원만, 폴링·실시간 구독 없음 → 로그인 화면으로 튈 경로 없음
- 전역 ErrorBoundary / `window.onerror` / `unhandledrejection` 핸들러 자체가 없음

→ 기존 결재 알림에서 문제가 없었다는 관찰과 일치한다.

## 4. 이미 조치한 것 — 리마인더 측 (⚠ 미배포)

`appwrite/functions/calendar-reminder/src/main.js` 수정 완료. 구문 검사 통과.

1. **배치 생성 도입** — `CREATE_BATCH = 25`.
   전사 공개 일정은 수신자가 수백 명이라 한꺼번에 만들면 접속 중인 모든 클라이언트가
   그 수만큼 실시간 이벤트를 동시에 맞는다. 나눠 만들어 피크를 낮춘다.
2. **`Promise.all` → `Promise.allSettled`**.
   기존 코드는 500건 중 1건만 실패해도 전체가 reject → `reminded` 플래그 미설정 →
   **5분 뒤 전원이 다시 받는** 문제가 있었다. 이제 한 건이라도 성공하면 플래그를 세우고
   실패는 로그로만 남긴다. 전량 실패일 때만 다음 실행에서 재시도한다.

**수신자 범위(전 사원)와 실행 주기(5분)는 변경하지 않았다.**

배포 명령 (아직 실행하지 않음):
```
node scripts/deploy-calendar-reminder.mjs --prod
```

## 5. 수정해야 할 것 — 알림 공통

> 소유: `lucaskim365` / `hongchaerish`. 이 세션에서는 손대지 않았다.

### 5-1. [필수] 알림 클릭 시 탭 하드 내비게이션 제거

**위치** `public/firebase-messaging-sw.js:66-72`

```js
// 1) 데스크톱 창이 열려 있으면: 라우트 이동 없이 그 창에서 처리.   ← 주석
if (desktop) {
  if (data.roomId) {
    desktop.postMessage({ type: 'workfit-open-chat', roomId: data.roomId });  // 채팅: 정상
  } else if (data.linkUrl) {
    desktop.navigate(data.linkUrl);   // ← 주석과 달리 실제 페이지 이동
  }
```

채팅 알림만 `postMessage`로 앱에 넘겨 SPA 라우팅으로 처리하고, 그 외(결재·일정)는
`navigate()`로 페이지를 다시 로드한다. 주석의 의도와 코드가 어긋나 있다.

**수정 방향**
- `desktop.navigate(data.linkUrl)` → `desktop.postMessage({ type: 'workfit-open-link', linkUrl: data.linkUrl })`
- 수신부는 이미 있는 리스너에 분기 추가: `src/app/shell/AppShell.tsx:76-87`
  (현재 `'workfit-open-chat'`만 처리 → `'workfit-open-link'` 추가 후 react-router `navigate()`로 이동)
- PWA 경로도 동일 사안: 같은 파일 `:87` `pwa.navigate(target)`

**효과** 리마인더뿐 아니라 결재 알림 클릭 시 작업 유실도 함께 해소된다.

### 5-2. [필수] 알림 1건마다 전 접속자가 목록 전체를 재조회

**위치**
- `src/data/notification/notification.repo.ts:239`
- `src/data/approvalDoc/approvalDoc.repo.ts:216` (이벤트마다 결재 문서 전체 `loadAll()`)
- `src/data/documentExecution/documentExecution.repo.ts:259`

```js
subscribe(userId, callback) {
  void this.list(userId).then(callback);
  const unsub = appwriteClient!.subscribe(this.channels(), () => {
    void this.list(userId).then(callback);   // 이벤트 내용을 안 보고 전체 재조회
  });
```

구독 채널이 **컬렉션 전체**라 누구의 알림 문서가 생기든 모든 클라이언트가 수신하고,
콜백은 payload를 확인하지 않고 목록 전체를 다시 읽는다.

**원인** Firestore → Appwrite 이관의 부작용. Firestore 시절에는 서버측 필터가 있었다:
```js
onSnapshot(query(collection(COLL), where('userId', '==', userId)), ...)
```
Appwrite Realtime은 채널에 쿼리 필터를 걸 수 없어 "이벤트 발생 → 전체 재조회"로 `onSnapshot`
시맨틱을 대체했고(주석 `notification.repo.ts:161`), 그 과정에서 `userId` 필터가 소실됐다.

**규모** 동일 구독이 화면당 4곳에서 중복 마운트된다:
`src/app/App.tsx:135` / `src/app/shell/AppShell.tsx:49` /
`src/app/shell/Topbar.tsx:76` / `src/features/gw/desktop/GroupwarePanel.tsx:32`
→ 전 사원(수백 명) 대상 발송 시 **클라이언트 1대당 (수신자 수 × 4)회 재조회**.
브라우저 정지 수준이다. 전 사원 수신을 유지하려면 반드시 선행되어야 한다.

**수정 방향**
- 구독 콜백에서 이벤트 payload의 `userId`가 본인이 아니면 재조회를 건너뛴다 (각 1줄)
- 중복 구독 4개를 단일 구독 공유로 통합

### 5-3. [권장] 데스크톱 알림이 자동으로 안 사라지고 쌓임

**위치**
- `public/firebase-messaging-sw.js:82-85` (백그라운드)
  ```js
  tag: data.roomId || data.docId || undefined,   // 일정 알림은 둘 다 없어 tag 미지정 → 미병합
  requireInteraction: true,                       // 닫기 전까지 화면에 계속 유지
  ```
- `src/app/App.tsx` `onForegroundMessage` 블록 (포그라운드) — 동일 설정

알림이 화면에 남아 있어 치우려면 클릭해야 하고, 클릭하면 5-1 증상으로 이어진다.
5-1을 고쳐도 알림이 계속 쌓이는 것 자체는 그대로라 UX가 나쁘다.

**수정 방향** 일정 알림에 `tag` 부여(중복 병합) + `requireInteraction` 해제(자동 소멸).
알림센터에는 남으므로 "전 사원이 본다"는 요건에 영향 없다.

## 7. 미확인 사항

- **제보자가 OS 알림 배너를 클릭했는지.** 5-1은 클릭이 방아쇠다.
  클릭 없이도 리로드됐다면 위 사슬로는 설명되지 않고, 남은 후보는
  `src/app/App.tsx:13-24`의 청크 로드 실패 시 `window.location.reload()`
  (배포 직후 열려 있던 탭에서 발생. 8/27 해당 시간대 배포: 11:09, 11:16, 12:00, 12:03, 12:29, 12:37)
- **운영 `notifications`의 8/27 10:35~13:00 구간 `type='일정'` 문서 생성 시각 분포.**
  운영 API 키에 `executions.read` 스코프가 없어 조회하지 못했다.
  Appwrite 콘솔에서 확인하면 5분 간격 생성 여부가 확정된다.
